# Multi-service compose (Django + PostgreSQL + Redis)

## Bu darsda nimalarni o'rganasiz

- `healthcheck` orqali xizmatning **haqiqatan** tayyor bo'lishini kutishni sozlay olasiz
- `depends_on` bilan `condition: service_healthy`ni birlashtira olasiz
- `.env` fayli orqali Compose'da maxfiy ma'lumotlarni boshqara olasiz
- To'liq, production'ga yaqin Django + PostgreSQL + Redis Compose tizimini qura olasiz

## Nazariy qism

### `healthcheck` — xizmatning "haqiqatan tayyor"ligini tekshirish

4.1-darsda ko'rgan muammoni eslang: `depends_on` faqat konteynerning **ishga tushganini**, lekin xizmatning **ichki tayyorligini** kafolatlamaydi. Bu muammoni **`healthcheck`** hal qiladi — u konteyner ichida muntazam bir tekshiruv buyrug'ini bajarib, xizmat haqiqatan "sog'lom" (ishga tayyor) ekanini aniqlaydi:

```yaml
services:
  db:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=parol123
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5
```

| Parametr | Ma'nosi |
|---|---|
| `test` | Sog'liqni tekshirish uchun bajariladigan buyruq (`0` chiqish kodi — sog'lom) |
| `interval` | Tekshiruvlar orasidagi vaqt |
| `timeout` | Bitta tekshiruv uchun maksimal kutish vaqti |
| `retries` | Nechta muvaffaqiyatsiz urinishdan keyin "sog'lom emas" deb belgilanishi |

`pg_isready` — PostgreSQL bilan birga keladigan, bazaning so'rovlarni qabul qilishga tayyorligini tekshiruvchi maxsus buyruq.

### `depends_on` + `condition: service_healthy` — to'g'ri ketma-ketlik

```yaml
services:
  veb:
    build: .
    depends_on:
      db:
        condition: service_healthy    # faqat DB "sog'lom" deb belgilangach ishga tushadi!
      kesh:
        condition: service_healthy

  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5

  kesh:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
```

Endi `veb` xizmati — `db` va `kesh` **haqiqatan** ishga tayyor bo'lgandan **keyingina** ishga tushadi, 4.1-darsdagi `time.sleep()` kabi "ishonchsiz" yechimga endi hojat qolmaydi.

### `.env` fayli — maxfiy ma'lumotlarni Compose'dan ajratish

Parollarni to'g'ridan-to'g'ri `compose.yaml` ichiga yozish (va uni Git'ga commit qilish) xavfsizlik nuqtai nazaridan yomon amaliyot. Buning o'rniga `.env` fayli ishlatiladi:

`.env` (bu fayl **`.gitignore`ga qo'shilishi** kerak — Python kursining 5.2-darsida ko'rgan fayllar bilan ishlash mavzusiga bog'liq amaliy qoida):

```
POSTGRES_PASSWORD=juda_xavfsiz_parol_123
POSTGRES_DB=mening_bazam
DJANGO_SECRET_KEY=mening-maxfiy-kalitim
```

`compose.yaml`:

```yaml
services:
  db:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
      - POSTGRES_DB=${POSTGRES_DB}
```

Docker Compose `.env` faylini **avtomatik** o'qiydi (agar u `compose.yaml` bilan bir papkada bo'lsa), va `${O'ZGARUVCHI_NOMI}` sintaksisi orqali qiymatlarni almashtiradi. Bu — parollarni koddan (va Git tarixidan) ajratib turishning standart usuli.

### `env_file` — butun `.env` faylini bitta xizmatga uzatish

```yaml
services:
  veb:
    build: .
    env_file:
      - .env
```

`env_file` — `.env` faylidagi **barcha** o'zgaruvchilarni to'g'ridan-to'g'ri konteyner ichiga (muhit o'zgaruvchilari sifatida) uzatadi — bu `environment:` ostida har birini alohida-alohida qayta yozishdan qutqaradi.

### Named volume vs bind mount — Compose'da

```yaml
services:
  db:
    image: postgres:16
    volumes:
      - pg_data:/var/lib/postgresql/data      # NOMLI VOLUME (3.1-darsda ko'rgan)

  veb:
    build: .
    volumes:
      - .:/app                                  # BIND MOUNT — development uchun (host kodini "jonli" ulash)

volumes:
  pg_data:      # bu yerda e'lon qilinishi SHART (fayl oxirida)
```

## Amaliy misol

To'liq, production'ga yaqin **Django + PostgreSQL + Redis** Compose tizimi — bu sizning oldingi Django darsligingizdagi (16-dars) mavzuni to'liq amaliy Compose ko'rinishida yakunlaydi:

```
mening-django-loyiham/
├── compose.yaml
├── Dockerfile
├── .env
├── .dockerignore
├── requirements.txt
└── loyiha/
    ├── manage.py
    └── ...
```

`.env`:

```
POSTGRES_DB=django_baza
POSTGRES_USER=django_user
POSTGRES_PASSWORD=xavfsiz_parol_2026
DJANGO_SECRET_KEY=juda-maxfiy-kalit-hech-kimga-aytmang
DEBUG=False
```

`requirements.txt`:

```
django==5.1
psycopg2-binary==2.9.9
redis==5.0.1
gunicorn==22.0.0
```

`Dockerfile`:

```dockerfile
FROM python:3.13-slim

WORKDIR /app

RUN apt-get update && \
    apt-get install -y --no-install-recommends libpq5 && \
    rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["gunicorn", "--bind", "0.0.0.0:8000", "loyiha.wsgi:application"]
```

`compose.yaml`:

```yaml
services:
  veb:
    build: .
    ports:
      - "8000:8000"
    env_file:
      - .env
    environment:
      - DATABASE_HOST=db
      - REDIS_HOST=kesh
    depends_on:
      db:
        condition: service_healthy
      kesh:
        condition: service_healthy
    volumes:
      - static_fayllar:/app/staticfiles

  db:
    image: postgres:16
    env_file:
      - .env
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER}"]
      interval: 5s
      timeout: 3s
      retries: 5

  kesh:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pg_data:
  static_fayllar:
```

Ishga tushirish va boshqarish:

```bash
# 1. Ishga tushirish (birinchi marta quriladi)
docker compose up --build -d

# 2. Holatni tekshirish — barcha xizmatlar "healthy" bo'lishini kutish
docker compose ps

# 3. Django migratsiyalarini bajarish (konteyner ichida)
docker compose exec veb python3 manage.py migrate

# 4. Superuser yaratish
docker compose exec veb python3 manage.py createsuperuser

# 5. Loglarni kuzatish
docker compose logs -f veb

# 6. To'xtatish (ma'lumotlar saqlanadi)
docker compose down

# 7. Qayta ishga tushirish — ma'lumotlar HAMON mavjud (volume tufayli)
docker compose up -d
```

Bu — sizning Django darsligingizdagi 16-27-darslarda ko'rilgan barcha g'oyalarni (Docker, PostgreSQL, production sozlamalari) bitta, to'liq ishlaydigan, zamonaviy `healthcheck` va `.env` bilan mustahkamlangan tizimga birlashtiradi.

## Keng tarqalgan xatolar

**Xato 1:** `.env` faylini Git'ga commit qilib, maxfiy ma'lumotlarni oshkor qilish.
❌ `.env` fayli (parollar, maxfiy kalitlar bilan) `git add .` orqali repozitoriyaga tasodifan qo'shilib ketishi — bu jiddiy xavfsizlik xatosi, ayniqsa loyiha ochiq (public) GitHub repozitoriyasida bo'lsa.
✅ To'g'ri: `.gitignore` fayliga `.env` qatorini albatta qo'shing (Python kursining 5.2-darsida ko'rgan fayllar bilan ishlash odatining davomi); o'rniga `.env.example` (haqiqiy qiymatlarsiz, faqat kalit nomlari bilan) faylni repozitoriyaga qo'shish tavsiya etiladi.

**Xato 2:** `healthcheck`siz `depends_on`ga ishonib, production'da tasodifiy ulanish xatolariga duch kelish.
❌ Faqat oddiy `depends_on: [db]` (shart yo'q) — konteyner tez ishga tushadigan tizimlarda ko'pincha "ishlab ketadi", lekin sekinroq yoki yuklangan serverlarda tasodifiy, takrorlanmaydigan xatolarga olib kelishi mumkin.
✅ To'g'ri: ma'lumotlar bazasi va shunga o'xshash "sekin tayyorlanadigan" xizmatlar uchun har doim `healthcheck` + `condition: service_healthy` birgalikda ishlating.

**Xato 3:** development uchun bind mount (`.:/app`) va production konfiguratsiyasini bitta `compose.yaml`da aralashtirib, ikkalasini ham noto'g'ri sozlash.
❌ Production serverida ham `.:/app` (bind mount) qoldirilsa, bu 2.1-darsda ko'rgan "image o'zgarmasligi kerak" tamoyilini buzadi va server fayl tizimidagi tasodifiy o'zgarishlar production'ga bevosita ta'sir qilishi mumkin.
✅ To'g'ri: development va production uchun **alohida** compose fayllar (`compose.yaml` + `compose.override.yaml`, yoki `compose.prod.yaml`) yozish tavsiya etiladi — bu mavzu 6-bobda kengroq ko'riladi.

## Mashq/topshiriq

**(Oson)** 4.1-darsdagi PostgreSQL + Redis + Python misoliga `healthcheck` qo'shing (ikkala xizmat uchun ham), `depends_on`ni `condition: service_healthy` bilan yangilang, va `main.py`dagi `time.sleep(3)` qatorini olib tashlab, tizim baribir to'g'ri ishlashini tasdiqlang.

**(O'rtacha)** `.env` fayli yaratib, undagi `POSTGRES_PASSWORD` va `POSTGRES_DB` qiymatlarini `compose.yaml`da `${...}` sintaksisi orqali ishlating, so'ng `.env`dagi qiymatni o'zgartirib, `docker compose up --build` orqali o'zgarish qo'llanganini tasdiqlang.

**(Qiyin)** Yuqoridagi to'liq Django+PostgreSQL+Redis misolini o'zingiz (soddalashtirilgan Django loyihasi bilan, masalan bo'sh `django-admin startproject` natijasi) qayta yarating, `docker compose up --build -d` bilan ishga tushiring, `docker compose exec veb python3 manage.py migrate` orqali migratsiyalarni bajaring, va `docker compose ps` orqali barcha xizmatlar `healthy` holatida ekanini tasdiqlang.

## Qisqacha xulosa

`healthcheck` — konteyner ichida muntazam tekshiruv orqali xizmatning **haqiqatan** ishga tayyorligini aniqlaydi (`pg_isready`, `redis-cli ping` kabi buyruqlar bilan), `depends_on` bilan `condition: service_healthy` birgalikda ishlatilganda — bu `time.sleep()` kabi ishonchsiz "kutish" usullariga ehtiyojni yo'qotadi; `.env` fayli va `env_file`/`${...}` sintaksisi — maxfiy ma'lumotlarni `compose.yaml`dan (va Git tarixidan) ajratib turishning standart, xavfsiz usuli; bu ikkita vosita birgalikda — Django + PostgreSQL + Redis kabi ko'p xizmatli tizimlarni ishonchli, production'ga yaqin darajada Compose orqali boshqarish imkonini beradi.
