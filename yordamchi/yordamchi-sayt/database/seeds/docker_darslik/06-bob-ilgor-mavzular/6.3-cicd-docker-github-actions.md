# CI/CD bilan Docker (GitHub Actions misolida)

## Bu darsda nimalarni o'rganasiz

- CI/CD tushunchasini va Docker unda qanday rol o'ynashini tushunasiz
- GitHub Actions orqali Docker image'ni avtomatik qurish va test qilishni bilasiz
- Image'ni avtomatik Docker Hub'ga yuklashni (push) sozlay olasiz
- Butun kurs davomida o'rganilgan bilimlarni yagona, avtomatlashtirilgan workflow'ga birlashtira olasiz

## Nazariy qism

### CI/CD nima — qisqacha kirish

**CI** (Continuous Integration — uzluksiz integratsiya) — har safar kod GitHub'ga yuklanganda (push qilinganda), avtomatik ravishda **testlar** ishga tushirilishi. **CD** (Continuous Deployment/Delivery — uzluksiz yetkazish) — testlardan muvaffaqiyatli o'tgan kodni avtomatik ravishda **production'ga joylashtirish**. Docker — bu jarayonda markaziy rol o'ynaydi, chunki u testlash va deploy qilish muhitlarining **izchil** (0.1-darsda ko'rgan asosiy Docker afzalligi) bo'lishini kafolatlaydi.

### Nega Docker CI/CD uchun ideal

Python kursining 6.2-darsida `pytest` bilan testlashni o'rgangan edingiz. Muammo: testlar sizning kompyuteringizda ishlasa-yu, GitHub'ning serverida (boshqa Python versiyasi, boshqa operatsion tizim bilan) ishlamasa-chi? Docker — bu muammoni butunlay yo'qotadi: testlar **aynan production'da ishlatiladigan** image ichida bajariladi, shuning uchun "mening kompyuterimda ishlaydi" (0.1-darsdagi asosiy muammo) CI/CD kontekstida ham butunlay bartaraf etiladi.

### GitHub Actions — asosiy tushunchalar

**GitHub Actions** — GitHub'ning o'rnatilgan CI/CD platformasi bo'lib, `.github/workflows/` papkasidagi YAML fayllar orqali sozlanadi (4-bobdagi Docker Compose YAML sintaksisiga tanish bo'lasiz).

```
mening-loyiham/
├── .github/
│   └── workflows/
│       └── docker-ci.yaml
├── Dockerfile
├── compose.yaml
└── ...
```

### Oddiy workflow — image qurish va testlash

`.github/workflows/docker-ci.yaml`:

```yaml
name: Docker CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test-va-build:
    runs-on: ubuntu-latest

    steps:
      - name: Kodni yuklab olish
        uses: actions/checkout@v4

      - name: Docker image qurish
        run: docker build -t mening-loyiham:test .

      - name: Testlarni konteyner ichida ishga tushirish
        run: docker run --rm mening-loyiham:test pytest
```

| Qism | Ma'nosi |
|---|---|
| `on: push/pull_request` | Qachon workflow ishga tushishi (kod yuklanganda yoki PR ochilganda) |
| `runs-on: ubuntu-latest` | GitHub o'zining Ubuntu virtual mashinasida ishga tushiradi (0.2-darsda o'rgangan Ubuntu — endi CI muhitida ham!) |
| `actions/checkout@v4` | Repozitoriya kodini virtual mashinaga yuklab oladi |
| `docker build` | 2.1-darsda ko'rgan buyruq, endi avtomatik ishga tushmoqda |
| `docker run --rm ... pytest` | Konteyner ichida testlarni bajaradi, tugagach avtomatik o'chadi (1.1-darsdagi `--rm`) |

### Docker Compose bilan to'liq CI — ma'lumotlar bazasi bilan test qilish

Ko'p loyihalarda testlar PostgreSQL kabi haqiqiy ma'lumotlar bazasini talab qiladi. Buni CI'da ham Compose orqali tashkil qilish mumkin:

```yaml
name: Docker CI (baza bilan)

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Kodni yuklab olish
        uses: actions/checkout@v4

      - name: Test uchun .env yaratish
        run: |
          echo "POSTGRES_DB=test_db" > .env
          echo "POSTGRES_USER=test_user" >> .env
          echo "POSTGRES_PASSWORD=test_parol" >> .env

      - name: Xizmatlarni ishga tushirish
        run: docker compose up -d --build

      - name: Baza tayyor bo'lishini kutish
        run: sleep 10

      - name: Migratsiya va testlarni bajarish
        run: |
          docker compose exec -T veb python3 manage.py migrate
          docker compose exec -T veb pytest

      - name: Loglarni chiqarish (xato bo'lsa, diagnostika uchun)
        if: failure()
        run: docker compose logs

      - name: Tozalash
        if: always()
        run: docker compose down -v
```

`if: failure()` — bu qadam faqat **oldingi qadamlardan biri muvaffaqiyatsiz** bo'lganda ishga tushadi (1.3-darsdagi diagnostika tamoyili — loglar avtomatik chiqariladi). `if: always()` — natijadan qat'iy nazar (muvaffaqiyat yoki xato) **har doim** bajariladi, bu tozalashning har qanday holatda amalga oshishini kafolatlaydi.

### Docker Hub'ga avtomatik yuklash — CD qismi

Testlar muvaffaqiyatli o'tgach, image'ni avtomatik Docker Hub'ga yuklash (1.2-darsda qo'lda ko'rgan `docker push`ning avtomatlashtirilgan versiyasi):

```yaml
jobs:
  test-va-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t mening-loyiham:test .
      - run: docker run --rm mening-loyiham:test pytest

  push-docker-hub:
    needs: test-va-build          # FAQAT test-va-build MUVAFFAQIYATLI tugagach ishga tushadi
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'   # FAQAT main branch'ga push qilinganda

    steps:
      - uses: actions/checkout@v4

      - name: Docker Hub'ga kirish
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Qurish va yuklash
        run: |
          docker build -t foydalanuvchi_nomi/mening-loyiham:latest .
          docker push foydalanuvchi_nomi/mening-loyiham:latest
```

`needs: test-va-build` — bu `push-docker-hub` ishi (job) **faqat** birinchi ish (`test-va-build`) muvaffaqiyatli tugagandan keyin ishga tushishini bildiradi — agar testlar muvaffaqiyatsiz bo'lsa, **hech qachon** buzuq kod Docker Hub'ga yuklanmaydi. Bu — CI/CD'ning eng muhim amaliy qiymati.

### GitHub Secrets — maxfiy ma'lumotlarni CI'da boshqarish

`${{ secrets.DOCKERHUB_USERNAME }}` va `${{ secrets.DOCKERHUB_TOKEN }}` — bu qiymatlar workflow fayli ichida **yozilmagan**, balki GitHub repozitoriyasining Settings → Secrets and variables → Actions bo'limida alohida saqlanadi. Bu — 4.2-darsdagi `.env` va 6.1-darsdagi `secrets` tushunchalarining GitHub Actions'dagi ekvivalenti: maxfiy ma'lumotlar hech qachon kod (yoki workflow fayli) ichida ochiq ko'rinmaydi.

## Amaliy misol

To'liq, real loyiha uchun ishlaydigan CI/CD pipeline — Django + PostgreSQL loyihasi uchun (5.1-darsdagi loyihaga asoslanib):

```yaml
# .github/workflows/django-ci-cd.yaml
name: Django CI/CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Kodni yuklab olish
        uses: actions/checkout@v4

      - name: Test muhiti uchun .env yaratish
        run: |
          cat << EOF > .env
          POSTGRES_DB=test_db
          POSTGRES_USER=test_user
          POSTGRES_PASSWORD=test_parol
          DJANGO_SECRET_KEY=faqat-test-uchun-maxfiy-emas
          DEBUG=True
          EOF

      - name: Docker Compose bilan ishga tushirish
        run: docker compose up -d --build

      - name: Baza tayyorligini kutish
        run: |
          for i in {1..10}; do
            docker compose exec -T db pg_isready -U test_user && break
            sleep 2
          done

      - name: Migratsiya
        run: docker compose exec -T veb python3 manage.py migrate

      - name: Testlarni bajarish
        run: docker compose exec -T veb pytest

      - name: Xato bo'lsa, barcha loglarni ko'rsatish
        if: failure()
        run: docker compose logs

      - name: Tozalash
        if: always()
        run: docker compose down -v

  build-va-push:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'

    steps:
      - uses: actions/checkout@v4

      - name: Docker Hub'ga kirish
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Production image qurish va yuklash
        run: |
          docker build -t ${{ secrets.DOCKERHUB_USERNAME }}/django-loyiha:${{ github.sha }} .
          docker build -t ${{ secrets.DOCKERHUB_USERNAME }}/django-loyiha:latest .
          docker push ${{ secrets.DOCKERHUB_USERNAME }}/django-loyiha:${{ github.sha }}
          docker push ${{ secrets.DOCKERHUB_USERNAME }}/django-loyiha:latest
```

`${{ github.sha }}` — har bir commit'ning noyob identifikatori (hash) — image'ni **shu aniq commit** bilan belgilash orqali, 1.2-darsda ko'rgan "`latest` tag'idan saqlaning" qoidasini CI/CD darajasida amalga oshiradi: agar biror muammo topilsa, aynan **qaysi commit** buzuq image yaratganini aniq bilish mumkin.

Bu workflow — har safar `main` branch'ga kod yuklanganda: (1) avtomatik testlarni haqiqiy PostgreSQL bilan, konteynerlarda ishga tushiradi, (2) faqat testlar o'tsa, image'ni quradi va Docker Hub'ga ikkita tag bilan (aniq commit va `latest`) yuklaydi — bu butun kursda o'rganilgan deyarli barcha tushunchalarni (Dockerfile, Compose, healthcheck, xavfsizlik, tozalash) yagona, avtomatlashtirilgan jarayonga birlashtiradi.

## Keng tarqalgan xatolar

**Xato 1:** maxfiy ma'lumotlarni (Docker Hub parolini) to'g'ridan-to'g'ri workflow faylida yozish.
❌ `password: mening_haqiqiy_parolim` — bu fayl repozitoriyada ochiq saqlanadi, va agar repozitoriya public bo'lsa, parol **hammaga ko'rinadi**.
✅ To'g'ri: har doim GitHub Secrets (`${{ secrets.NOM }}`) ishlating — bu qiymatlar hech qachon workflow loglarida yoki fayl tarixida ochiq ko'rinmaydi.

**Xato 2:** `needs:` munosabatini unutib, testlar muvaffaqiyatsiz bo'lsa ham image'ni Docker Hub'ga yuklash.
❌ Agar `push-docker-hub` ishi `needs: test-va-build`siz alohida, mustaqil ishlasa, u testlar natijasidan qat'iy nazar ishga tushishi mumkin — bu buzuq kodni tasodifan production'ga yuklab qo'yishga olib kelishi mumkin.
✅ To'g'ri: har doim `needs:` orqali ishlar orasidagi bog'liqlikni aniq belgilang, shunda faqat muvaffaqiyatli testlardan keyin deploy bosqichi ishga tushadi.

**Xato 3:** CI muhitida `docker compose down -v`ni "har doim" (`if: always()`) ishlatmaslik, natijada keyingi workflow ishga tushishlarida eski holat qoldiqlari to'planib qolishi.
❌ Agar tozalash faqat muvaffaqiyat holatida (standart holat) bajarilsa, va workflow xato bilan tugasa, GitHub'ning virtual mashinasida (garchi u har safar "toza" bo'lsa ham) resurs boshqaruvi izchil bo'lmasligi mumkin.
✅ To'g'ri: yuqoridagi misolda ko'rganimizdek, tozalash qadamini har doim `if: always()` bilan belgilang — bu 6.2-darsdagi "har doim toza holatni saqlash" tamoyilining CI/CD'dagi qo'llanilishi.

## Mashq/topshiriq

**(Oson)** Oddiy GitHub Actions workflow yozing — faqat `docker build` va `docker run --rm ... python3 -m pytest` bosqichlari bilan, Python kursining 6.2-darsidagi oddiy `test_*.py` fayllaringiz uchun.

**(O'rtacha)** 5.1-darsdagi Django loyihangiz uchun to'liq test workflow'ini (Compose bilan, PostgreSQL healthcheck kutish, migratsiya, pytest, `if: failure()`/`if: always()` bilan) yozing — GitHub'ga push qilib sinab ko'rmasangiz ham, faylning sintaktik to'g'ri va mantiqiy izchil ekanini tekshiring.

**(Qiyin)** Yuqoridagi to'liq `django-ci-cd.yaml` namunasini asos qilib, ikkinchi `deploy` ishini (job) qo'shing — bu ish `build-va-push`dan keyin ishga tushib, (soddalashtirilgan holda) faqat "Deploy qilindi: <image nomi>" deb `echo` qiladi (haqiqiy serverga ulanish emas, faqat workflow tuzilmasini mashq qilish uchun), va uni ham faqat `main` branch uchun sharlab qo'ying.

## Qisqacha xulosa

CI/CD — kod har safar GitHub'ga yuklanganda avtomatik testlash (CI) va, muvaffaqiyatli testlardan so'ng, avtomatik joylashtirish (CD) jarayoni bo'lib, Docker bu jarayonda **izchil, ishonchli** test va deploy muhitini ta'minlaydi; GitHub Actions orqali `docker build`, `docker compose up`, `pytest` (Python kursining 6.2-darsi) va `docker push` (1.2-dars) bosqichlari `.github/workflows/*.yaml` faylida birlashtirilib, `needs:` orqali bosqichlar ketma-ketligi, GitHub Secrets orqali esa maxfiy ma'lumotlar xavfsiz boshqariladi — bu, butun Docker darsligi davomida o'rganilgan barcha tushunchalarni (image qurish, Compose, healthcheck, xavfsizlik, tozalash) yagona, avtomatlashtirilgan ishlab chiqarish jarayoniga birlashtirib, kursni yakunlaydi.
