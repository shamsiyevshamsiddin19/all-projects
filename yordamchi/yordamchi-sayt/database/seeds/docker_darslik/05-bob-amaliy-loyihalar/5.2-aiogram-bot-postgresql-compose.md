# Aiogram bot + PostgreSQL Docker Compose bilan

## Bu darsda nimalarni o'rganasiz

- Django va Aiogram botni **bitta** PostgreSQL bazasini ulashadigan holda, ikkita alohida konteynerda ishga tushira olasiz
- `runserver` va `runbot` management buyruqlarini Compose orqali parallel boshqara olasiz
- Bir nechta Django-asosli xizmat orasida umumiy image'dan foydalanishni (`build` takrorlanishini) tushunasiz
- Bot konteyneri qulab tushganda avtomatik qayta ishga tushishini (`restart` siyosati) sozlay olasiz

## Nazariy qism

### Vaziyat — Django darsligidagi arxitekturaning Docker ko'rinishi

Sizning oldingi Django darsligingizning 2-bo'limida (18-27-darslar) Django va Aiogram bot **bitta** kod bazasi va **bitta** PostgreSQL orqali ishlaydigan arxitektura qurilgan edi — `runserver` va `runbot` ikkita **alohida jarayon** sifatida, ikkita terminalda ishga tushirilgan. Endi shu arxitekturani Docker Compose orqali, ikkita **alohida konteyner** sifatida tashkil qilamiz — bu production'da ishonchli, kuzatiladigan va boshqariladigan yondashuv.

### Arxitektura sxemasi

```
┌─────────────────┐     ┌─────────────────┐
│  veb (Django)      │     │  bot (Aiogram)     │
│  runserver/gunicorn │     │  runbot              │
└────────┬────────┘     └────────┬────────┘
         │                          │
         └──────────┬─────────────┘
                       │
              ┌─────────────┐
              │  db (PostgreSQL) │
              └─────────────┘
```

Ikkala konteyner (`veb` va `bot`) — **bir xil** Django loyihasi kodidan foydalanadi (bir xil model, bir xil ma'lumotlar bazasi sxemasi), lekin ular **turli buyruqlar** bilan ishga tushiriladi va **mustaqil** jarayonlar sifatida ishlaydi.

### Bitta image, ikkita xizmat — `build` takrorlanmasligi

Docker Compose'da bir nechta xizmat **bir xil** Dockerfile'dan image qurishi mumkin, lekin turli buyruqlar (`command:`) bilan ishga tushirilishi mumkin:

```yaml
services:
  veb:
    build: .
    command: python3 manage.py runserver 0.0.0.0:8000
    ports:
      - "8000:8000"
    depends_on:
      db:
        condition: service_healthy
    env_file:
      - .env

  bot:
    build: .              # XUDDI O'SHA Dockerfile, lekin BOSHQA buyruq bilan
    command: python3 manage.py runbot
    depends_on:
      db:
        condition: service_healthy
    env_file:
      - .env

  db:
    image: postgres:16
    env_file:
      - .env
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER}"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pg_data:
```

`command:` — Dockerfile'dagi `CMD`ni **almashtiradi** (2.1-darsda ko'rgan tushuncha, endi Compose kontekstida): `veb` va `bot` — bir xil image'dan qurilgan, lekin har biri o'z, aniq vazifasiga mos buyruq bilan ishga tushadi.

> 📌 **Bu — resurs tejash nuqtai nazaridan samarali.** Docker `veb` va `bot` uchun image'ni **ikki marta qayta qurmaydi** — agar ikkalasi ham `build: .` (bir xil Dockerfile'ga ishora qiluvchi) ishlatsa, Compose buni aniqlab, faqat **bitta** marta quradi va ikkalasiga ham ishlatadi.

### `restart` siyosati — bot yiqilib qolsa, avtomatik qayta ishga tushirish

Telegram botlar ba'zan tarmoq xatolari yoki kutilmagan istisnolar tufayli to'xtab qolishi mumkin (Python kursining 5.1-darsida ko'rgan istisno tushunchasi bevosita bog'liq). Production'da bot **avtomatik** qayta ishga tushishi kerak:

```yaml
services:
  bot:
    build: .
    command: python3 manage.py runbot
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
```

| `restart` qiymati | Ma'nosi |
|---|---|
| `no` (standart) | Konteyner to'xtasa, qayta ishga tushirilmaydi |
| `always` | Konteyner qanday to'xtagan bo'lishidan qat'iy nazar, **har doim** qayta ishga tushiriladi |
| `unless-stopped` | Qayta ishga tushiriladi, **agar siz uni qo'lda to'xtatmagan bo'lsangiz** (`docker compose stop`) |
| `on-failure` | Faqat **xato** (nolinchi bo'lmagan chiqish kodi) bilan to'xtaganda qayta ishga tushiriladi |

`unless-stopped` — production botlar uchun eng tavsiya etiladigan variant: agar bot ichki xatodan yiqilsa, Docker uni avtomatik qayta ishga tushiradi, lekin agar siz ataylab `docker compose stop bot` desangiz, u qayta o'z-o'zidan yonib ketmaydi.

### Loglarni ikkita xizmat uchun alohida kuzatish

```bash
docker compose logs -f veb    # faqat Django loglari
docker compose logs -f bot     # faqat bot loglari
docker compose logs -f          # ikkalasi HAM, aralash (prefiks bilan ajratilgan)
```

Bu — 25-darsdagi (Django darsligi) `runbot` va `runserver`ni ikkita alohida terminalda kuzatishning Docker'dagi ekvivalenti, lekin endi loglar Docker tomonidan markazlashtirilgan tarzda boshqariladi.

### Bot konteynerida migratsiya — kim bajarishi kerak

Muhim savol: agar ikkala konteyner (`veb` va `bot`) bir xil bazani ishlatsa, migratsiyani **qaysi biri** bajarishi kerak? Odatda — faqat **bittasi**, chunki migratsiyani ikki marta (parallel) bajarish ziddiyatlarga olib kelishi mumkin:

```yaml
services:
  migratsiya:
    build: .
    command: python3 manage.py migrate
    depends_on:
      db:
        condition: service_healthy
    env_file:
      - .env

  veb:
    build: .
    command: python3 manage.py runserver 0.0.0.0:8000
    depends_on:
      migratsiya:
        condition: service_completed_successfully   # migratsiya TUGAGANIDAN keyin ishga tushadi
    ports:
      - "8000:8000"

  bot:
    build: .
    command: python3 manage.py runbot
    depends_on:
      migratsiya:
        condition: service_completed_successfully
    restart: unless-stopped
```

`condition: service_completed_successfully` — Compose'ga `migratsiya` xizmati **muvaffaqiyatli tugaguncha** (chiqish kodi `0` bilan tugaguncha) kutishni buyuradi, faqat shundan keyin `veb` va `bot` ishga tushadi. Bu — migratsiyani alohida, bir martalik "vazifa" (task) sifatida tashkil qilishning toza va ishonchli usuli.

## Amaliy misol

To'liq Do'kon boti tizimi (Django darsligining 27-darsidagi yakuniy loyihaning Docker Compose ko'rinishi):

```
dokon-bot-loyiha/
├── compose.yaml
├── Dockerfile
├── .env
├── requirements.txt
└── loyiha/
    ├── manage.py
    ├── loyiha/
    │   └── settings.py
    ├── apps/
    │   ├── shop/           # Order, Product modellari (Django darsligi 20-dars)
    │   └── bot/
    │       ├── loader.py
    │       ├── handlers/
    │       └── management/commands/runbot.py
    └── ...
```

`compose.yaml`:

```yaml
services:
  migratsiya:
    build: .
    command: python3 loyiha/manage.py migrate --noinput
    env_file:
      - .env
    depends_on:
      db:
        condition: service_healthy

  veb:
    build: .
    command: python3 loyiha/manage.py runserver 0.0.0.0:8000
    ports:
      - "8000:8000"
    env_file:
      - .env
    depends_on:
      migratsiya:
        condition: service_completed_successfully

  bot:
    build: .
    command: python3 loyiha/manage.py runbot
    restart: unless-stopped
    env_file:
      - .env
    depends_on:
      migratsiya:
        condition: service_completed_successfully

  db:
    image: postgres:16
    env_file:
      - .env
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER}"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pg_data:
```

Ishga tushirish va tekshirish:

```bash
# 1. Barcha xizmatlarni ishga tushirish
docker compose up --build -d

# 2. Ketma-ketlikni kuzatish — migratsiya avval, keyin veb va bot
docker compose logs migratsiya
docker compose ps
# migratsiya-1   Exited (0)   <- muvaffaqiyatli tugadi
# veb-1          Up            <- endi ishga tushdi
# bot-1          Up            <- endi ishga tushdi
# db-1           Up (healthy)

# 3. Admin panelga kirib, mahsulot qo'shish (Django darsligi 21-dars mantig'i)
docker compose exec veb python3 loyiha/manage.py createsuperuser

# 4. Bot loglarini kuzatish — Telegram'dan /start yuborilganda
docker compose logs -f bot

# 5. Agar bot ataylab to'xtatilsa (xato simulyatsiyasi), avtomatik qayta tiklanishini kuzatish
docker compose kill bot
sleep 3
docker compose ps
# bot-1   Up   <- restart: unless-stopped tufayli AVTOMATIK qayta ishga tushdi!
```

## Keng tarqalgan xatolar

**Xato 1:** migratsiyani `veb` va `bot`ning har birida alohida bajarishga urinish.
❌ Ikkala xizmat ham o'zining `command:`ida `migrate && runserver` yoki `migrate && runbot` deb yozsa, ikkalasi **bir vaqtda**, parallel migratsiya bajarishga urinishi mumkin — bu PostgreSQL darajasida ziddiyat (lock) yoki xatoga olib kelishi mumkin.
✅ To'g'ri: migratsiyani **alohida, bitta** xizmat sifatida ajrating (`migratsiya` xizmati), va qolganlar `service_completed_successfully` sharti bilan undan keyin ishga tushsin.

**Xato 2:** botga `restart: unless-stopped` qo'shishni unutish.
❌ Standart holda (`restart` ko'rsatilmasa), agar bot biror kutilmagan xato tufayli qulab tushsa, u **qayta ishga tushmaydi** va foydalanuvchilar botga murojaat qilolmay qoladi, buni administrator darhol sezmasligi mumkin.
✅ To'g'ri: production botlar uchun har doim `restart: unless-stopped` (yoki `always`) qo'shing.

**Xato 3:** `veb` va `bot` konteynerlarida turli, mos kelmaydigan kod versiyasi ishlatilishi.
❌ Agar `veb` va `bot` uchun turli Dockerfile yoki turli image versiyalari ishlatilsa (masalan, biri yangilangan, ikkinchisi eski qolgan), ular bir xil ma'lumotlar bazasi modeliga tayanayotgani uchun **mos kelmaslik** xatolariga olib kelishi mumkin.
✅ To'g'ri: `veb` va `bot` har doim **bir xil** `build: .` (bitta Dockerfile, bitta image) dan foydalanishi kerak — bu ularning har doim bir xil kod versiyasi va model sxemasi bilan ishlashini kafolatlaydi.

## Mashq/topshiriq

**(Oson)** Yuqoridagi `compose.yaml`ni (soddalashtirilgan, `migratsiya` xizmatisiz, faqat `veb`, `bot`, `db` bilan) yozib, `docker compose up --build -d` orqali barcha uchta konteyner ishga tushishini `docker compose ps` bilan tasdiqlang.

**(O'rtacha)** `bot` xizmatiga `restart: unless-stopped` qo'shing, so'ng `docker compose kill bot` orqali uni "yiqiting" va bir necha soniyadan keyin `docker compose ps` orqali u avtomatik qayta ishga tushganini tasdiqlang.

**(Qiyin)** To'liq migratsiya-ajratilgan tizimni (`migratsiya`, `veb`, `bot`, `db`, `condition: service_completed_successfully` bilan) quring va ishga tushiring, so'ng ataylab `migratsiya` buyrug'iga xato kiritib (masalan, mavjud bo'lmagan `manage.py` yo'li), `veb` va `bot` xizmatlarining **umuman ishga tushmasligini** kuzating va sababini `docker compose ps`/`docker compose logs migratsiya` orqali tushuntiring.

<details>
<summary>Javoblarni ko'rish</summary>

1. Yuqoridagi misoldan `migratsiya` xizmatini olib tashlab, `veb` va `bot`ning `depends_on`ini oddiy `db: {condition: service_healthy}`ga o'zgartirish kifoya; `docker compose ps` — barcha uchta xizmat `Up` holatida ko'rinadi.
2. `bot` xizmatiga `restart: unless-stopped` qo'shilgach, `docker compose kill bot` konteynerni majburan to'xtatadi, lekin Docker uni deyarli darhol (bir necha soniya ichida) qayta ishga tushiradi — `docker compose ps`da `bot` yana `Up` holatida ko'rinadi, garchi `CONTAINER ID` yoki ishga tushish vaqti o'zgargan bo'lsa ham.
3. `migratsiya` xizmati xato bilan (masalan, `Exited (1)`) tugaydi; `condition: service_completed_successfully` — faqat **muvaffaqiyatli** (kod `0`) tugashni "muvaffaqiyatli tugash" deb hisoblaydi, shuning uchun `veb` va `bot` **hech qachon** ishga tushmaydi — `docker compose ps`da ular `Created` yoki umuman ko'rinmaydigan holatda qoladi; `docker compose logs migratsiya` esa aniq xato sababini (masalan, `python3: can't open file`) ko'rsatadi.

</details>

## Qisqacha xulosa

Django va Aiogram bot — Docker Compose orqali **bitta** image (bitta `Dockerfile`)dan qurilib, ikkita alohida xizmat (`veb` — `runserver`/Gunicorn, `bot` — `runbot`) sifatida, bitta umumiy PostgreSQL bazasini ulashgan holda ishga tushiriladi; migratsiyani ziddiyatlarsiz bajarish uchun uni alohida `migratsiya` xizmatiga ajratib, `condition: service_completed_successfully` orqali qolgan xizmatlarni undan keyin ishga tushirish tavsiya etiladi; `restart: unless-stopped` esa botning tasodifiy xatolardan keyin ham avtomatik ishlashda davom etishini ta'minlaydi — bu Django darsligining 2-bo'limida qurilgan arxitekturani to'liq, ishonchli production Docker tizimiga aylantiradi.
