# Alembic bilan migratsiyalar

## Bu darsda nimalarni o'rganasiz

- Migratsiya nima ekanini va nima uchun `create_all()` yetarli emasligini tushunasiz
- Alembic'ni loyihaga sozlashni o'rganasiz
- Migratsiya fayllarini avtomatik generatsiya qilish va qo'llashni bilasiz
- Migratsiyalarni Git bilan qanday boshqarishni tushunasiz

## Nazariy qism

### Migratsiya nima va nima uchun kerak

4.1-darsda ko'rilgan `SQLModel.metadata.create_all(engine)` — faqat **mavjud bo'lmagan** jadvallarni yaratadi. Lekin real loyiha rivojlanishi davomida, deyarli har doim quyidagi ehtiyojlar yuzaga keladi:

- Mavjud jadvalga **yangi ustun** qo'shish
- Ustun turini o'zgartirish
- Ustunni o'chirish yoki nomini o'zgartirish
- Jadvallar orasida yangi bog'lanish (foreign key) qo'shish

Bunday o'zgarishlarni **xavfsiz, boshqariladigan va qaytariladigan** tarzda amalga oshirish uchun **migratsiya vositasi** kerak bo'ladi. **Alembic** — SQLAlchemy/SQLModel ekotizimida bu vazifa uchun standart, rasmiy tavsiya etilgan vosita hisoblanadi.

> 📌 **Git bilan konseptual o'xshashlik:** migratsiya fayllari — Git va GitHub darsligining 1-bobida ko'rilgan commit'larga o'xshaydi: har bir migratsiya, ma'lumotlar bazasi sxemasidagi **bitta o'zgarishni** ifodalaydi, va ular ketma-ket, tarixiy tartibda qo'llaniladi. Xuddi Git tarixi orqali kod holatini istalgan nuqtaga qaytarish mumkin bo'lgani kabi, Alembic orqali ham ma'lumotlar bazasi sxemasini oldingi versiyaga qaytarish (`downgrade`) mumkin.

### Alembic'ni o'rnatish va sozlash

```bash
uv add alembic
```

```bash
alembic init migrations
```

Bu buyruq quyidagi tuzilmani yaratadi:

```
migrations/
├── env.py              # Alembic'ning asosiy konfiguratsiyasi
├── script.py.mako       # Yangi migratsiya fayllari uchun shablon
└── versions/            # Har bir migratsiya shu yerda saqlanadi
alembic.ini              # Asosiy sozlamalar fayli
```

### `alembic.ini` — ma'lumotlar bazasi manzilini sozlash

```ini
# alembic.ini
sqlalchemy.url = postgresql://fastapi_user:parol123@localhost:5432/kutubxona_db
```

> ⚠️ **Xavfsizlik eslatmasi:** `alembic.ini` faylida parolni ochiq yozish — 4.1-darsdagi `.env` tamoyiliga zid. Amaliyotda, `env.py` faylini o'zgartirib, manzilni dasturiy ravishda `.env`dan o'qish tavsiya etiladi (quyida ko'rsatiladi).

### `env.py` — SQLModel bilan bog'lash

Alembic, standart holda sizning SQLModel jadvallaringiz haqida "bilmaydi". `migrations/env.py` faylida, quyidagi bog'lanishni sozlash kerak:

```python
# migrations/env.py (tegishli qismi)
from sqlmodel import SQLModel
from app.models import Kitob, Muallif  # BARCHA modellar shu yerda import qilinishi kerak
from app.config import sozlamalar

config.set_main_option("sqlalchemy.url", sozlamalar.database_url)
target_metadata = SQLModel.metadata
```

> 📌 **Nima uchun barcha modellarni import qilish shart:** Alembic, `target_metadata` orqali, qaysi jadvallar "bo'lishi kerak"ligini biladi; agar biror model fayli import qilinmasa, Alembic uni "mavjud emas" deb hisoblab, uni **o'chirib tashlashga** urinishi mumkin — bu, migratsiya generatsiya qilishdagi eng keng tarqalgan chalkashliklardan biri.

### Birinchi migratsiyani avtomatik generatsiya qilish

```bash
alembic revision --autogenerate -m "Boshlang'ich jadvallar: Kitob va Muallif"
```

Bu buyruq — joriy modellar (`target_metadata`) va ma'lumotlar bazasining **hozirgi holatini solishtirib**, farqni avtomatik aniqlaydi va `migrations/versions/` papkasida yangi Python faylini yaratadi:

```python
# migrations/versions/a1b2c3d4e5f6_boshlang_ich_jadvallar.py
def upgrade():
    op.create_table(
        'muallif',
        sa.Column('id', sa.Integer(), nullable=False),
        sa.Column('ism', sa.String(), nullable=False),
        sa.PrimaryKeyConstraint('id')
    )
    op.create_table(
        'kitob',
        sa.Column('id', sa.Integer(), nullable=False),
        sa.Column('nomi', sa.String(length=200), nullable=False),
        # ...
    )

def downgrade():
    op.drop_table('kitob')
    op.drop_table('muallif')
```

| Funksiya | Vazifasi |
|---|---|
| `upgrade()` | O'zgarishni **qo'llash** uchun kod (masalan, jadval/ustun yaratish) |
| `downgrade()` | O'zgarishni **bekor qilish** uchun kod (Git darsligining 5.1-darsidagi `git revert`ga konseptual o'xshash) |

> ⚠️ **Har doim avtomatik generatsiya qilingan migratsiyani tekshiring:** Alembic'ning `--autogenerate` xususiyati — juda foydali, lekin **mukammal emas**. Ba'zi o'zgarishlar (masalan, ustun nomini o'zgartirish) — Alembic tomonidan "eski ustunni o'chirish + yangi ustun qo'shish" sifatida noto'g'ri aniqlanishi mumkin (bu — mavjud ma'lumotni yo'qotadi). Har doim generatsiya qilingan faylni qo'lda ko'rib chiqing.

### Migratsiyani qo'llash

```bash
alembic upgrade head
```

`head` — "eng so'nggi (oxirgi) migratsiyagacha" degan ma'noni bildiradi. Bu buyruq, hali qo'llanilmagan barcha migratsiyalarni, ketma-ket tartibda bajaradi.

### Migratsiyani orqaga qaytarish

```bash
# Bitta migratsiyani orqaga qaytarish
alembic downgrade -1

# Muayyan migratsiyagacha qaytarish
alembic downgrade a1b2c3d4e5f6

# Barchasini bekor qilish (bo'sh bazaga qaytarish)
alembic downgrade base
```

### Migratsiya tarixini ko'rish

```bash
alembic history --verbose
alembic current    # hozirgi qo'llangan migratsiya qaysi ekanini ko'rsatadi
```

### Amaliy stsenariy — yangi ustun qo'shish

Loyiha rivojlanishi davomida, `Kitob` modeliga yangi `tavsif` maydoni qo'shish kerak bo'lsa:

```python
# app/models.py - o'zgartirish
class KitobAsosi(SQLModel):
    nomi: str = Field(max_length=200)
    muallif: str
    yil: int
    tavsif: str | None = Field(default=None, max_length=1000)   # YANGI maydon
```

```bash
alembic revision --autogenerate -m "Kitob jadvaliga tavsif ustuni qo'shish"
alembic upgrade head
```

Bu — mavjud jadvaldagi ma'lumotlarni **yo'qotmasdan**, faqat yangi ustunni qo'shadi (mavjud qatorlarda, yangi ustun `NULL` qiymati bilan to'ldiriladi).

### Migratsiyalarni Git bilan boshqarish

`migrations/versions/` papkasidagi fayllar — Python darsligi va Git darsligida ko'rilgan tamoyilga muvofiq, **har doim Git'da kuzatilishi** kerak (Git va GitHub darsligining 6.2-darsida, Django migratsiyalari uchun ko'rilgan xuddi shu qoida, Alembic uchun ham to'liq amal qiladi):

```gitignore
# .gitignore - migratsiya FAYLLARI emas, faqat vaqtinchalik keshlar e'tiborsiz qoldiriladi
__pycache__/
```

Jamoaviy loyihalarda, agar ikki dasturchi bir vaqtda migratsiya yaratsa, Git darsligining 6.2-darsida ko'rilgan "migratsiya konflikti" muammosi bu yerda ham yuzaga kelishi mumkin — Alembic'da bu, `alembic merge` buyrug'i orqali hal qilinadi (Django'dagi `--merge`ga konseptual o'xshash).

## Amaliy misol

To'liq migratsiya jarayoni — noldan, birinchi jadvaldan, keyingi o'zgarishgacha:

```bash
# 1. Alembic'ni sozlash
uv add alembic
alembic init migrations
```

```python
# migrations/env.py ichida qo'shiladi
from app.models import Kitob, Muallif
from app.config import sozlamalar

config.set_main_option("sqlalchemy.url", sozlamalar.database_url)
target_metadata = SQLModel.metadata
```

```bash
# 2. Birinchi migratsiya
alembic revision --autogenerate -m "Boshlang'ich jadvallar"
alembic upgrade head

# 3. Ma'lumotlar bazasida jadvallar yaratilganini tekshirish
docker exec -it fastapi-db psql -U fastapi_user -d kutubxona_db -c "\dt"
```

```python
# 4. Modelga yangi maydon qo'shamiz
class KitobAsosi(SQLModel):
    nomi: str = Field(max_length=200)
    muallif: str
    yil: int
    tavsif: str | None = None    # YANGI
```

```bash
# 5. Yangi migratsiya
alembic revision --autogenerate -m "Kitobga tavsif ustuni qo'shildi"

# 6. Generatsiya qilingan faylni tekshiramiz (migrations/versions/ ichida)
cat migrations/versions/<yangi_fayl>.py

# 7. Qo'llaymiz
alembic upgrade head

# 8. Git'ga commit qilamiz
git add migrations/versions/ app/models.py
git commit -m "Kitob jadvaliga tavsif ustuni qo'shish migratsiyasi"
```

## Keng tarqalgan xatolar

**Xato 1:** yangi model fayl yaratib, uni `migrations/env.py`da import qilishni unutish, natijada Alembic uni "ko'rmasligi".
❌ Agar yangi model (masalan, `Buyurtma`) `env.py`da import qilinmasa, `--autogenerate` uni umuman aniqlamaydi, yoki undan ham yomoni — mavjud, lekin import qilinmagan jadvalni **o'chirish** migratsiyasini generatsiya qilib qo'yishi mumkin.
✅ To'g'ri: har safar yangi model klass yaratilganda, uni darhol `migrations/env.py` faylidagi import ro'yxatiga qo'shishni odat qiling.

**Xato 2:** `--autogenerate` natijasini, ko'rib chiqmasdan, ko'r-ko'rona `alembic upgrade head` bilan qo'llash.
❌ Ayniqsa ustun nomini o'zgartirish yoki murakkab o'zgarishlarda, Alembic ba'zan noto'g'ri (masalan, ma'lumotni yo'qotuvchi "drop + create") migratsiya generatsiya qilishi mumkin.
✅ To'g'ri: har doim, `alembic upgrade head`dan oldin, yangi generatsiya qilingan faylni ochib, `upgrade()`/`downgrade()` funksiyalarini diqqat bilan o'qib chiqing — bu, Git darsligining 4.2-darsida ko'rilgan "PR'ni merge qilishdan oldin o'z-o'zini review qilish" tamoyilining, migratsiyalar uchun tabiiy qo'llanilishi.

**Xato 3:** production ma'lumotlar bazasida, sinov qilinmagan migratsiyani to'g'ridan-to'g'ri qo'llash.
❌ Agar migratsiya xato bo'lsa (masalan, mavjud ma'lumot bilan mos kelmaydigan `NOT NULL` cheklov qo'shsa), bu — production'da ma'lumotlar yo'qolishi yoki xizmat to'xtab qolishiga olib kelishi mumkin.
✅ To'g'ri: har qanday migratsiyani, avval **development yoki staging muhitida** (production nusxasiga yaqin test ma'lumotlari bilan) sinab ko'ring, va faqat shundan keyin production'ga qo'llang — bu, Git va GitHub darsligining 4.1-darsida ko'rilgan GitHub Flow (`main` — doim tayyor holatda) tamoyiliga mos.

## Mashq/topshiriq

**(Oson)** Alembic'ni yangi FastAPI loyihasida sozlang (`alembic init migrations`), `alembic.ini` faylida ma'lumotlar bazasi manzilini to'g'irlang.

**(O'rtacha)** `Talaba` modeli uchun birinchi migratsiyani (`--autogenerate`) generatsiya qiling, uni `alembic upgrade head` orqali qo'llang, va Docker'dagi PostgreSQL'da `\dt` buyrug'i orqali jadval yaratilganini tasdiqlang.

**(Qiyin)** `Talaba` modeliga yangi `email: str | None = None` maydonini qo'shing, migratsiya generatsiya qiling, uni qo'llashdan oldin fayl mazmunini o'qib chiqing va tushuntiring. Keyin, `alembic downgrade -1` orqali uni bekor qiling va `\d talaba` (PostgreSQL'da jadval strukturasini ko'rish) orqali, `email` ustuni haqiqatan olib tashlanganini tasdiqlang.

<details>
<summary>Javoblarni ko'rish</summary>

1. `uv add alembic && alembic init migrations`, so'ng `alembic.ini`da `sqlalchemy.url` qatorini haqiqiy PostgreSQL manziliga o'zgartirish (yoki `env.py` orqali `.env`dan o'qish).
2. `alembic revision --autogenerate -m "Talaba jadvali"`, `alembic upgrade head`, `docker exec -it <konteyner-nomi> psql -U <foydalanuvchi> -d <baza> -c "\dt"` — `talaba` jadvali ro'yxatda ko'rinishi kerak.
3. Model faylga `email: str | None = None` qo'shiladi, `alembic revision --autogenerate -m "Talabaga email qo'shish"` — generatsiya qilingan faylda `upgrade()` ichida `op.add_column('talaba', sa.Column('email', sa.String(), nullable=True))`, `downgrade()` ichida `op.drop_column('talaba', 'email')` ko'rinishi kutiladi; `alembic upgrade head` bilan qo'llanadi, so'ng `alembic downgrade -1` bilan bekor qilinadi, `\d talaba` — `email` ustuni endi jadval strukturasida yo'qligini ko'rsatadi.

</details>

## Qisqacha xulosa

Alembic — SQLModel/SQLAlchemy loyihalarida, ma'lumotlar bazasi sxemasidagi o'zgarishlarni (yangi ustun, jadval, bog'lanish) xavfsiz, bosqichma-bosqich va **qaytariladigan** tarzda boshqarish uchun standart vosita; `alembic revision --autogenerate` — modellar va bazaning joriy holati orasidagi farqni avtomatik aniqlab, `upgrade()`/`downgrade()` funksiyalariga ega migratsiya fayl yaratadi, `alembic upgrade head` esa uni haqiqatan qo'llaydi. Har bir avtomatik generatsiya qilingan migratsiyani qo'llashdan oldin qo'lda tekshirish, va migratsiya fayllarini har doim Git'da kuzatib borish — real loyihalarda ma'lumotlar bazasi evolyutsiyasini xavfsiz boshqarishning asosiy qoidalari hisoblanadi. Keyingi darsda, ma'lumotlar bazasi bilan **asinxron** (`async`/`await`) ishlashni, FastAPI'ning to'liq asinxron tabiatidan foydalangan holda, o'rganamiz.
