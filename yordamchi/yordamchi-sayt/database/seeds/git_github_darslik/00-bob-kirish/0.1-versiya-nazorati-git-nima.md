# Versiya nazorati nima, Git tarixi va nega kerak

## Bu darsda nimalarni o'rganasiz

- Versiya nazorati tizimi (VCS) nima ekanini va u qanday muammoni hal qilishini tushuntira olasiz
- Git'ning boshqa versiya nazorati tizimlaridan farqini (taqsimlangan tabiati) bilasiz
- Git, GitHub va Git'ning boshqa "uy-joy" xizmatlari (GitLab, Bitbucket) orasidagi farqni tushunasiz
- Git'ning asosiy ish tsiklini (working directory → staging → repository) tasavvur qila olasiz

## Nazariy qism

### Muammo — kod o'zgarishlarini qo'lda kuzatish imkonsiz

Har qanday dasturchi loyiha ustida ishlaganda, ko'p muammolarga duch keladi: "kecha ishlagan kod bugun nega ishlamayapti?", "bu funksiyani kim va qachon o'zgartirgan?", "eski, ishlagan versiyaga qanday qaytish mumkin?", "ikki dasturchi bitta faylni bir vaqtda o'zgartirsa nima bo'ladi?". Ba'zi boshlovchilar bu muammolarni `loyiha_v1.py`, `loyiha_v2_yakuniy.py`, `loyiha_v2_yakuniy_HAQIQIY.py` kabi fayl nomlari orqali "hal qilishga" urinishadi — bu esa tezda boshqarib bo'lmas tartibsizlikka aylanadi.

**Versiya nazorati tizimi** (Version Control System, VCS) — bu muammoni tubdan hal qiladi: u faylning **har bir o'zgarishini** vaqt bilan birga saqlaydi, kim, qachon, nima uchun o'zgartirganini yozib boradi, va istalgan vaqtda istalgan oldingi holatga qaytish imkonini beradi.

### Git — taqsimlangan versiya nazorati tizimi

**Git** — Linux yadrosi yaratuvchisi Linus Torvalds tomonidan 2005-yilda yaratilgan, hozirda dunyoda eng keng tarqalgan versiya nazorati tizimi. Git'ning eng muhim xususiyati — u **taqsimlangan** (distributed): har bir dasturchining kompyuterida loyihaning **to'liq tarixi** (barcha commit'lar, barcha branch'lar) saqlanadi, markaziy serverga bog'liq bo'lmasdan ham ishlash mumkin.

```
MARKAZIY VCS (masalan, eski SVN):        TAQSIMLANGAN VCS (Git):

     [Markaziy server]                    [Server: to'liq tarix]
       /    |    \                              |
      /     |     \                    ┌────────┼────────┐
[Dasturchi][Dast.][Dast.]        [Dasturchi 1:  [Dasturchi 2:  [Dasturchi 3:
 (faqat      (faqat  (faqat       TO'LIQ tarix]  TO'LIQ tarix]  TO'LIQ tarix]
 joriy       joriy   joriy
 versiya)    versiya) versiya)
```

Bu farq amaliy jihatdan katta ahamiyatga ega: agar internet aloqasi bo'lmasa ham, Git bilan ishlash (commit qilish, tarixni ko'rish, branch yaratish) **to'liq davom etishi** mumkin — faqat boshqalar bilan **almashish** (sinxronlash) uchun tarmoq kerak bo'ladi.

### Git vs GitHub — eng ko'p uchraydigan chalkashlik

Boshlovchilar ko'pincha Git va GitHub'ni bir xil narsa deb o'ylashadi — bu noto'g'ri:

| | Git | GitHub |
|---|---|---|
| Nima u | Versiya nazorati **dasturi** (kompyuteringizga o'rnatiladi) | Git repozitoriyalarini internetda saqlash va ular ustida hamkorlik qilish uchun **veb-xizmat** |
| Kim yaratgan | Linus Torvalds (2005) | Alohida kompaniya (hozir Microsoft'ga tegishli) |
| Internetsiz ishlaydimi | Ha, to'liq | Yo'q — bu onlayn xizmat |
| Alternativalari bormi | Yo'q (Git — standart) | Ha — GitLab, Bitbucket, Codeberg va boshqalar |

Metafora: **Git** — bu "yozish texnologiyasi" (masalan, qalam va qog'oz), **GitHub** — bu shu yordamda yozilgan hujjatlarni saqlaydigan va boshqalar bilan ulashadigan "kutubxona/bulut xizmati". Git'siz GitHub'ni ishlatib bo'lmaydi, lekin Git'ni GitHub'siz ham to'liq, mustaqil ishlatish mumkin (masalan, faqat shaxsiy kompyuteringizda).

### Git'ning uchta asosiy hududi (Three Trees)

Git bilan ishlashni tushunish uchun eng muhim tushuncha — fayllar Git nazoratida uchta "hudud" orasida harakatlanadi:

```
┌──────────────────┐   git add    ┌──────────────────┐   git commit   ┌──────────────────┐
│  Working Directory │ ──────────► │   Staging Area      │ ─────────────► │   Repository (tarix) │
│  (ishchi papka)      │             │   (tayyorlov maydoni) │                │   (.git papkasi)       │
└──────────────────┘              └──────────────────┘                └──────────────────┘
   Fayllarni tahrirlaysiz          "Keyingi commit'ga             Doimiy saqlanadigan,
   (oddiy matn muharririda)         nima kirishini tanlaysiz"      o'zgarmas tarix
```

| Hudud | Tavsifi |
|---|---|
| **Working Directory** | Kompyuteringizdagi oddiy fayllar — ularni matn muharririda tahrirlaysiz, Git ularni "kuzatib" turadi, lekin hali hech narsa saqlanmagan |
| **Staging Area** (yoki "index") | "Keyingi commit'ga qaysi o'zgarishlar kirishi kerak" degan **tanlov ro'yxati** — `git add` orqali fayllar shu yerga "qo'yiladi" |
| **Repository** | `.git` papkasida saqlanadigan, **doimiy va o'zgarmas** tarix — `git commit` orqali staging area'dagi o'zgarishlar shu yerga "yozib qo'yiladi" |

Bu uch bosqichli tizim — nega Git boshqa oddiyroq vositalardan (masalan, fayllarni oddiy nusxalash) kuchliroq ekanini tushuntiradi: siz **aniq tanlab** (staging orqali), qaysi o'zgarishlar bitta "commit" (tarixiy nuqta) sifatida saqlanishini nazorat qila olasiz.

### Nega Git dasturchilar uchun majburiy ko'nikma

1. **Xavfsizlik** — istalgan noto'g'ri o'zgarishni bekor qilib, oldingi ishlaydigan holatga qaytish mumkin.
2. **Hamkorlik** — bir nechta dasturchi bitta loyiha ustida, bir-birining ishini buzmasdan parallel ishlashi mumkin (2-bobda "branch" tushunchasi orqali).
3. **Tarix va hisobdorlik** — har bir o'zgarish kim, qachon, nima uchun qilinganini saqlaydi (`git log` orqali).
4. **Ish beruvchilar talabi** — deyarli barcha professional dasturlash lavozimlari Git bilan ishlay olishni talab qiladi; GitHub profili ko'pincha portfolio vazifasini ham bajaradi.
5. **Zamonaviy ish jarayonlari (CI/CD)** — sizning Docker darsligingizdagi 6.3-darsda ko'rganingizdek, GitHub Actions kabi avtomatlashtirish vositalari to'g'ridan-to'g'ri Git commit'lari orqali ishga tushadi.

## Amaliy misol

Git bilan ishlashning konseptual ketma-ketligi (hali buyruqlarsiz, keyingi darsda amaliy qilamiz):

```
1. Loyiha papkasini Git nazoratiga olish (bir marta)
   └── "Bu papkani endi Git kuzatib borsin" deb belgilash

2. Fayl yaratish yoki o'zgartirish (Working Directory)
   └── main.py faylida yangi funksiya yozasiz

3. O'zgarishni "tayyorlov maydoni"ga qo'shish (Staging)
   └── "Bu o'zgarishni keyingi saqlashga kiritaman" deb belgilash

4. O'zgarishni doimiy saqlash (Commit)
   └── "Foydalanuvchi autentifikatsiyasi qo'shildi" degan izoh bilan tarixga yozish

5. Kerak bo'lsa, GitHub'ga yuborish (Push)
   └── Lokal tarixni onlayn repozitoriyaga sinxronlash
```

Bu besh bosqich — butun Git ish tsiklining asosi bo'lib, keyingi darslarda har biri aniq buyruqlar bilan chuqur o'rganiladi.

## Keng tarqalgan xatolar

**Xato 1:** Git va GitHub'ni bir xil narsa deb tushunish.
❌ "Menda Git yo'q, faqat GitHub akkauntim bor" — bu noto'g'ri tushuncha, chunki GitHub'da loyiha yaratish uchun ham, uni kompyuteringizda ishlatish uchun ham **Git dasturi** kompyuteringizga o'rnatilgan bo'lishi kerak.
✅ To'g'ri: Git — mahalliy dastur (0.2-darsda o'rnatamiz), GitHub — bu Git repozitoriyalarini saqlaydigan onlayn xizmat; ular birga ishlaydi, lekin alohida-alohida tushunchalar.

**Xato 2:** fayllarni qo'lda nusxalab (`loyiha_v1`, `loyiha_v2`) "versiya nazorati" qilishga urinish.
❌ Bu usul — loyiha kattalashgach tezda boshqarib bo'lmas holga keladi, chunki qaysi fayl qaysi o'zgarishni o'z ichiga olganini eslab qolish, ikkita versiyani solishtirish yoki ularni birlashtirish deyarli imkonsiz.
✅ To'g'ri: Git — bu muammoni professional, kompaktroq (barcha "versiyalar" bitta `.git` papkasida, ixcham formatda saqlanadi) va qidiriladigan (`git log`, `git diff` orqali) tarzda hal qiladi.

**Xato 3:** Git'ni faqat "jamoada ishlaganda kerak" deb, yakka o'zi ishlaydigan loyihalarda ishlatmaslik.
❌ Yakka dasturchilar ko'pincha "menga Git kerak emas, men yolg'iz ishlayman" deb o'ylashadi.
✅ To'g'ri: Git — hatto yakka loyihalarda ham juda foydali (eski holatga qaytish, turli g'oyalarni branch orqali sinab ko'rish, xatolarni tarix orqali topish); bundan tashqari, GitHub'dagi ochiq profil — ish qidirishda muhim portfolio vositasi hisoblanadi.

## Mashq/topshiriq

**(Oson)** O'z so'zlaringiz bilan (3-4 gap) Git va GitHub orasidagi farqni, ularni kitob yozish va kutubxonaga metafora orqali (yoki o'zingiz tanlagan boshqa metafora bilan) tushuntirib bering.

**(O'rtacha)** Working Directory, Staging Area va Repository — uchta hududni jadval ko'rinishida yozing va har birida fayl "qanday holatda" bo'lishini (masalan, "hali saqlanmagan", "saqlashga tayyorlangan", "doimiy saqlangan") tavsiflab bering.

**(Qiyin)** Taqsimlangan (Git) va markaziy (masalan, eski SVN tizimi) versiya nazorati orasidagi farqni tushuntirib, nima uchun internet aloqasi vaqtincha uzilib qolgan holatda ham Git bilan ishlashni davom ettirish mumkinligini (lekin markaziy tizimda mumkin emasligini) asoslab bering.

## Qisqacha xulosa

Git — Linus Torvalds tomonidan yaratilgan, **taqsimlangan** versiya nazorati tizimi bo'lib, har bir dasturchining kompyuterida loyihaning to'liq tarixini saqlaydi va fayllarni uchta hudud (Working Directory → Staging Area → Repository) orqali boshqaradi; GitHub esa Git repozitoriyalarini internetda saqlash va hamkorlik qilish uchun **alohida, veb-asosli xizmat** bo'lib, Git'ning o'zi emas — bu farqni tushunish butun qolgan kursning (mahalliy Git buyruqlari va GitHub'ga bog'liq bo'lim'lar orasidagi chegara) asosini tashkil qiladi.
