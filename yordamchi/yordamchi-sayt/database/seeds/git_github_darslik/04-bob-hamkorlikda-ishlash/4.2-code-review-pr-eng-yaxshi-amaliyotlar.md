# Code review va Pull Request eng yaxshi amaliyotlari

## Bu darsda nimalarni o'rganasiz

- Code review nima uchun kerakligini va uning afzalliklarini tushunasiz
- Yaxshi PR yaratish qoidalarini o'rganasiz
- GitHub'da review qoldirish mexanizmini (Approve/Request changes/Comment) bilasiz
- Branch protection qoidalari orqali sifatni texnik jihatdan ta'minlashni o'rganasiz

## Nazariy qism

### Code review nima va nima uchun kerak

**Code review** — bir dasturchi tomonidan yozilgan kodni, boshqa dasturchi(lar) tomonidan, `main`ga qo'shilishidan **oldin** ko'rib chiqish jarayoni. Bu — Pull Request mexanizmining asosiy vazifalaridan biri.

Code review'ning afzalliklari:

| Afzallik | Tavsif |
|---|---|
| Xatolarni erta topish | Xato production'ga yetib borishidan oldin aniqlanadi |
| Bilim almashish | Jamoa a'zolari bir-birining kodidan o'rganadi, loyihaning turli qismlari bilan tanishadi |
| Kod sifatini saqlash | Nomlash, arxitektura, standartlarga rioya qilish tekshiriladi |
| "Bus factor"ni kamaytirish | Faqat bitta odam bilgan kod qismlari kamayadi |

### Yaxshi Pull Request qanday yaratiladi

**1. Kichik va aniq maqsadli PR'lar**

```
❌ "Turli tuzatishlar" (500 qator o'zgargan, 12 xil narsa)
✅ "Login formasidagi email validatsiya xatosini tuzatish" (15 qator, bitta maqsad)
```

Kichik PR'lar — tezroq review qilinadi, xatoni topish osonroq, va agar muammo chiqsa, uni orqaga qaytarish (`revert`) ham osonroq.

**2. Tushunarli sarlavha va tavsif**

Yaxshi PR tavsifi odatda quyidagilarni o'z ichiga oladi:
- **Nima** o'zgardi (qisqacha)
- **Nima uchun** bu o'zgarish kerak (muammo yoki vazifa)
- **Qanday** sinovdan o'tkazilgani (qo'lda tekshirildimi, avtomatik test qo'shildimi)
- Bog'liq Issue raqami (masalan, `Closes #42`)

**3. O'z-o'zini review qilish**

PR ochishdan oldin, o'zingiz `git diff` orqali barcha o'zgarishlarni ko'rib chiqing — bu, boshqa birovga vaqt sarflashdan oldin, oddiy xatolarni (debug uchun qoldirilgan `print()`, izohlar, ishlatilmayotgan kod) o'zingiz tutib olish imkonini beradi.

### GitHub'da review qoldirish

Reviewer, PR sahifasida **Files changed** bo'limida, har bir qatorga izoh qoldirishi mumkin. Review yakunida uch variantdan biri tanlanadi:

| Variant | Ma'nosi |
|---|---|
| **Approve** | O'zgarishlar ma'qullandi, merge qilish mumkin |
| **Request changes** | O'zgarish talab qilinadi, PR muallifi tuzatishi kerak (bu — merge tugmasini bloklashi mumkin, agar shunday sozlangan bo'lsa) |
| **Comment** | Shunchaki izoh/savol, rasmiy qaror emas |

### Yaxshi review izohi qanday bo'ladi

| Yomon izoh | Yaxshi izoh |
|---|---|
| "Bu noto'g'ri" | "Bu yerda `None` qiymat kelsa, funksiya xato beradi — `if x is None` tekshiruvini qo'shish tavsiya etiladi" |
| "Menga yoqmadi" | "Bu yondashuv ishlaydi, lekin `for` sikli o'rniga list comprehension ishlatish o'qilishini oshiradi, masalan: `[x*2 for x in ro'yxat]`" |

Yaxshi review — **tanqidiy emas, konstruktiv**: nima noto'g'ri ekanini emas, balki **nima uchun** va **qanday yaxshiroq qilish mumkinligini** tushuntiradi.

### Branch protection rules — sifatni texnik jihatdan ta'minlash

GitHub'da repository sozlamalarida (**Settings → Branches → Branch protection rules**), `main` branch uchun qoidalar o'rnatish mumkin:

| Qoida | Vazifasi |
|---|---|
| Require pull request before merging | To'g'ridan-to'g'ri `main`ga push qilishni taqiqlaydi |
| Require approvals | Kamida N kishi Approve qilmaguncha, merge qilib bo'lmaydi |
| Require status checks to pass | CI testlari (GitHub Actions) muvaffaqiyatli o'tmaguncha, merge bloklanadi |
| Require conversation resolution | Barcha review izohlari "hal qilingan" deb belgilanmaguncha, merge bloklanadi |

Bu qoidalar — jamoaning kelishilgan workflow'ini (oldingi darsda ko'rilgan) **texnik jihatdan majburiy** qiladi, ya'ni inson xatosiga (masalan, kimdir shoshilib to'g'ridan-to'g'ri `main`ga push qilib qo'yishi) yo'l qoldirmaydi.

### Reviewer sifatida — nimalarga e'tibor berish kerak

1. **To'g'rilik** — kod aslida vazifani bajaradimi?
2. **Chekka holatlar (edge cases)** — bo'sh ro'yxat, `None`, juda katta son kabi holatlar hisobga olinganmi?
3. **O'qilishi** — boshqa dasturchi (yoki 6 oydan keyin siz o'zingiz) bu kodni tushuna oladimi?
4. **Testlar** — yangi funksionallik uchun test qo'shilganmi (Python darsligining `pytest` darsi bilan bog'liq)?
5. **Xavfsizlik** — maxfiy ma'lumotlar (parollar, kalitlar) tasodifan qo'shilmaganmi?

## Amaliy misol

To'liq review jarayoni — PR muallifi va reviewer nuqtai nazaridan:

```bash
# PR MUALLIFI: PR ochishdan oldin o'z-o'zini tekshiradi
git diff main...feature/parol-validatsiya
# (barcha o'zgarishlarni diqqat bilan ko'rib chiqadi)

gh pr create \
  --title "Parol validatsiyasiga minimal uzunlik tekshiruvi qo'shish" \
  --body "## Nima o'zgardi
Parol kamida 8 belgidan iborat bo'lishi endi tekshiriladi.

## Nima uchun
Foydalanuvchilar juda qisqa (masalan, '123') parol qo'yishlari mumkin edi.

## Qanday sinovdan o'tkazildi
- Qo'lda: 3, 8, 12 belgili parollar bilan tekshirildi
- Yangi test qo'shildi: test_parol_validatsiya.py

Closes #57"
```

Reviewer tomonidan:

```
# GitHub veb-interfeysida, "Files changed" bo'limida:
# 23-qatorga izoh: "Bu yerda parol uzunligi 8 emas, balki 
#                   xavfsizlik standartlariga ko'ra 10 belgi tavsiya etiladi - 
#                   OWASP qo'llanmasiga muvofiq o'zgartirish mumkinmi?"
#
# So'ng: "Request changes" tanlanadi
```

Muallif tuzatib, qaytadan push qiladi (PR avtomatik yangilanadi, yangi commit qo'shiladi):

```bash
# Tuzatish kiritiladi
git add validatsiya.py
git commit -m "Parol minimal uzunligini 10 ga oshirish (review izohi asosida)"
git push
```

Reviewer qayta ko'rib, endi **Approve** qiladi, va (agar branch protection ruxsat bersa) **Squash and merge** bosiladi.

## Keng tarqalgan xatolar

**Xato 1:** review izohlarini shaxsiy tanqid sifatida qabul qilish (yoki, reviewer sifatida, shaxsga qaratilgan tarzda yozish).
❌ Bu — jamoada keraksiz ziddiyat va noqulaylikni keltirib chiqaradi, kelajakda odamlarning PR ochishdan cho'chishiga sabab bo'lishi mumkin.
✅ To'g'ri: review — **kodga**, shaxsga emas, qaratilgan bo'lishi kerak; izohlar har doim konstruktiv, aniq sabab bilan ("nima uchun" tushuntirilgan holda) yozilishi lozim.

**Xato 2:** PR'ni faqat yuzaki, "umumiy ko'rinishga" qarab, kodni chuqur o'qimasdan Approve qilish.
❌ Bu — code review'ning butun maqsadini yo'qqa chiqaradi, xatolar tekshirilmasdan `main`ga o'tib ketaveradi.
✅ To'g'ri: har bir o'zgargan faylni diqqat bilan o'qing, agar vaqt yetishmasa, reviewni keyinroqqa qoldiring — "tezroq Approve" qilishdan ko'ra, "sifatli, kechroq review" afzalroq.

**Xato 3:** branch protection qoidalarini sozlamasdan, faqat "og'zaki kelishuv"ga tayanish (masalan, "hamma to'g'ridan-to'g'ri `main`ga push qilmaslikka rozi").
❌ Inson xatosi — kimdir shoshilib, unutib yoki bilmasdan qoidani buzishi mumkin.
✅ To'g'ri: kelishilgan qoidalarni GitHub'ning **Branch protection rules** orqali texnik jihatdan majburiy qiling — bu inson xatosidan qat'i nazar, qoidaning buzilishini imkonsiz qiladi.

## Mashq/topshiriq

**(Oson)** O'zingiz yaratgan (yoki mashq uchun ochilgan) PR uchun, yuqorida ko'rsatilgan shablon asosida (Nima o'zgardi / Nima uchun / Qanday sinovdan o'tkazildi) to'liq tavsif yozing.

**(O'rtacha)** Ikkita xil kodni tasavvur qiling — biri to'liq ishlaydigan, lekin tushunarsiz nomlangan o'zgaruvchilar bilan; ikkinchisi — kichik xatoga ega, lekin toza va tushunarli kod. Har biriga qanday review izohi yozgan bo'lardingiz, ikkitasini yozing.

**(Qiyin)** GitHub repository sozlamalarida (yoki mashq uchun, tasavvuran) `main` branch uchun quyidagi branch protection qoidalarini qo'llang: kamida 1 ta Approve talab qilinsin, CI testlari o'tishi shart bo'lsin. ## Qisqacha xulosa

Code review — kodni `main`ga qo'shishdan oldin, boshqa dasturchi(lar) tomonidan tekshirish jarayoni bo'lib, xatolarni erta topish, bilim almashish va kod sifatini saqlashga xizmat qiladi; yaxshi PR — kichik, aniq maqsadli, va "nima/nima uchun/qanday sinovdan o'tkazilgani" tushuntirilgan tavsifga ega bo'lishi kerak. GitHub'da review — Approve/Request changes/Comment orqali rasmiylashtirilib, **Branch protection rules** yordamida (masalan, "kamida 1 Approve" yoki "CI testlari o'tishi shart") bu jarayon texnik jihatdan majburiy qilinishi mumkin — bu, jamoaviy ishlashda inson xatosidan mustaqil, ishonchli sifat nazoratini ta'minlaydi.
