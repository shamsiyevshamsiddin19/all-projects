# Tag'lar va GitHub Releases

## Bu darsda nimalarni o'rganasiz

- Git tag nima ekanini va uning branch'dan farqini tushunasiz
- Lightweight va annotated tag turlarini o'rganasiz
- Semantik versiyalash (Semantic Versioning) qoidalarini bilasiz
- GitHub Releases orqali rasmiy chiqarishlarni e'lon qilishni o'rganasiz

## Nazariy qism

### Tag nima

**Tag** — loyiha tarixidagi **muayyan bir commit'ga** doimiy, o'zgarmas belgi qo'yish usuli — odatda **rasmiy versiya chiqarilishini** (release) belgilash uchun ishlatiladi (masalan, `v1.0.0`).

### Tag va branch — muhim farq

| Xususiyat | Branch | Tag |
|---|---|---|
| Harakatlanadimi | Ha — yangi commit qilinganda avtomatik "oldinga siljiydi" | Yo'q — doimo bitta muayyan commit'ga qotib qoladi |
| Maqsadi | Faol ishlanayotgan yo'nalish | Tarixdagi muhim nuqtani "belgilash" (masalan, release) |
| Odatiy ishlatilishi | `main`, `feature/x` | `v1.0.0`, `v2.3.1` |

### Ikki xil tag turi

**1. Lightweight tag** — shunchaki commit'ga ishora qiluvchi oddiy belgi, qo'shimcha ma'lumotsiz:

```bash
git tag v1.0.0
```

**2. Annotated tag** — muallif, sana va izoh kabi qo'shimcha ma'lumotlarni o'z ichiga oladi (rasmiy release'lar uchun **tavsiya etiladi**):

```bash
git tag -a v1.0.0 -m "Birinchi barqaror versiya"
```

| Tur | Qачон ishlatiladi |
|---|---|
| Lightweight | Vaqtinchalik, shaxsiy belgilash uchun |
| Annotated | Rasmiy release'lar uchun (deyarli har doim shu tavsiya etiladi) |

### Asosiy tag buyruqlari

```bash
# Barcha tag'larni ko'rish
git tag

# Muayyan naqshga mos tag'larni qidirish
git tag -l "v1.*"

# Tag haqida to'liq ma'lumot (annotated tag uchun)
git show v1.0.0

# O'tmishdagi muayyan commit'ga tag qo'yish (joriy HEAD'ga emas)
git tag -a v0.9.0 a1b2c3d -m "Beta versiya"

# Tag'ni o'chirish (lokal)
git tag -d v1.0.0
```

### Tag'larni GitHub'ga yuklash

> 📌 **Muhim:** oddiy `git push` — tag'larni **avtomatik yubormaydi**. Ularni alohida push qilish kerak:

```bash
# Bitta tag'ni yuklash
git push origin v1.0.0

# Barcha tag'larni birdaniga yuklash
git push origin --tags
```

### Semantik versiyalash (Semantic Versioning / SemVer)

Ko'pchilik dasturiy loyihalar, versiya raqamlarini **semantik versiyalash** qoidasiga muvofiq nomlaydi: `MAJOR.MINOR.PATCH` (masalan, `2.4.1`):

| Qism | Qачон oshiriladi |
|---|---|
| **MAJOR** (birinchi raqam) | Orqaga mos kelmaydigan (breaking) o'zgarishlar kiritilganda |
| **MINOR** (ikkinchi raqam) | Yangi funksiya qo'shilganda, lekin eski funksionallik buzilmaganda |
| **PATCH** (uchinchi raqam) | Faqat xato tuzatilganda, yangi funksiya qo'shilmaganda |

Misollar: `1.0.0` → `2.0.0` (breaking change), `1.0.0` → `1.1.0` (yangi funksiya), `1.0.0` → `1.0.1` (xato tuzatildi).

### GitHub Releases — tag'ni rasmiy chiqarishga aylantirish

**GitHub Releases** — tag asosida, GitHub'da **rasmiy, ko'rinadigan release sahifasi** yaratish imkonini beradi. Bu sahifa quyidagilarni o'z ichiga olishi mumkin:

- Release nomi va tavsifi (odatda "nima o'zgargani" — changelog)
- Tag'ga bog'langan manba kodi (avtomatik `.zip`/`.tar.gz` sifatida)
- Qo'shimcha binary fayllar (masalan, tayyor dastur fayli, agar kerak bo'lsa)
- "Latest release" belgisi

Release yaratish — GitHub veb-interfeysida: **Releases → Draft a new release**, mavjud tag tanlanadi (yoki yangisi yaratiladi), tavsif yoziladi, **Publish release** bosiladi.

### GitHub CLI orqali Release yaratish

```bash
gh release create v1.0.0 --title "Versiya 1.0.0" --notes "Birinchi barqaror versiya - login va parol tiklash funksiyalari qo'shildi"

# Fayl biriktirib
gh release create v1.0.0 dist/dastur.tar.gz --title "v1.0.0"

# Barcha release'larni ko'rish
gh release list
```

### Avtomatik Changelog

Ko'p loyihalar, har bir release tavsifida, oxirgi release'dan buyon qilingan barcha commit'lar/PR'lar ro'yxatini avtomatik keltiradi. GitHub — "Generate release notes" tugmasi orqali, ochilgan/merge qilingan PR'lar asosida bu ro'yxatni **avtomatik yaratib berish** imkoniyatiga ega.

### CI/CD bilan bog'liqlik

Tag yaratish — ko'pincha GitHub Actions workflow'ini ishga tushiruvchi trigger sifatida ishlatiladi (Docker darsligining 6.3-darsida ko'rilgan `on: push` kabi). Masalan:

```yaml
on:
  push:
    tags:
      - 'v*'
```

Bu — `v` bilan boshlanuvchi har qanday tag push qilinganda (masalan, `v1.2.0`), avtomatik build va deploy jarayonini ishga tushiradi — bu, 6-bobda ko'riladigan real loyiha misolida chuqurroq qo'llaniladi.

## Amaliy misol

To'liq jarayon — versiyani tag qilish va GitHub Release sifatida e'lon qilish:

```bash
mkdir tag-mashqi && cd tag-mashqi && git init
echo "versiya 1.0" > dastur.py
git add dastur.py
git commit -m "Birinchi barqaror versiya"

# Annotated tag yaratamiz
git tag -a v1.0.0 -m "Birinchi barqaror chiqarilish - asosiy funksiyalar tayyor"

git tag
# v1.0.0

git show v1.0.0
# tag v1.0.0
# Tagger: Shamsiddin Shamsiyev <...>
# Date: ...
# Birinchi barqaror chiqarilish - asosiy funksiyalar tayyor
# commit a1b2c3d...

# Remote'ga yuklaymiz
git remote add origin git@github.com:shamsiddin/tag-mashqi.git
git push -u origin main
git push origin v1.0.0

# GitHub Release yaratamiz
gh release create v1.0.0 \
  --title "v1.0.0 - Birinchi barqaror versiya" \
  --notes "## Yangiliklar
- Asosiy funksiyalar tayyor
- Birinchi barqaror chiqarilish"

# Keyinroq, kichik xato tuzatilgach - PATCH versiya
echo "versiya 1.0.1 - xato tuzatildi" >> dastur.py
git add dastur.py
git commit -m "Kichik xatoni tuzatish"
git tag -a v1.0.1 -m "Xato tuzatildi"
git push origin v1.0.1
gh release create v1.0.1 --title "v1.0.1" --notes "Kichik xato tuzatildi"
```

## Keng tarqalgan xatolar

**Xato 1:** oddiy `git push` qilib, tag'larning GitHub'ga yuklanmaganidan hayron bo'lish.
❌ `git push` — standart holda faqat commit'larni yuboradi, tag'lar **alohida** yuborilishi kerak.
✅ To'g'ri: har doim tag yaratgandan so'ng, `git push origin <tag-nomi>` (yoki barchasi uchun `git push origin --tags`) alohida ishga tushiring.

**Xato 2:** versiya raqamlarini tartibsiz, semantik ma'nosiz belgilash (masalan, `yangi-versiya`, `final`, `final2`, `final-haqiqiy`).
❌ Bu — foydalanuvchilar va boshqa dasturchilar uchun, versiyalar orasidagi farq qanchalik jiddiy ekanini (kichik tuzatishmi yoki katta breaking change'mi) tushunishni imkonsiz qiladi.
✅ To'g'ri: Semantik Versiyalash (`MAJOR.MINOR.PATCH`) qoidasiga rioya qiling — bu, versiya raqamining o'zidan, o'zgarish qanchalik jiddiy ekanini bir qarashda tushunish imkonini beradi.

**Xato 3:** lightweight tag'dan, rasmiy release'lar uchun foydalanish (izoh, sana, muallif ma'lumotisiz).
❌ Bu — keyinchalik, "bu versiya aynan qачон va nima sababdan chiqarilgani" haqidagi muhim kontekstni yo'qotadi.
✅ To'g'ri: rasmiy release'lar uchun har doim **annotated tag** (`-a` bayrog'i bilan, izoh qo'shib) ishlating — bu, `git show` orqali to'liq tarixiy ma'lumotni saqlab qoladi.

## Mashq/topshiriq

**(Oson)** Loyihada `v0.1.0` nomli annotated tag yarating (`-a` va `-m` bilan), so'ng `git show v0.1.0` orqali uning ma'lumotlarini ko'ring.

**(O'rtacha)** Yaratilgan tag'ni GitHub'ga push qiling (`git push origin v0.1.0`), so'ng GitHub veb-interfeysida (yoki `gh release create` orqali) shu tag asosida Release yarating, tavsif yozing.

**(Qiyin)** Loyihangizda ketma-ket uchta o'zgarish qiling va ularni Semantik Versiyalash qoidasiga muvofiq nomlang: birinchisi — kichik xato tuzatish (PATCH), ikkinchisi — yangi, orqaga mos funksiya qo'shish (MINOR), uchinchisi — eski funksiyani butunlay olib tashlash yoki uning ishlash tartibini tubdan o'zgartirish (MAJOR). Har uchtasi uchun mos versiya raqamlarini yozib, sababini tushuntiring.

## Qisqacha xulosa

Git tag — loyiha tarixidagi muayyan commit'ga qo'yiladigan, branch'dan farqli o'laroq **o'zgarmas** belgi bo'lib, odatda rasmiy versiya chiqarishlarini (release) belgilash uchun ishlatiladi; annotated tag'lar (`-a -m`) rasmiy release'lar uchun tavsiya etiladi, chunki ular muallif, sana va izoh ma'lumotlarini saqlaydi. Tag'lar `git push origin --tags` orqali alohida yuklanadi, va Semantik Versiyalash (`MAJOR.MINOR.PATCH`) qoidasi — versiya raqamining o'zidan o'zgarish qanchalik jiddiy ekanini tushunish imkonini beradi. GitHub Releases — tag asosida, changelog va fayllar bilan boyitilgan rasmiy chiqarish sahifasini yaratadi, bu esa ko'pincha CI/CD (GitHub Actions) jarayonlarini ishga tushiruvchi trigger sifatida ham xizmat qiladi.
