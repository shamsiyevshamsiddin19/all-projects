# Docker xavfsizligi va eng yaxshi amaliyotlar

## Bu darsda nimalarni o'rganasiz

- Konteynerlarni `root` o'rniga oddiy foydalanuvchi bilan ishga tushirishni bilasiz
- Maxfiy ma'lumotlarni (`secrets`) xavfsiz boshqarishni tushunasiz
- Image'larni xavfsizlik zaifliklariga tekshirish (`docker scout`) usulini bilasiz
- Umumiy xavfsizlik cheklist'ini qo'llay olasiz

## Nazariy qism

### Muammo — standart holda konteynerlar `root` sifatida ishlaydi

Agar Dockerfile'da aniq ko'rsatilmasa, konteyner ichidagi jarayon standart holda **`root`** foydalanuvchisi nomidan ishlaydi. Bu — 0.1-darsda ko'rgan "konteyner host yadrosini ulashadi" tushunchasi bilan birga, xavfsizlik nuqtai nazaridan xatarli: agar konteyner ichidagi dastur biror zaiflik orqali "buzilsa" (kompromisga uchrasa), tajovuzkor konteyner ichida **root huquqlariga** ega bo'ladi — bu esa, ba'zi noto'g'ri sozlangan holatlarda, host tizimga ham ta'sir qilishi mumkin.

### Yechim — Dockerfile'da oddiy foydalanuvchi yaratish

```dockerfile
FROM python:3.13-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Yangi, imtiyozsiz foydalanuvchi yaratish
RUN useradd --create-home --shell /bin/bash mening_foydalanuvchim

# Fayllar egaligini yangi foydalanuvchiga o'tkazish
RUN chown -R mening_foydalanuvchim:mening_foydalanuvchim /app

# Keyingi barcha buyruqlar (va konteyner ishga tushganda) shu foydalanuvchi nomidan bajariladi
USER mening_foydalanuvchim

CMD ["python3", "main.py"]
```

`USER <foydalanuvchi>` — Dockerfile'dagi barcha keyingi buyruqlar va, eng muhimi, **konteyner ishga tushganda ishlaydigan jarayon** shu foydalanuvchi nomidan bajarilishini bildiradi. Bu — 4.1-darsdagi Python kursida ko'rgan "imtiyozlarni cheklash" (inkapsulyatsiya) tamoyilining Docker'dagi amaliy qo'llanilishi.

```bash
docker exec mening_konteyner whoami
# mening_foydalanuvchim   (root EMAS!)
```

### Rasmiy image'larda tayyor "non-root" foydalanuvchilar

Ko'p rasmiy image'lar (masalan, `postgres`, `nginx`) allaqachon o'zining ichki, imtiyozsiz foydalanuvchisiga ega va uni ishlatish tavsiya etiladi — bu haqda image'ning Docker Hub sahifasidagi hujjatlarni tekshirish kerak.

### Maxfiy ma'lumotlar (secrets) — `.env`dan yanada xavfsizroq usul

4.2-darsda `.env` fayl orqali parollarni boshqarishni ko'rgan edik — bu development uchun yetarli, lekin **production**da, ayniqsa ko'p serverli (Swarm, Kubernetes) muhitlarda, Docker'ning maxsus **secrets** mexanizmi tavsiya etiladi:

```yaml
services:
  db:
    image: postgres:16
    secrets:
      - db_password
    environment:
      - POSTGRES_PASSWORD_FILE=/run/secrets/db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

`POSTGRES_PASSWORD_FILE` (oddiy `POSTGRES_PASSWORD` emas) — parolni **muhit o'zgaruvchisi** sifatida emas, balki **fayl** sifatida o'qishni bildiradi. Bu muhim farq: muhit o'zgaruvchilari ba'zan `docker inspect` yoki xato loglarida tasodifan ko'rinib qolishi mumkin, fayl sifatida saqlangan maxfiy ma'lumot esa bunday "sizib chiqish" xavfidan ancha himoyalangan.

### `docker scout` — image'ni zaifliklarga tekshirish

Zamonaviy Docker (2023-yildan buyon) o'rnatilgan `docker scout` vositasini taqdim etadi — bu image ichidagi ma'lum xavfsizlik zaifliklarini (CVE — Common Vulnerabilities and Exposures) tekshiradi:

```bash
docker scout cves python:3.13-slim
```

Natija — image ichidagi paketlarda topilgan ma'lum zaifliklar ro'yxati, ularning jiddiylik darajasi (Critical, High, Medium, Low) bilan birga. Bu — ayniqsa production'ga chiqarishdan oldin, image'ning "toza" ekanini tekshirish uchun foydali qadam.

```bash
docker scout quickview python:3.13-slim    # qisqa, umumiy hisobot
docker scout recommendations python:3.13-slim   # xavfsizroq alternativalar bo'yicha tavsiyalar
```

### Rasmiy va yangilangan bazaviy image'larni tanlash

Xavfsizlikning eng oddiy, lekin eng samarali qoidasi:

1. **Har doim rasmiy image'larni** ishlating (1.2-darsda ko'rganimizdek).
2. **`slim` yoki `alpine`** versiyalarni tanlang — kamroq o'rnatilgan paket, kamroq potentsial zaiflik.
3. Image'larni **muntazam yangilab turing** — `docker pull python:3.13-slim` vaqti-vaqti bilan qayta bajarilsa, xavfsizlik yamoqlari (patches) bilan yangilangan versiyani oladi.
4. **Aniq versiya** (1.2-darsda ko'rgan `latest`dan saqlanish qoidasi) — bu nafaqat barqarorlik, balki qaysi versiyada qanday zaiflik borligini **aniq bilish** imkonini beradi.

### `.dockerignore` — xavfsizlik nuqtai nazaridan (2.1-darsning davomi)

2.1-darsda `.dockerignore`ni "keraksiz fayllarni chetlab o'tish" sifatida ko'rgan edik — bu, aslida, birinchi navbatda **xavfsizlik** vositasi:

```
.git/
.env
*.pem
*.key
__pycache__/
venv/
```

`.pem`, `.key` (shifrlash kalitlari), `.env` (parollar) — bularning **hech biri** image ichiga tushmasligi kerak, chunki image (agar Docker Hub'ga yuklansa yoki boshqa birov bilan ulashilsa) — bu fayllar bilan birga **butunlay oshkor** bo'lib qoladi.

### Umumiy Docker xavfsizlik cheklisti

| Band | Tavsif |
|---|---|
| ☐ Root'siz foydalanuvchi | `USER` direktivasi bilan imtiyozsiz foydalanuvchi ishlatilganmi |
| ☐ Aniq versiya | `latest` emas, aniq tag (`python:3.13-slim`) ishlatilganmi |
| ☐ Rasmiy image | Docker Hub'ning rasmiy (Official) image'lari ishlatilganmi |
| ☐ `.dockerignore` | Maxfiy fayllar (`.env`, `.git/`) chetlab o'tilganmi |
| ☐ Maxfiy ma'lumotlar | Parollar kodga "qattiq yozilmagan" (hardcoded), `.env`/`secrets` orqali uzatilganmi |
| ☐ Minimal port ochish | Faqat kerakli portlar `-p`/`ports:` bilan tashqariga ochilganmi (5.3-darsdagi `expose` tamoyili) |
| ☐ Zaifliklarni tekshirish | `docker scout` (yoki shunga o'xshash vosita) bilan muntazam tekshirilganmi |
| ☐ Muntazam yangilash | Bazaviy image'lar vaqti-vaqti bilan yangilanadimi |

## Amaliy misol

Xavfsiz Django Dockerfile — barcha yuqoridagi tamoyillar birlashtirilgan:

```dockerfile
FROM python:3.13-slim

WORKDIR /app

# Faqat runtime uchun zarur paket, dev vositalar YO'Q (2.3-darsdagi multi-stage tamoyili bilan birga ishlatilishi mumkin)
RUN apt-get update && \
    apt-get install -y --no-install-recommends libpq5 && \
    rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Imtiyozsiz foydalanuvchi yaratish va fayllar egaligini o'tkazish
RUN useradd --create-home --shell /bin/bash django_user && \
    chown -R django_user:django_user /app

USER django_user

EXPOSE 8000

CMD ["gunicorn", "--bind", "0.0.0.0:8000", "loyiha.wsgi:application"]
```

Tekshirish:

```bash
docker build -t xavfsiz-django .
docker scout cves xavfsiz-django

docker run -d --name test_konteyner xavfsiz-django
docker exec test_konteyner whoami
# django_user   (root EMAS — muvaffaqiyatli!)
```

## Keng tarqalgan xatolar

**Xato 1:** `USER`ni `COPY`/`RUN`dan **oldin** yozib, fayllar egaligi muammosiga duch kelish.
❌ 
```dockerfile
USER mening_foydalanuvchim
COPY . .    # bu fayllar HALI ROOT egaligida nusxalanadi, keyin foydalanuvchi ularga YOZOLMAYDI
```
✅ To'g'ri: avval barcha fayl operatsiyalarini (`COPY`, `RUN`) bajaring, `chown` bilan egalikni o'zgartiring, va **eng oxirida** `USER`ni yozing (yuqoridagi amaliy misolda ko'rganimizdek).

**Xato 2:** parollarni Dockerfile ichiga to'g'ridan-to'g'ri yozish.
❌ `ENV POSTGRES_PASSWORD=maxfiy123` — bu qiymat image tarixida (`docker history`) va, agar image boshqa birov bilan ulashilsa, **hammaga ko'rinadi**.
✅ To'g'ri: parollarni har doim `.env`, `env_file`, yoki `secrets` orqali, **ishga tushirish vaqtida** (runtime) uzating, hech qachon Dockerfile ichiga yozmang.

**Xato 3:** "kichik loyiha, xavfsizlik unchalik muhim emas" deb, barcha xavfsizlik amaliyotlarini e'tiborsiz qoldirish.
❌ Shaxsiy yoki kichik loyihalarda "hozircha `root` bilan ishlayveradi" deb, `USER` direktivasini butunlay o'tkazib yuborish — bu odat katta, jiddiy loyihalarga ham "ko'chib o'tishi" mumkin.
✅ To'g'ri: xavfsizlik amaliyotlarini (root'siz foydalanuvchi, `.dockerignore`, aniq versiyalar) **boshidanoq**, hatto eng kichik loyihalarda ham odat qilib olish — bu keyinchalik katta loyihalarda tabiiy ravishda davom etadi.

## Mashq/topshiriq

**(Oson)** 2.1-darsdagi `salomlashuv-app` Dockerfile'iga `USER` direktivasi qo'shing (imtiyozsiz foydalanuvchi bilan), qayta quring va `docker exec ... whoami` orqali `root` emasligini tasdiqlang.

**(O'rtacha)** `docker scout cves python:3.13` va `docker scout cves python:3.13-slim` buyruqlarini ishga tushirib, ikkalasidagi topilgan zaifliklar sonini solishtiring va nega `slim` versiyada odatda kamroq zaiflik topilishini tushuntirib bering.

**(Qiyin)** 5.1-darsdagi Django Dockerfile'ini to'liq xavfsizlik cheklisti bo'yicha qayta ko'rib chiqing: `USER` qo'shing, `.dockerignore`ni to'ldiring (`.env`, `.git/`, `*.pyc`), va `.env`dagi barcha maxfiy qiymatlarni (`SECRET_KEY`, parollar) tekshirib, ular Dockerfile ichida emas, faqat `.env`/`env_file` orqali uzatilayotganini tasdiqlang.

## Qisqacha xulosa

Docker xavfsizligi — konteynerlarni `root` o'rniga imtiyozsiz foydalanuvchi (`USER` direktivasi) bilan ishga tushirish, maxfiy ma'lumotlarni Dockerfile ichiga emas, `.env`/`secrets` orqali runtime'da uzatish, `docker scout` orqali image'larni zaifliklarga muntazam tekshirish, va rasmiy, yengil (`slim`/`alpine`), aniq versiyali bazaviy image'larni tanlashdan iborat; bu amaliyotlar — hatto kichik, shaxsiy loyihalarda ham boshidanoq odat qilib olinishi kerak bo'lgan, keyinchalik katta production tizimlarida hayotiy ahamiyatga ega bo'ladigan asosiy xavfsizlik tamoyillaridir.
