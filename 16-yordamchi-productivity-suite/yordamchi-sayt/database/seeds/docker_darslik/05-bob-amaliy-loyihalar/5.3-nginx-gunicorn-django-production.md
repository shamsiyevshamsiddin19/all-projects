# Nginx + Gunicorn + Django production setup

## Bu darsda nimalarni o'rganasiz

- Nginx va Gunicorn'ning production'da qanday rol taqsimlab ishlashini tushuntira olasiz
- Nginx'ni Docker konteynerida Django'ning "old eshigi" (reverse proxy) sifatida sozlay olasiz
- Statik va media fayllarni Nginx orqali to'g'ridan-to'g'ri xizmat qilishni tashkil qila olasiz
- To'liq, uch konteynerli (Nginx + Gunicorn + PostgreSQL) production tizimini qura olasiz

## Nazariy qism

### Nega Django o'zi yetarli emas — Nginx va Gunicorn'ning roli

Django'ning o'zi (`runserver`) — faqat **development** uchun mo'ljallangan, bir vaqtning o'zida faqat bitta so'rovni qayta ishlaydigan sodda server. Production'da ikkita qo'shimcha qatlam kerak:

| Komponent | Vazifasi |
|---|---|
| **Gunicorn** | Django'ni **bir nechta worker jarayoni** orqali ishga tushiruvchi, ko'p so'rovlarni parallel qayta ishlay oladigan WSGI server |
| **Nginx** | Gunicorn oldida turuvchi **reverse proxy** — statik fayllarni to'g'ridan-to'g'ri xizmat qiladi, SSL/HTTPS'ni boshqaradi, so'rovlarni Gunicorn'ga yo'naltiradi |

### To'liq so'rov oqimi (request flow)

```
Foydalanuvchi brauzeri
        │
        ▼
  Nginx (80/443-port) ──── statik fayl so'rovi? ──── to'g'ridan-to'g'ri javob (tez!)
        │
        │ dinamik so'rov (masalan, /admin/, /api/)
        ▼
  Gunicorn (8000-port, ICHKI, tashqariga OCHIQ EMAS)
        │
        ▼
     Django
        │
        ▼
   PostgreSQL
```

Nginx — **statik fayllarni** (CSS, JS, rasmlar) to'g'ridan-to'g'ri diskdan xizmat qiladi (bu Gunicorn/Django orqali o'tishdan ancha tezroq), **dinamik** so'rovlarni (ma'lumotlar bazasi bilan ishlaydigan sahifalar) esa Gunicorn'ga "uzatadi" (proxy qiladi).

### Nginx konfiguratsiyasi — `nginx.conf`

```nginx
upstream django_server {
    server veb:8000;    # "veb" — Compose xizmat nomi (3.2-darsdagi networking tushunchasi)
}

server {
    listen 80;

    location /static/ {
        alias /app/staticfiles/;    # statik fayllarni TO'G'RIDAN-TO'G'RI xizmat qiladi
    }

    location /media/ {
        alias /app/media/;           # foydalanuvchi yuklagan fayllar
    }

    location / {
        proxy_pass http://django_server;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

| Direktiva | Ma'nosi |
|---|---|
| `upstream django_server` | Gunicorn qayerda ishlayotganini (Compose xizmat nomi orqali) belgilaydi |
| `location /static/ { alias ... }` | `/static/` bilan boshlangan so'rovlarni to'g'ridan-to'g'ri fayl tizimidan xizmat qiladi |
| `location / { proxy_pass ... }` | Qolgan barcha so'rovlarni Gunicorn'ga "uzatadi" |
| `proxy_set_header X-Forwarded-For` | Django'ga **haqiqiy** foydalanuvchi IP manzilini uzatadi (aks holda Django faqat Nginx'ning IP manzilini ko'radi) |

### Nginx'ni Docker'da ishga tushirish — maxsus image qurish

```dockerfile
# Dockerfile.nginx
FROM nginx:1.27-alpine

COPY nginx.conf /etc/nginx/conf.d/default.conf
```

Bu — 2.1-darsda ko'rgan minimal Dockerfile: rasmiy `nginx` image'i ustiga, faqat bitta o'zimizning konfiguratsiya faylimizni qo'shamiz.

### Statik fayllarni Nginx va Django orasida ulashish — umumiy volume

Muammo: Django (`collectstatic` orqali) statik fayllarni `veb` konteyneri ichida yig'adi, lekin ularni xizmat qilishi kerak bo'lgan **Nginx** — butunlay **boshqa** konteyner. Yechim — 3.1-darsda ko'rgan **umumiy (shared) volume**:

```yaml
services:
  veb:
    build: .
    volumes:
      - static_fayllar:/app/staticfiles    # veb YOZADI
      - media_fayllar:/app/media

  nginx:
    build:
      context: .
      dockerfile: Dockerfile.nginx
    volumes:
      - static_fayllar:/app/staticfiles:ro    # nginx O'QIYDI (read-only)
      - media_fayllar:/app/media:ro
    ports:
      - "80:80"
    depends_on:
      - veb

volumes:
  static_fayllar:
  media_fayllar:
```

`static_fayllar` volume'i — ikkala konteyner tomonidan **ulashiladi**: `veb` unga statik fayllarni yozadi (`collectstatic` orqali), `nginx` esa ularni **faqat o'qiydi** (`:ro` — 3.1-darsda ko'rgan read-only mount) va foydalanuvchilarga xizmat qiladi.

### Gunicorn'ning tashqariga ochilmasligi — muhim xavfsizlik tamoyili

```yaml
services:
  veb:
    build: .
    command: gunicorn --bind 0.0.0.0:8000 loyiha.wsgi:application
    expose:
      - "8000"      # PORTS emas, EXPOSE — faqat boshqa konteynerlar uchun "ko'rinadi"
```

`expose:` (`ports:` emas!) — bu port faqat **Compose tarmog'i ichida** (boshqa konteynerlar uchun) ochiq bo'lishini, lekin **tashqi dunyoga** (host yoki internet) **chiqmasligini** bildiradi. Faqat `nginx` xizmatida `ports: ["80:80"]` bo'ladi — bu xavfsizlik nuqtai nazaridan muhim: foydalanuvchilar Gunicorn/Django'ga **bevosita** emas, faqat Nginx orqali murojaat qila oladi.

## Amaliy misol

To'liq, uch qatlamli production tizimi:

```
production-loyiha/
├── compose.yaml
├── compose.prod.yaml
├── Dockerfile
├── Dockerfile.nginx
├── nginx.conf
├── entrypoint.sh
├── .env
├── requirements.txt
└── loyiha/
```

`compose.yaml` (asosiy, umumiy qism):

```yaml
services:
  veb:
    build: .
    env_file:
      - .env
    volumes:
      - static_fayllar:/app/staticfiles
      - media_fayllar:/app/media
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16
    env_file:
      - .env
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER}"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pg_data:
  static_fayllar:
  media_fayllar:
```

`compose.prod.yaml` (production — Nginx qo'shiladi, Gunicorn ichkariga yashiriladi):

```yaml
services:
  veb:
    command: ./entrypoint.sh
    expose:
      - "8000"
    restart: unless-stopped

  nginx:
    build:
      context: .
      dockerfile: Dockerfile.nginx
    ports:
      - "80:80"
    volumes:
      - static_fayllar:/app/staticfiles:ro
      - media_fayllar:/app/media:ro
    depends_on:
      - veb
    restart: unless-stopped
```

Ishga tushirish:

```bash
docker compose -f compose.yaml -f compose.prod.yaml up --build -d

docker compose -f compose.yaml -f compose.prod.yaml ps
# veb-1     Up (healthy)     <- port TASHQARIGA ochiq emas
# nginx-1   Up                <- 0.0.0.0:80->80/tcp — bu YAGONA tashqi eshik
# db-1      Up (healthy)

# Brauzerda: http://localhost/ — Nginx orqali Django sahifasi ko'rinadi
# Brauzerda: http://localhost/static/... — statik fayl to'g'ridan-to'g'ri Nginx'dan
```

Bu tizim — sizning Django darsligingizning 16-darsida ("Production: Docker, Gunicorn, Nginx") tasvirlangan arxitekturaning to'liq, ishlaydigan Docker Compose amalga oshirilishi hisoblanadi.

## Keng tarqalgan xatolar

**Xato 1:** Gunicorn portini `ports:` orqali tashqariga ochib qo'yish.
❌ `veb` xizmatida `ports: ["8000:8000"]` qoldirilsa, foydalanuvchilar Nginx'ni **chetlab o'tib**, to'g'ridan-to'g'ri Gunicorn'ga (masalan, `http://server:8000`) murojaat qilishlari mumkin — bu Nginx'ning xavfsizlik va statik fayl optimallashtirish afzalliklarini yo'qqa chiqaradi.
✅ To'g'ri: `veb` xizmatida faqat `expose: ["8000"]` ishlating, `ports:` faqat `nginx` xizmatida bo'lsin — bu foydalanuvchilarni **majburan** Nginx orqali o'tkazadi.

**Xato 2:** statik fayllar uchun volume'ni ulashishni unutish, natijada Nginx "404 Not Found" berishi.
❌ `nginx` xizmatida `static_fayllar` volume'i ulanmasa, `veb` konteyneri ichida `collectstatic` orqali yig'ilgan fayllar Nginx uchun **ko'rinmaydi** — barcha CSS/JS so'rovlari 404 xatosi bilan tugaydi.
✅ To'g'ri: `static_fayllar` (va `media_fayllar`) volume'ini **ikkala** xizmatga ham (`veb` — yozish uchun, `nginx` — o'qish uchun, `:ro` bilan) ulang.

**Xato 3:** Nginx konfiguratsiyasida `proxy_set_header`larni unutish.
❌ `X-Forwarded-For` va boshqa sarlavhalarsiz `proxy_pass` — Django tomonidan barcha so'rovlar **Nginx**ning IP manzilidan kelayotgandek ko'rinadi, foydalanuvchining haqiqiy IP manzili yo'qoladi — bu loglash, xavfsizlik tekshiruvlari va ba'zi Django funksiyalari (masalan, geolokatsiya) uchun muammo tug'diradi.
✅ To'g'ri: yuqoridagi `nginx.conf` namunasida ko'rsatilgan barcha `proxy_set_header` qatorlarini har doim qo'shing.

## Mashq/topshiriq

**(Oson)** Oddiy `nginx.conf` yozing — faqat `/` yo'lini `veb:8000`ga proxy qiluvchi, statik fayllarsiz — va uni `Dockerfile.nginx` orqali qurib, `compose.yaml`ga qo'shing.

**(O'rtacha)** Yuqoridagi to'liq misolni (statik fayllar bilan) o'zingiz qurib, `docker compose -f compose.yaml -f compose.prod.yaml up --build -d` orqali ishga tushiring, so'ng brauzerda Django admin panelining CSS stillari to'g'ri yuklanganini (Nginx orqali xizmat qilinayotganini) tasdiqlang.

**(Qiyin)** `veb` xizmatida ataylab `ports: ["8000:8000"]`ni **qoldirib** (xato holatini simulyatsiya qilib), brauzerda ham `http://localhost` (Nginx orqali), ham `http://localhost:8000` (to'g'ridan-to'g'ri Gunicorn) manzillariga kirib ko'ring — ikkalasi ham ishlashini kuzatib, bu nega xavfsizlik nuqtai nazaridan muammo ekanini tushuntirib bering, so'ng `ports:`ni `expose:`ga almashtirib muammoni tuzating.

## Qisqacha xulosa

Production Django tizimida Gunicorn (ko'p worker bilan Django'ni ishga tushiruvchi WSGI server) va Nginx (statik fayllarni to'g'ridan-to'g'ri xizmat qiluvchi, dinamik so'rovlarni Gunicorn'ga yo'naltiruvchi reverse proxy) birgalikda ishlaydi — bu ikkala qatlam Docker Compose'da alohida konteynerlar sifatida, statik/media fayllar uchun **umumiy volume** va Gunicorn portini faqat `expose:` (hech qachon `ports:` emas) orqali ichki tarmoqqa ochish orqali tashkil qilinadi; bu arxitektura — foydalanuvchilarni majburan xavfsiz, optimallashtirilgan Nginx qatlamidan o'tkazadi va sizning Django darsligingizning production bobini to'liq, amaliy Docker tizimiga aylantiradi.
