# SQLModel asoslari va PostgreSQL bilan ulanish

## Bu darsda nimalarni o'rganasiz

- SQLModel nima ekanini va u SQLAlchemy hamda Pydantic bilan qanday bog'liqligini tushunasiz
- Ubuntu'da PostgreSQL'ni Docker orqali ishga tushirasiz
- SQLModel jadval modellarini yaratishni o'rganasiz
- Ma'lumotlar bazasiga ulanish (engine, session) mexanizmini tushunasiz

## Nazariy qism

### SQLModel nima

**SQLModel** — FastAPI'ning muallifi (Sebastián Ramírez) tomonidan yaratilgan kutubxona bo'lib, **SQLAlchemy** (Python'dagi eng mashhur ORM) va **Pydantic**ni **bitta modelda birlashtiradi**. Bu — ayniqsa FastAPI bilan ishlashda katta qulaylik yaratadi: bitta klass, ham ma'lumotlar bazasi jadvalini, ham API'ning request/response modelini tavsiflaydi.

```
SQLModel = SQLAlchemy (ma'lumotlar bazasi bilan ishlash) + Pydantic (validatsiya)
```

> 📌 **Eslatma:** SQLModel — FastAPI'ning rasmiy hujjatlarida tavsiya etilgan, boshlang'ich va o'rta darajadagi loyihalar uchun juda mos yechim. Katta, murakkab loyihalarda, ba'zi jamoalar sof SQLAlchemy 2.0 uslubini afzal ko'rishi mumkin (bu — ilg'or mavzu, ushbu darslik doirasidan tashqarida), lekin SQLModel — FastAPI bilan ma'lumotlar bazasini o'rganishni boshlash uchun eng tabiiy yo'l hisoblanadi.

### PostgreSQL'ni Docker orqali ishga tushirish

Docker darsligida o'rganilganidek, PostgreSQL'ni to'g'ridan-to'g'ri Ubuntu'ga o'rnatish o'rniga, uni konteyner sifatida ishga tushirish — eng toza va qulay yondashuv:

```bash
docker run -d \
  --name fastapi-postgres \
  -e POSTGRES_USER=fastapi_user \
  -e POSTGRES_PASSWORD=xavfsiz_parol \
  -e POSTGRES_DB=fastapi_db \
  -p 5432:5432 \
  postgres:17
```

Yoki, Docker darsligining 4-bobida ko'rilgan `docker compose` uslubida:

```yaml
# compose.yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: fastapi_user
      POSTGRES_PASSWORD: xavfsiz_parol
      POSTGRES_DB: fastapi_db
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fastapi_user"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

```bash
docker compose up -d
```

### Kerakli kutubxonalarni o'rnatish

```bash
uv add sqlmodel psycopg2-binary
```

| Paket | Vazifasi |
|---|---|
| `sqlmodel` | ORM va model klasslar |
| `psycopg2-binary` | PostgreSQL uchun sinxron drayver (4.4-darsda asinxron `asyncpg`ni ko'ramiz) |

### SQLModel jadval modeli yaratish

```python
from sqlmodel import SQLModel, Field

class Kitob(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    nomi: str = Field(index=True, max_length=200)
    muallif: str
    yil: int
    mavjud: bool = Field(default=True)
```

| Qism | Vazifasi |
|---|---|
| `SQLModel` | Bazaviy klass (2.1-darsda ko'rilgan `BaseModel`ga o'xshash, lekin ORM imkoniyatlari bilan) |
| `table=True` | Bu klass, **haqiqiy ma'lumotlar bazasi jadvaliga** mos kelishini bildiradi |
| `Field(primary_key=True)` | Ushbu ustun — jadvalning asosiy kaliti (primary key) |
| `Field(index=True)` | Ushbu ustun uchun indeks yaratiladi (qidiruvni tezlashtiradi) |

> 📌 **`id: int \| None`ning ma'nosi:** yangi qator yaratilganda, `id` hali mavjud emas (ma'lumotlar bazasi uni avtomatik generatsiya qiladi), shuning uchun u `None` bo'lishi mumkin; qator saqlangandan so'ng esa, u haqiqiy butun songa ega bo'ladi.

### Ikki xil model — jadval va API uchun (naqsh)

1.3-darsda ko'rilgan "kirish va chiqish uchun alohida model" tamoyili, SQLModel bilan ham davom etadi — odatda **uchta** model yoziladi:

```python
from sqlmodel import SQLModel, Field

# Umumiy maydonlar - takrorlanishni oldini olish uchun
class KitobAsosi(SQLModel):
    nomi: str = Field(max_length=200)
    muallif: str
    yil: int

# Ma'lumotlar bazasi jadvali (table=True)
class Kitob(KitobAsosi, table=True):
    id: int | None = Field(default=None, primary_key=True)

# API'ga kiruvchi ma'lumot (yaratish uchun)
class KitobYaratish(KitobAsosi):
    pass

# API'dan chiquvchi ma'lumot (javob uchun)
class KitobJavob(KitobAsosi):
    id: int
```

Bu naqsh — jadval strukturasi va API interfeysini **mustaqil** rivojlantirish imkonini beradi (masalan, kelajakda jadvalga `yaratilgan_vaqt` kabi ichki maydon qo'shilsa, uni API javobida ko'rsatish yoki ko'rsatmaslikni alohida boshqarish mumkin).

### Engine — ma'lumotlar bazasiga ulanish

**Engine** — SQLAlchemy/SQLModel'ning ma'lumotlar bazasi bilan "aloqa liniyasi" bo'lib, ulanish parametrlarini (manzil, foydalanuvchi, parol) o'z ichiga oladi:

```python
from sqlmodel import create_engine

DATABASE_URL = "postgresql://fastapi_user:xavfsiz_parol@localhost:5432/fastapi_db"

engine = create_engine(DATABASE_URL, echo=True)
```

`echo=True` — rivojlantirish paytida, SQLModel tomonidan generatsiya qilingan har bir SQL so'rovini konsolga chop etadi (production'da odatda `False` qilinadi — 7-bobda ko'riladi).

### Maxfiy ma'lumotlarni `.env` orqali boshqarish

Git va GitHub darsligining 6.2-darsida ko'rilganidek, ma'lumotlar bazasi manzili (parol bilan) — hech qachon kodga to'g'ridan-to'g'ri yozilmasligi kerak:

```bash
uv add pydantic-settings
```

```python
# config.py
from pydantic_settings import BaseSettings

class Sozlamalar(BaseSettings):
    database_url: str
    model_config = {"env_file": ".env"}

sozlamalar = Sozlamalar()
```

```bash
# .env (gitignore qilingan)
DATABASE_URL=postgresql://fastapi_user:xavfsiz_parol@localhost:5432/fastapi_db
```

```python
# database.py
from sqlmodel import create_engine
from config import sozlamalar

engine = create_engine(sozlamalar.database_url)
```

### Jadvallarni yaratish

```python
from sqlmodel import SQLModel
from database import engine
import models  # barcha model klasslar shu yerda import qilinishi kerak

def jadvallarni_yaratish():
    SQLModel.metadata.create_all(engine)
```

> ⚠️ **Muhim eslatma:** `SQLModel.metadata.create_all(engine)` — faqat kichik loyihalar yoki dastlabki sozlash uchun mos. Haqiqiy loyihalarda, jadval o'zgarishlarini boshqarish uchun **Alembic** (4.3-darsda ko'riladi) ishlatiladi — u, jadval allaqachon mavjud bo'lganda ham, uni xavfsiz "migratsiya" qilish imkonini beradi.

### Session — ma'lumotlar bazasi bilan "suhbat"

**Session** — bitta so'rov davomida, ma'lumotlar bazasi bilan barcha operatsiyalarni (o'qish, yozish) olib boruvchi vaqtinchalik "aloqa". 3.2-darsda ko'rilgan Dependency Injection, bu yerda o'z tabiiy qo'llanilishini topadi:

```python
from sqlmodel import Session
from database import engine

def session_olish():
    with Session(engine) as session:
        yield session
```

## Amaliy misol

To'liq, boshidan oxirigacha ma'lumotlar bazasi sozlash:

```bash
# 1. PostgreSQL'ni Docker orqali ishga tushirish
docker run -d --name fastapi-db \
  -e POSTGRES_USER=fastapi_user \
  -e POSTGRES_PASSWORD=parol123 \
  -e POSTGRES_DB=kutubxona_db \
  -p 5432:5432 \
  postgres:17

# 2. Kerakli paketlarni o'rnatish
uv add sqlmodel psycopg2-binary pydantic-settings
```

```python
# app/models.py
from sqlmodel import SQLModel, Field

class KitobAsosi(SQLModel):
    nomi: str = Field(max_length=200, index=True)
    muallif: str
    yil: int

class Kitob(KitobAsosi, table=True):
    id: int | None = Field(default=None, primary_key=True)

class KitobYaratish(KitobAsosi):
    pass

class KitobJavob(KitobAsosi):
    id: int
```

```python
# app/database.py
from sqlmodel import create_engine, Session, SQLModel

DATABASE_URL = "postgresql://fastapi_user:parol123@localhost:5432/kutubxona_db"
engine = create_engine(DATABASE_URL, echo=True)

def jadvallarni_yaratish():
    SQLModel.metadata.create_all(engine)

def session_olish():
    with Session(engine) as session:
        yield session
```

```python
# app/main.py
from contextlib import asynccontextmanager
from fastapi import FastAPI
from app.database import jadvallarni_yaratish

@asynccontextmanager
async def lifespan(app: FastAPI):
    jadvallarni_yaratish()   # ilova ishga tushganda, jadvallar yaratiladi
    yield

app = FastAPI(lifespan=lifespan)
```

> 📌 **`lifespan` haqida:** bu — ilova ishga tushganda va to'xtaganda ishlaydigan maxsus funksiya (6.3-darsda batafsil ko'riladi); bu yerda uni, ilova ishga tushganda ma'lumotlar bazasi jadvallarini avtomatik yaratish uchun ishlatdik.

## Keng tarqalgan xatolar

**Xato 1:** ma'lumotlar bazasi parolini, to'g'ridan-to'g'ri Python kodida (`DATABASE_URL = "postgresql://user:parol@..."`) yozib, uni Git'ga commit qilish.
❌ Bu — Git va GitHub darsligining 1.2 va 6.2-darslarida batafsil ko'rilgan jiddiy xavfsizlik xatosi.
✅ To'g'ri: ma'lumotlar bazasi manzilini har doim `.env` faylida saqlang (`pydantic-settings` orqali o'qing), `.env`ni esa `.gitignore`ga qo'shing.

**Xato 2:** `table=True` bilan e'lon qilingan bitta modelni, ham API request/response, ham ma'lumotlar bazasi jadvali sifatida, alohida modellarsiz ishlatish.
❌ Bu, boshida qulay tuyulishi mumkin, lekin loyiha kattalashganda, ma'lumotlar bazasidagi ichki maydonlar (masalan, `parol_xash`) tasodifan API javobida "chiqib ketishi" xavfini tug'diradi.
✅ To'g'ri: har doim kamida uch xil model yarating (asosiy/umumiy, yaratish uchun, javob uchun) — bu, 1.3-darsda ko'rilgan `response_model` tamoyilining, ma'lumotlar bazasi bilan ishlashdagi tabiiy davomi.

**Xato 3:** `SQLModel.metadata.create_all(engine)`ni, production loyihasida, jadval strukturasini o'zgartirish uchun doimiy ishlatishda davom etish.
❌ `create_all()` — faqat **mavjud bo'lmagan** jadvallarni yaratadi; agar mavjud jadvalga yangi ustun qo'shish yoki mavjudini o'zgartirish kerak bo'lsa, bu funksiya **hech narsa qilmaydi** (xato ham bermaydi, shunchaki e'tiborsiz qoldiradi) — bu, "nega yangi ustun ko'rinmayapti" degan chalkash muammoga olib kelishi mumkin.
✅ To'g'ri: dastlabki, kichik loyihalar/prototiplar uchun `create_all()` yetarli, lekin haqiqiy, rivojlanayotgan loyihalarda, jadval o'zgarishlarini boshqarish uchun har doim Alembic (4.3-darsda ko'riladi) ishlatilishi kerak.

## Mashq/topshiriq

**(Oson)** Docker orqali PostgreSQL konteynerini ishga tushiring, so'ng `psql` yoki boshqa vosita orqali unga ulanib, bo'sh ma'lumotlar bazasi yaratilganini tasdiqlang.

**(O'rtacha)** `Talaba` nomli SQLModel jadval modelini yarating (`id`, `ism`, `familiya`, `guruh` maydonlari bilan), va uni uchta modelga (`TalabaAsosi`, `Talaba` (`table=True`), `TalabaJavob`) ajrating.

**(Qiyin)** To'liq `database.py` faylini yozing: `.env` faylidan `DATABASE_URL`ni `pydantic-settings` orqali o'qing, `engine` yarating, va `session_olish()` dependency funksiyasini yozing. Keyin, nima uchun `Session(engine)` uchun `with` operatoridan foydalanish (yuqoridagi misoldagi kabi) muhimligini, resurslarni boshqarish nuqtai nazaridan tushuntirib bering (3.2-darsdagi `yield` dependency mavzusiga bog'lab).

from sqlmodel import create_engine, Session

`with Session(engine)` ishlatilishi muhim, chunki bu — 3.2-darsda ko'rilgan `yield` dependency naqshiga o'xshab, sessiya **avtomatik yopilishini** kafolatlaydi: `with` bloki tugagach (so'rov muvaffaqiyatli yoki xato bilan tugashidan qat'i nazar), sessiya ma'lumotlar bazasi bilan aloqani to'g'ri yopadi — agar bu qo'lda, `try`/`finally`siz qilinsa, ochiq qolgan sessiyalar to'planib, ma'lumotlar bazasi ulanishlari tugab qolishi (connection pool exhaustion) mumkin.

## Qisqacha xulosa

SQLModel — SQLAlchemy (ma'lumotlar bazasi ORM) va Pydantic (validatsiya)ni birlashtirib, `table=True` bilan e'lon qilingan klasslar orqali, ham ma'lumotlar bazasi jadvalini, ham Python modelini bitta joyda tavsiflash imkonini beradi; PostgreSQL — Docker konteyneri orqali ishga tushiriladi (Docker darsligiga bevosita bog'liq holda), ulanish parametrlari esa `.env` fayli va `pydantic-settings` orqali xavfsiz boshqariladi. Real loyihalarda, jadval modeli va API request/response modellari **alohida** klasslar sifatida (umumiy asosiy klassdan meros olgan holda) yaratiladi — bu, ma'lumotlar bazasi strukturasi va tashqi API interfeysini mustaqil rivojlantirish imkonini beradi. Keyingi darsda, ushbu modellar asosida to'liq CRUD (Create, Read, Update, Delete) endpoint'larini yaratamiz.
