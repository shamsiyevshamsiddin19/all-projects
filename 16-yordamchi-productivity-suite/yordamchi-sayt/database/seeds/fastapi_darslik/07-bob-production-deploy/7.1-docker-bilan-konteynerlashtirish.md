# FastAPI ilovasini Docker bilan konteynerlashtirish

## Bu darsda nimalarni o'rganasiz

- FastAPI loyihasi uchun to'g'ri Dockerfile yozishni o'rganasiz
- `uv` bilan ishlaydigan optimallashtirilgan, multi-stage build yaratasiz
- Docker Compose orqali FastAPI + PostgreSQL'ni birga ishga tushirasiz
- `.dockerignore` va production'ga tayyor konteyner amaliyotlarini qo'llaysiz

## Nazariy qism

### Nima uchun FastAPI'ni konteynerlashtirish kerak

Docker darsligida chuqur o'rganilgan tamoyillar — FastAPI loyihalari uchun ham to'liq amal qiladi: "mening kompyuterimda ishlaydi" muammosidan qutulish, barcha muhitlarda (rivojlantirish, sinov, production) bir xil natijani kafolatlash, va Docker Compose orqali, ilova + ma'lumotlar bazasini (4-bobda ko'rilgan PostgreSQL) birgalikda, izchil boshqarish.

### Oddiy Dockerfile — boshlang'ich nuqta

```dockerfile
FROM python:3.13-slim

WORKDIR /app

COPY pyproject.toml uv.lock ./
RUN pip install uv && uv sync --frozen --no-dev

COPY . .

EXPOSE 8000

CMD ["uv", "run", "fastapi", "run", "app/main.py", "--port", "8000"]
```

| Qism | Vazifasi |
|---|---|
| `python:3.13-slim` | Yengil, minimal Python bazaviy image (Docker darsligining 2.1-darsida ko'rilgan image tanlash tamoyillariga mos) |
| `uv sync --frozen` | `uv.lock`dagi **aniq** versiyalarni o'rnatadi (0.2-darsda ko'rilgan takrorlanuvchi o'rnatish tamoyili) |
| `--no-dev` | Faqat production uchun zarur paketlarni o'rnatadi, test kutubxonalarini (`pytest`, va h.k.) o'tkazib yuboradi |
| `fastapi run` | Production rejimida ishga tushirish (1.1-darsda ko'rilgan `fastapi dev`dan farqli — hot reload'siz, optimallashtirilgan) |

### Multi-stage build — optimallashtirilgan yechim

Docker darsligining 2.3-darsida ko'rilgan multi-stage build naqshi, FastAPI loyihalarida ham image hajmini sezilarli kamaytiradi:

```dockerfile
# 1-bosqich: bog'liqliklarni o'rnatish
FROM python:3.13-slim AS builder

WORKDIR /app

RUN pip install uv

COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project

COPY . .
RUN uv sync --frozen --no-dev

# 2-bosqich: yakuniy, yengil image
FROM python:3.13-slim

WORKDIR /app

COPY --from=builder /app/.venv /app/.venv
COPY --from=builder /app /app

ENV PATH="/app/.venv/bin:$PATH"

EXPOSE 8000

CMD ["fastapi", "run", "app/main.py", "--port", "8000"]
```

| Bosqich | Vazifasi |
|---|---|
| `builder` bosqichi | Barcha qurish vositalari (`uv`, kompilyatsiya kerak bo'lgan paketlar) shu yerda ishlatiladi |
| Yakuniy bosqich | Faqat **tayyor** virtual muhit (`.venv`) va kod nusxalanadi — qurish vositalari yakuniy image'ga kirmaydi |

> 📌 **`--no-install-project` bilan ikki bosqichli `uv sync`:** birinchi `uv sync` (loyiha kodi nusxalanishidan **oldin**) — faqat bog'liqliklarni o'rnatadi; bu, Docker darsligining 2.2-darsida ko'rilgan **build cache** tamoyiliga mos — agar faqat kod o'zgarsa (bog'liqliklar emas), Docker, bog'liqliklarni o'rnatish qadamini **qayta bajarmasdan**, keshdan foydalanadi, bu esa qurish vaqtini sezilarli tezlashtiradi.

### `.dockerignore` — keraksiz fayllarni chiqarib tashlash

Git darsligining 1.2-darsida ko'rilgan `.gitignore` tamoyiliga o'xshab, Docker ham o'zining "e'tiborsiz qoldirish" mexanizmiga ega:

```dockerignore
.venv/
__pycache__/
*.pyc
.env
.git/
.pytest_cache/
tests/
README.md
.gitignore
```

Bu — `COPY . .` buyrug'i, keraksiz (va ba'zan maxfiy, masalan `.env`) fayllarni image ichiga nusxalab qo'yishining oldini oladi, hamda qurish jarayonini tezlashtiradi.

### Docker Compose — FastAPI + PostgreSQL birgalikda

4.1-darsda alohida ishga tushirilgan PostgreSQL konteyneri, endi to'liq loyiha bilan birga, `compose.yaml` orqali boshqariladi:

```yaml
# compose.yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://fastapi_user:parol123@db:5432/kutubxona_db
    depends_on:
      db:
        condition: service_healthy
    volumes:
      - ./app:/app/app   # rivojlantirish uchun - kod o'zgarishi darhol aks etadi

  db:
    image: postgres:17
    environment:
      POSTGRES_USER: fastapi_user
      POSTGRES_PASSWORD: parol123
      POSTGRES_DB: kutubxona_db
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fastapi_user"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

> 📌 **`depends_on` + `condition: service_healthy`:** bu, Docker darsligining 4.2-darsida chuqur o'rganilgan naqsh — `web` xizmati, `db`ning shunchaki "ishga tushishini" emas, balki `healthcheck` orqali **haqiqatan so'rovlarni qabul qilishga tayyor** ekanini kutadi. Bu, FastAPI ilovasi, hali to'liq tayyor bo'lmagan ma'lumotlar bazasiga ulanishga urinib, xatoga uchrashining oldini oladi.

```bash
docker compose up -d --build
```

### Maxfiy ma'lumotlarni Docker Compose'da boshqarish

4.1 va 5.1-darslarda ko'rilgan `.env` tamoyili, Docker Compose bilan ham davom etadi:

```yaml
services:
  web:
    build: .
    env_file:
      - .env
```

```bash
# .env (gitignore qilingan, Docker darsligining 6.1-darsidagi kabi)
DATABASE_URL=postgresql://fastapi_user:parol123@db:5432/kutubxona_db
MAXFIY_KALIT=juda-uzun-tasodifiy-maxfiy-kalit-2026
```

### `fastapi run` vs `fastapi dev` — production'da farq

| Xususiyat | `fastapi dev` | `fastapi run` |
|---|---|---|
| Avtomatik qayta yuklash | Ha (kod o'zgarganda) | Yo'q |
| Ishga tushirish tezligi | Sekinroq (debug vositalari yoqilgan) | Tezroq, optimallashtirilgan |
| Qачон ishlatiladi | Faqat lokal rivojlantirish | Production, Docker konteynerida |

## Amaliy misol

To'liq, production'ga tayyor Docker sozlamasi — kutubxona API loyihasi:

```dockerfile
# Dockerfile
FROM python:3.13-slim AS builder
WORKDIR /app
RUN pip install --no-cache-dir uv
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project
COPY . .
RUN uv sync --frozen --no-dev

FROM python:3.13-slim
WORKDIR /app
RUN groupadd -r fastapi && useradd -r -g fastapi fastapi
COPY --from=builder /app/.venv /app/.venv
COPY --from=builder /app /app
ENV PATH="/app/.venv/bin:$PATH"
USER fastapi
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s \
  CMD python -c "import httpx; httpx.get('http://localhost:8000/salomatlik')" || exit 1
CMD ["fastapi", "run", "app/main.py", "--port", "8000"]
```

> 📌 **`USER fastapi` — nima uchun muhim:** bu, Docker darsligining 6.1-darsida ko'rilgan xavfsizlik tamoyili — konteyner ichida, ilovani `root` foydalanuvchi sifatida emas, balki maxsus, kamroq huquqli foydalanuvchi nomidan ishga tushirish, xavfsizlik zaifliklari ta'sirini cheklaydi.

```yaml
# compose.yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    env_file:
      - .env
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:17
    env_file:
      - .env
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fastapi_user"]
      interval: 5s
      retries: 5

volumes:
  postgres_data:
```

```bash
# .dockerignore
.venv/
__pycache__/
*.pyc
.env
.git/
tests/

# Ishga tushirish
docker compose up -d --build

# Loglarni kuzatish (Docker darsligining 6.2-darsida ko'rilgan)
docker compose logs -f web

# Salomatlikni tekshirish
curl http://localhost:8000/salomatlik
```

## Keng tarqalgan xatolar

**Xato 1:** `.env` faylini, `.dockerignore`ga qo'shmasdan, `COPY . .` orqali to'g'ridan-to'g'ri image ichiga nusxalash.
❌ Bu, maxfiy ma'lumotlarni (ma'lumotlar bazasi paroli, JWT maxfiy kaliti) image ichiga "quyib qo'yadi" — agar image, jamoat registriga (Docker Hub) tasodifan yuklansa, bu ma'lumotlar oshkor bo'ladi.
✅ To'g'ri: `.env`ni har doim `.dockerignore`ga qo'shing, va production konfiguratsiyasini, `docker compose`ning `env_file` yoki tashqi sirlar boshqaruvi (masalan, Docker Secrets) orqali, image **tashqarisida** yetkazing.

**Xato 2:** `fastapi dev` buyrug'ini, production Dockerfile'ida ham ishlatishda davom etish.
❌ `fastapi dev` — avtomatik qayta yuklash va boshqa debug vositalarini o'z ichiga oladi, bu esa production'da keraksiz resurs sarfi va potentsial xavfsizlik zaifliklariga olib kelishi mumkin.
✅ To'g'ri: Dockerfile'ning `CMD` buyrug'ida, har doim `fastapi run` (production rejimi) ishlatilishi kerak; `fastapi dev` — faqat lokal, konteynersiz rivojlantirish uchun qoldirilishi kerak.

**Xato 3:** multi-stage build'ni ishlatmasdan, oddiy, bitta bosqichli Dockerfile bilan qolib, image hajmini keraksiz kattalashtirish.
❌ Bitta bosqichli build — qurish vositalari (kompilyatorlar, keshlar) yakuniy image ichida qolib ketishiga olib keladi, bu esa image hajmini sezilarli oshiradi va deploy vaqtini uzaytiradi.
✅ To'g'ri: har doim multi-stage build'dan foydalaning — bu, Docker darsligining 2.3-darsida batafsil ko'rilgan, production Docker image'lari uchun standart amaliyot.

## Mashq/topshiriq

**(Oson)** Oddiy, bitta bosqichli Dockerfile yozing (yuqoridagi birinchi misoldagi kabi), uni `docker build -t mening-api .` orqali qurib, `docker run -p 8000:8000 mening-api` orqali ishga tushiring.

**(O'rtacha)** Yuqoridagi Dockerfile'ni, multi-stage build'ga o'zgartiring, va `docker images` orqali, ikkala versiyaning (oddiy vs multi-stage) hajmini solishtiring.

**(Qiyin)** To'liq `compose.yaml` fayli yozing — FastAPI ilovasi va PostgreSQL'ni birga ishga tushirsin, `healthcheck` va `depends_on: condition: service_healthy` bilan. Keyin, `.env` faylida maxfiy ma'lumotlarni saqlab, `env_file` orqali ikkala xizmatga ham uzating. Nima uchun `depends_on`da oddiy (shartsiz) versiya emas, balki `condition: service_healthy` ishlatilishi kerakligini, Docker darsligiga bog'lab tushuntiring.

<summary>Javoblarni ko'rish</summary>

1. `docker build -t mening-api . && docker run -p 8000:8000 mening-api`, so'ng `curl http://localhost:8000` orqali tekshirish.
2. Multi-stage Dockerfile'ni yozib, `docker build -t mening-api-optimallashtirilgan .`, so'ng `docker images` — odatda multi-stage versiya, sezilarli kichikroq hajmga ega bo'ladi, chunki qurish vositalari yakuniy image'da yo'q.
3. Amaliy misoldagi `compose.yaml`ga o'xshash tuzilma, `.env` faylida `DATABASE_URL`, `MAXFIY_KALIT` kabi qiymatlar, ikkala xizmatda ham `env_file: [.env]`. Oddiy `depends_on` (shartsiz) — faqat konteynerning **ishga tushganini** (process boshlanganini) kutadi, lekin PostgreSQL, hali ichki tayyorgarlik (ma'lumotlar bazasini initsializatsiya qilish) jarayonida bo'lishi mumkin — bu holatda, `web` xizmati, hali **so'rovlarni qabul qilishga tayyor bo'lmagan** bazaga ulanishga urinib, xatoga uchrashi mumkin; `condition: service_healthy` esa, Docker darsligining 4.2-darsida ko'rilganidek, `healthcheck` (`pg_isready`) haqiqatan **muvaffaqiyatli** javob berguncha kutadi, bu esa ishga tushirish tartibini ancha ishonchli qiladi.

</details>

## Qisqacha xulosa

FastAPI loyihasini konteynerlashtirish — Docker darsligida o'rganilgan barcha tamoyillarni (multi-stage build, `.dockerignore`, `healthcheck`, `USER` orqali xavfsizlik) to'g'ridan-to'g'ri qo'llaydi, faqat FastAPI'ga xos jihatlar (`uv sync --frozen` bilan takrorlanuvchi o'rnatish, `fastapi run` production rejimi) qo'shiladi. Docker Compose — FastAPI ilovasi va PostgreSQL'ni (4-bobda ko'rilgan) birgalikda, `depends_on: condition: service_healthy` orqali to'g'ri tartibda ishga tushiradi, `.env`/`env_file` esa maxfiy ma'lumotlarni xavfsiz, image tashqarisida saqlaydi. Keyingi darsda, bu konteynerlashtirilgan ilovani, Nginx va bir nechta worker jarayoni bilan, haqiqiy production muhitiga qanday tayyorlashni o'rganamiz.
