# FastAPI'ni testlash: pytest va httpx

## Bu darsda nimalarni o'rganasiz

- Nima uchun API'larni avtomatik test qilish muhimligini tushunasiz
- `TestClient` orqali sinxron testlar yozishni o'rganasiz
- `httpx.AsyncClient` orqali asinxron testlar yozishni bilasiz
- Testlar uchun alohida (test) ma'lumotlar bazasini sozlashni o'rganasiz

## Nazariy qism

### Nima uchun API'ni test qilish muhim

Python darsligining 5-bobida, `pytest` orqali umumiy testlash asoslari o'rganilgan edi. FastAPI ilovalari uchun testlash, ayniqsa muhim, chunki:

- API'ni har safar qo'lda, `curl` yoki Swagger UI orqali sinash — vaqt talab qiladi va xatolarga moyil
- Yangi funksiya qo'shilganda, **eski** funksionallik buzilmaganini avtomatik tekshirish kerak (regressiya testlari)
- Git va GitHub darsligining 6.1-darsida ko'rilgan CI/CD zanjiri, aynan avtomatik testlar orqali ishlaydi — testsiz, CI/CD "nima tekshirishni bilmaydi"

### Kerakli paketlarni o'rnatish

```bash
uv add --dev pytest httpx
```

| Paket | Vazifasi |
|---|---|
| `pytest` | Test yozish va ishga tushirish freymvorki (Python darsligida ko'rilgan) |
| `httpx` | HTTP mijoz kutubxonasi — FastAPI testlarida, both sinxron va asinxron so'rovlar uchun ishlatiladi |

> 📌 **`--dev` bayrog'i haqida:** `uv add --dev` — paketni faqat **rivojlantirish** bog'liqliklari sifatida qo'shadi (production serverida kerak emas, faqat test/ishlab chiqish paytida). Bu, `pyproject.toml`da alohida `[dependency-groups]` bo'limida saqlanadi.

### `TestClient` — sinxron testlar

Oddiy, sinxron endpoint'lar (4.1-4.3-darslarda ko'rilgan uslub) uchun, `TestClient` eng oddiy yechim:

```python
# test_main.py
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_bosh_sahifa():
    javob = client.get("/")
    assert javob.status_code == 200
    assert javob.json() == {"xabar": "API ishlayapti!"}

def test_kitob_yaratish():
    javob = client.post("/kitoblar", json={
        "nomi": "O'tkan kunlar",
        "muallif": "Abdulla Qodiriy",
        "yil": 1926,
    })
    assert javob.status_code == 201
    malumot = javob.json()
    assert malumot["nomi"] == "O'tkan kunlar"
    assert "id" in malumot
```

Ishga tushirish (Python darsligida ko'rilgan):

```bash
uv run pytest -v
```

### `httpx.AsyncClient` — asinxron testlar

4.4-darsda ko'rilgan asinxron endpoint'larni (yoki umuman, asinxron test uslubini) test qilish uchun, FastAPI'ning rasmiy hujjatlari `httpx.AsyncClient`ni tavsiya etadi:

```python
# test_main.py
import pytest
from httpx import AsyncClient, ASGITransport
from app.main import app

@pytest.mark.asyncio
async def test_kitob_yaratish_async():
    transport = ASGITransport(app=app)
    async with AsyncClient(transport=transport, base_url="http://test") as mijoz:
        javob = await mijoz.post("/kitoblar", json={
            "nomi": "Mehrobdan chayon",
            "muallif": "Abdulla Qodiriy",
            "yil": 1929,
        })
    assert javob.status_code == 201
```

| Qism | Vazifasi |
|---|---|
| `ASGITransport(app=app)` | FastAPI ilovasiga, haqiqiy tarmoq (server) ishga tushirmasdan, **to'g'ridan-to'g'ri** ulanish |
| `base_url="http://test"` | Test uchun soxta (haqiqiy bo'lmagan) manzil — talab qilinadi, lekin haqiqiy server bilan bog'liq emas |
| `@pytest.mark.asyncio` | `pytest`ga, bu test funksiyasi **asinxron** ekanini bildiradi |

`pytest-asyncio` paketi kerak bo'ladi:

```bash
uv add --dev pytest-asyncio
```

```ini
# pyproject.toml ichida
[tool.pytest.ini_options]
asyncio_mode = "auto"
```

`asyncio_mode = "auto"` — barcha `async def test_...` funksiyalarni, `@pytest.mark.asyncio` dekoratorisiz ham, avtomatik asinxron test sifatida tanib olishni ta'minlaydi.

### Testlar uchun alohida ma'lumotlar bazasi

> ⚠️ **Muhim tamoyil:** testlar, **hech qachon** haqiqiy (production yoki hatto oddiy rivojlantirish) ma'lumotlar bazasiga yozmasligi kerak. Buning o'rniga, har bir test uchun **toza, vaqtinchalik** ma'lumotlar bazasi ishlatiladi.

```python
# conftest.py
import pytest
from sqlmodel import SQLModel, Session, create_engine
from fastapi.testclient import TestClient
from app.main import app
from app.database import session_olish

TEST_DATABASE_URL = "sqlite://"  # xotiradagi, vaqtinchalik SQLite bazasi

@pytest.fixture(name="session")
def session_fixture():
    engine = create_engine(TEST_DATABASE_URL, connect_args={"check_same_thread": False})
    SQLModel.metadata.create_all(engine)
    with Session(engine) as session:
        yield session

@pytest.fixture(name="client")
def client_fixture(session: Session):
    def test_session_olish():
        return session

    app.dependency_overrides[session_olish] = test_session_olish
    client = TestClient(app)
    yield client
    app.dependency_overrides.clear()
```

| Qism | Vazifasi |
|---|---|
| `TEST_DATABASE_URL = "sqlite://"` | Xotiradagi (fayl yaratmaydigan), har bir test uchun **toza** SQLite bazasi |
| `app.dependency_overrides[...]` | FastAPI'ning maxsus mexanizmi — haqiqiy `session_olish` dependency'sini, **test uchun mo'ljallangan** versiyasi bilan almashtiradi |

> 📌 **`dependency_overrides` — nima uchun muhim:** bu, 3.2-darsda o'rganilgan Dependency Injection'ning eng katta amaliy afzalliklaridan biri — chunki ma'lumotlar bazasi (yoki boshqa tashqi xizmat) ulanishi, `Depends()` orqali "kiritilgan", uni testlarda **osongina almashtirish** mumkin, endpoint kodining o'zini o'zgartirmasdan. Bu, testlarni yozishni sezilarli osonlashtiradi.

### `pytest` fixture'laridan foydalanish

```python
# test_kitoblar.py
def test_kitob_yaratish(client):
    javob = client.post("/kitoblar", json={
        "nomi": "Sarob", "muallif": "Abdulla Qahhor", "yil": 1934,
    })
    assert javob.status_code == 201

def test_mavjud_bolmagan_kitob(client):
    javob = client.get("/kitoblar/999")
    assert javob.status_code == 404
    assert javob.json()["detail"] == "Kitob topilmadi"
```

`client` — `conftest.py`da e'lon qilingan fixture, `pytest` tomonidan avtomatik "kiritiladi" (bu ham, o'z navbatida, Dependency Injection'ga konseptual o'xshaydi).

### Autentifikatsiya bilan testlar

5.1-darsda ko'rilgan JWT autentifikatsiyasi bilan himoyalangan endpoint'larni test qilish:

```python
def test_himoyalangan_endpoint(client):
    # Avval ro'yxatdan o'tish va token olish
    client.post("/royxatdan-otish", json={
        "ism": "Test", "email": "test@example.com", "parol": "TestParol123",
    })
    kirish_javobi = client.post("/token", data={
        "username": "test@example.com", "password": "TestParol123",
    })
    token = kirish_javobi.json()["access_token"]

    # Tokendan foydalanib, himoyalangan endpoint'ni chaqirish
    javob = client.get("/profil", headers={"Authorization": f"Bearer {token}"})
    assert javob.status_code == 200
    assert javob.json()["email"] == "test@example.com"
```

## Amaliy misol

```python
from fastapi.testclient import TestClient
from app.main import app
from app.database import session_olish

@pytest.fixture(name="session")

    engine = create_engine("sqlite://", connect_args={"check_same_thread": False})
    SQLModel.metadata.create_all(engine)
    with Session(engine) as session:
        yield session

@pytest.fixture(name="client")
def client_fixture(session: Session):
    app.dependency_overrides[session_olish] = lambda: session
    yield TestClient(app)
    app.dependency_overrides.clear()
```

```python
# test_kitoblar.py
class TestKitoblarAPI:
    def test_yangi_kitob_yaratish(self, client):

        client.post("/kitoblar", json={"nomi": "Kitob 1", "muallif": "M1", "yil": 2000})
        client.post("/kitoblar", json={"nomi": "Kitob 2", "muallif": "M2", "yil": 2010})

        javob = client.get("/kitoblar")
        assert javob.status_code == 200
        assert len(javob.json()) == 2

    def test_mavjud_bolmagan_kitob_404(self, client):
        javob = client.get("/kitoblar/12345")
        assert javob.status_code == 404
```

## Keng tarqalgan xatolar

**Xato 1:** testlarni, haqiqiy (production yoki umumiy rivojlantirish) ma'lumotlar bazasiga qarshi ishga tushirish.
❌ Bu, testlar orqali yaratilgan "chalkash" test ma'lumotlari, haqiqiy ma'lumotlar bilan aralashib ketishiga, yoki (undan ham yomoni) testlar, tasodifan haqiqiy, muhim ma'lumotlarni o'chirib yuborishiga olib kelishi mumkin.
✅ To'g'ri: har doim, `app.dependency_overrides` orqali, testlar uchun **alohida, vaqtinchalik** (masalan, xotiradagi SQLite) ma'lumotlar bazasidan foydalaning — bu, testlarni to'liq izolyatsiya qilingan, xavfsiz holatda ishga tushirish imkonini beradi.

**Xato 2:** faqat "muvaffaqiyatli" holatlarni (masalan, to'g'ri ma'lumot bilan yaratish) test qilish, xato holatlarni (`404`, `422`, `401`) e'tiborsiz qoldirish.
❌ Bu, API'ning **xato holatlarda** to'g'ri ishlashini (masalan, mavjud bo'lmagan resurs so'ralganda, haqiqatan `404` qaytarishini) tasdiqlamasdan qoldiradi — production'da, aynan shu "chekka holatlar" ko'pincha muammoларга sabab bo'ladi.
✅ To'g'ri: har bir endpoint uchun, nafaqat "baxtli yo'l" (happy path), balki keng tarqalgan xato holatlarni (mavjud bo'lmagan ID, noto'g'ri ma'lumot, ruxsatsiz kirish) ham alohida testlar bilan qamrab oling.

**Xato 3:** testlar orasida holatni (masalan, global o'zgaruvchi yoki bir xil ma'lumotlar bazasi obyekti) baham ko'rish, natijada testlarning bir-biriga bog'liq bo'lib qolishi.
❌ Agar bir test, boshqasidan **oldin** ishga tushishi kerak bo'lsa (masalan, "avval kitob yaratilishi kerak, keyin uni o'chirish testi ishlaydi"), bu — testlarni **mo'rt** (fragile) va tartibga bog'liq qiladi, bitta testning o'zgarishi, boshqasini kutilmaganda buzishi mumkin.
✅ To'g'ri: har bir test funksiyasi, `pytest` fixture'lari orqali (yuqoridagi `session`/`client` kabi), **har safar yangi, toza** holatdan boshlanishi kerak — bu, testlarning bir-biridan mustaqil, istalgan tartibda ishga tushirilishi mumkinligini kafolatlaydi.

## Mashq/topshiriq

**(Oson)** `test_bosh_sahifa()` nomli oddiy test yozing, u `GET /` so'rovi `200` status kod va kutilgan JSON qaytarishini tekshirsin.

**(O'rtacha)** `conftest.py`da ko'rsatilgan `session` va `client` fixture'larini o'z loyihangizga sozlang, so'ng `POST /kitoblar` va `GET /kitoblar/{id}` uchun, ikkalasi ham "muvaffaqiyatli" va "404" holatlarini tekshiruvchi to'rtta test yozing.

**(Qiyin)** 5.1-darsdagi autentifikatsiya tizimi uchun, to'liq test stsenariysini yozing: (1) yangi foydalanuvchi ro'yxatdan o'tkazing, (2) noto'g'ri parol bilan kirishga urinib, `401` olganini tekshiring, (3) to'g'ri parol bilan kirib, token oling, (4) token bilan `/profil`ga so'rov yuborib, `200` va to'g'ri email qaytarilganini tekshiring, (5) token **berilmasdan** `/profil`ga so'rov yuborib, `401` olganini tekshiring.

## Qisqacha xulosa

FastAPI ilovalarini testlash — `TestClient` (sinxron kod uchun) yoki `httpx.AsyncClient` + `ASGITransport` (asinxron kod uchun) orqali, haqiqiy server ishga tushirmasdan, to'g'ridan-to'g'ri ilova bilan "suhbatlashish" imkonini beradi; `app.dependency_overrides` — 3.2-darsda o'rganilgan Dependency Injection'ning eng katta amaliy afzalligini namoyish etib, haqiqiy ma'lumotlar bazasini, testlar uchun toza, vaqtinchalik baza bilan osongina almashtirish imkonini beradi. Har bir endpoint uchun, nafaqat muvaffaqiyatli, balki xato holatlarni (`404`, `422`, `401`) ham qamrab oluvchi testlar yozish — Git va GitHub darsligining 6.1-darsida ko'rilgan CI/CD zanjirining "test" bosqichini mazmunli qiladi. Keyingi darsda, `lifespan` events va asinxron dasturlashning ilg'or naqshlarini o'rganamiz.
