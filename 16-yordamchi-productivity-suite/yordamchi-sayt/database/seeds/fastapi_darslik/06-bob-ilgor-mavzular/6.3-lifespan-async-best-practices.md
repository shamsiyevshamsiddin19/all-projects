# Lifespan events va asinxron dasturlash bo'yicha eng yaxshi amaliyotlar

## Bu darsda nimalarni o'rganasiz

- `lifespan` context manager orqali ilova ishga tushishi/to'xtashini boshqarasiz
- Eskirgan `@app.on_event` o'rniga zamonaviy uslubni qo'llashni o'rganasiz
- Asinxron kodda "bloklovchi" chaqiruvlardan qanday saqlanishni bilasiz
- FastAPI ilovasining umumiy unumdorligini oshirish bo'yicha amaliy tavsiyalarni o'rganasiz

## Nazariy qism

### `lifespan` nima uchun kerak

Real ilovalarda, ko'pincha ilova **ishga tushganda** (masalan, ma'lumotlar bazasi ulanish pool'ini tayyorlash, tashqi xizmat bilan bog'lanish) va **to'xtaganda** (masalan, ulanishlarni toza yopish) bajarilishi kerak bo'lgan kod bo'ladi. 4.1 va 4.4-darslarda, ma'lumotlar bazasi jadvallarini yaratish uchun `lifespan` allaqachon qisqacha ko'rilgan edi — endi uni chuqurroq o'rganamiz.

### Eskirgan uslub — `@app.on_event` (ishlatilmasligi kerak)

```python
# ESKI, TAVSIYA ETILMAYDIGAN uslub
@app.on_event("startup")
def ishga_tushirish():
    print("Ilova ishga tushdi")

@app.on_event("shutdown")
def toxtatish():
    print("Ilova to'xtadi")
```

> ⚠️ **Bu uslub — rasmiy hujjatlarda eskirgan (deprecated) deb belgilangan.** Yangi loyihalarda, bu o'rniga, quyida ko'rsatilgan `lifespan` context manager ishlatilishi shart.

### Zamonaviy uslub — `lifespan`

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Bu qism - ILOVA ISHGA TUSHGANDA, bir marta bajariladi
    print("Ilova ishga tushmoqda...")
    yield
    # Bu qism - ILOVA TO'XTAGANDA, bir marta bajariladi
    print("Ilova to'xtamoqda...")

app = FastAPI(lifespan=lifespan)
```

`yield`dan **oldingi** kod — "startup", `yield`dan **keyingi** kod — "shutdown" bosqichiga mos keladi (bu, 3.2-darsda ko'rilgan `yield` dependency naqshiga konseptual jihatdan juda o'xshash).

### `lifespan` orqali umumiy resurslarni boshqarish

Eng keng tarqalgan amaliy qo'llanilish — ma'lumotlar bazasi engine yoki tashqi xizmat mijozini, **bitta marta** yaratib, uni butun ilova davomida qayta ishlatish:

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI
from sqlalchemy.ext.asyncio import create_async_engine

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup
    app.state.db_engine = create_async_engine("postgresql+asyncpg://...")
    print("Ma'lumotlar bazasi ulanishi tayyor")

    yield

    # Shutdown
    await app.state.db_engine.dispose()
    print("Ma'lumotlar bazasi ulanishi yopildi")

app = FastAPI(lifespan=lifespan)
```

`app.state` — FastAPI ilovasi bo'ylab, istalgan joydan kirish mumkin bo'lgan, umumiy holat (state) saqlash uchun maxsus obyekt.

### Bir nechta resursni boshqarish

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    print("Ma'lumotlar bazasiga ulanmoqda...")
    engine = create_async_engine(DATABASE_URL)

    print("Kesh xizmatiga ulanmoqda...")
    kesh_mijozi = KeshMijozi()
    await kesh_mijozi.ulash()

    app.state.db_engine = engine
    app.state.kesh = kesh_mijozi

    yield   # ilova shu yerda, so'rovlarni qayta ishlashda ishlaydi

    print("Resurslarni tozalash...")
    await engine.dispose()
    await kesh_mijozi.uzish()
```

### Bloklovchi (blocking) kod — asinxron kontekstda eng katta xavf

0.1-darsda qisqacha eslatilgan muammo — bu yerda, amaliy jihatdan **eng muhim** unumdorlik tuzog'i hisoblanadi:

```python
import time
from fastapi import FastAPI

app = FastAPI()

@app.get("/xato-misol")
async def xato_misol():
    time.sleep(3)   # XATO! Bu - butun serverni 3 soniyaga "muzlatadi"
    return {"xabar": "Tayyor"}
```

`async def` ichida, **sinxron, bloklovchi** funksiya (`time.sleep()`, oddiy `requests.get()`, sinxron fayl o'qish) chaqirilsa — bu, FastAPI'ning butun asinxron "voqealar sikli"ni (event loop) **to'xtatib qo'yadi**, va shu 3 soniya davomida, **hech qanday boshqa so'rov** qayta ishlanmaydi — bu, 0.1-darsda ko'rilgan "restoran ofitsianti" metaforasidagi, "bitta stolda qotib qolgan ofitsiant"ga aynan mos keladi.

### To'g'ri yechimlar

| Vaziyat | Noto'g'ri | To'g'ri |
|---|---|---|
| Vaqt kutish | `time.sleep(3)` | `await asyncio.sleep(3)` |
| HTTP so'rov yuborish | `requests.get(url)` | `await httpx_mijoz.get(url)` (asinxron `httpx`) |
| Ma'lumotlar bazasi so'rovi | Sinxron `session.exec()` async funksiyada | `await async_session.exec()` (4.4-dars) |
| Og'ir, CPU talab qiluvchi hisoblash | To'g'ridan-to'g'ri `async def` ichida | Oddiy `def` (FastAPI, buni avtomatik alohida oqimda ishga tushiradi) yoki `run_in_executor` |

```python
import asyncio
import httpx

@app.get("/togri-misol")
async def togri_misol():
    await asyncio.sleep(3)   # TO'G'RI - boshqa so'rovlarni bloklamaydi

    async with httpx.AsyncClient() as mijoz:
        javob = await mijoz.get("https://api.example.com/malumot")

    return {"xabar": "Tayyor", "tashqi_malumot": javob.json()}
```

### Og'ir, CPU-intensiv hisoblash uchun — oddiy `def`

Qiziq nuance: agar funksiya, tarmoq yoki ma'lumotlar bazasini kutmasdan, faqat **og'ir hisoblash** (masalan, katta ma'lumotni qayta ishlash, murakkab matematik hisob-kitob) bajarsa, uni `async def` emas, balki oddiy `def` qilib yozish **afzalroq**:

```python
@app.post("/hisoblash")
def ogir_hisoblash(sonlar: list[int]):   # ODDIY def, async def EMAS
    natija = sum(x ** 2 for x in sonlar if x % 2 == 0)  # og'ir, CPU-intensiv
    return {"natija": natija}
```

0.1-darsda ko'rilganidek, FastAPI — oddiy `def` funksiyalarni, avtomatik ravishda, **alohida thread pool**da ishga tushiradi, bu esa, asinxron kod bilan solishtirganda, og'ir CPU ishlari uchun ko'pincha yaxshiroq (yoki hech bo'lmaganda, xavfsizroq) natija beradi — chunki bu, asosiy asinxron voqealar siklini "bloklamaydi".

### Sozlamalarni bir marta yuklash — `lru_cache`

Sozlamalar (4.1-darsda ko'rilgan `Sozlamalar` klassi) — har bir so'rovda qayta o'qilishi shart emas. `functools.lru_cache` orqali, ularni bir marta yuklab, keshlab qo'yish mumkin:

```python
from functools import lru_cache
from pydantic_settings import BaseSettings

class Sozlamalar(BaseSettings):
    database_url: str
    model_config = {"env_file": ".env"}

@lru_cache
def sozlamalarni_olish() -> Sozlamalar:
    return Sozlamalar()
```

```python
from typing import Annotated
from fastapi import Depends

@app.get("/sozlamalar-info")
def info(sozlamalar: Annotated[Sozlamalar, Depends(sozlamalarni_olish)]):
    return {"baza_manzili_uzunligi": len(sozlamalar.database_url)}
```

`@lru_cache` — funksiya birinchi marta chaqirilganda natijani "eslab qoladi", keyingi chaqiruvlarda esa, `.env` faylini qayta o'qimasdan, saqlangan natijani qaytaradi.

## Amaliy misol

To'liq, real loyihada uchraydigan `lifespan` va unumdorlik sozlamalari:

```python
# app/main.py
import logging
from contextlib import asynccontextmanager
from fastapi import FastAPI
from sqlalchemy.ext.asyncio import create_async_engine
from sqlmodel import SQLModel

from app.config import sozlamalarni_olish
from app.routers import kitoblar, auth

logger = logging.getLogger("mening_api")

@asynccontextmanager
async def lifespan(app: FastAPI):
    sozlamalar = sozlamalarni_olish()

    logger.info("Ma'lumotlar bazasi ulanishi tayyorlanmoqda...")
    engine = create_async_engine(
        sozlamalar.database_url.replace("postgresql://", "postgresql+asyncpg://")
    )

    async with engine.begin() as conn:
        await conn.run_sync(SQLModel.metadata.create_all)

    app.state.db_engine = engine
    logger.info("Ilova to'liq ishga tayyor")

    yield

    logger.info("Ilova to'xtamoqda, resurslar tozalanmoqda...")
    await engine.dispose()

app = FastAPI(title="Ilg'or Kutubxona API", lifespan=lifespan)
app.include_router(auth.router)
app.include_router(kitoblar.router)

@app.get("/salomatlik")
async def salomatlik_tekshiruvi():
    """Docker/orkestratsiya tizimlari uchun - ilova ishlab turganini tekshirish"""
    return {"holat": "sog'lom"}
```

> 📌 **`/salomatlik` endpoint'i haqida:** bu — Docker darsligining 4.2-darsida ko'rilgan `healthcheck` mexanizmi bilan bevosita bog'liq; production'da (7-bobda ko'riladi), orkestratsiya tizimlari (Docker Compose, Kubernetes) aynan shunday endpoint orqali, ilovaning "tirik va ishlashga tayyor" ekanini tekshiradi.

## Keng tarqalgan xatolar

**Xato 1:** eski `@app.on_event("startup")` uslubidan, yangi loyihalarda ham foydalanishda davom etish.
❌ Bu uslub — rasmiy hujjatlarda eskirgan deb belgilangan, va kelajakdagi FastAPI versiyalarida butunlay olib tashlanishi mumkin.
✅ To'g'ri: barcha yangi loyihalarda, har doim `lifespan` context manager (`@asynccontextmanager` bilan) ishlatilishi kerak.

**Xato 2:** `async def` endpoint ichida, sinxron, tarmoqqa bog'liq kutubxonalarni (masalan, oddiy, asinxron bo'lmagan `requests` kutubxonasi) `await`siz chaqirish.
❌ Bu, butun serverning, o'sha so'rov davomida, **boshqa hech qanday** so'rovni qayta ishlay olmasligiga olib keladi — bu, ayniqsa yuqori trafikli production muhitida, jiddiy unumdorlik muammosiga aylanadi.
✅ To'g'ri: `async def` ichida, faqat **asinxron** kutubxonalardan (`httpx.AsyncClient`, `asyncpg`, `asyncio.sleep`) foydalaning; agar sinxron kutubxona muqarrar bo'lsa, funksiyaning o'zini oddiy `def` qilib yozing (FastAPI uni avtomatik, xavfsiz tarzda, alohida oqimda ishga tushiradi).

**Xato 3:** har bir so'rovda, sozlamalar faylini (`.env`) yoki og'ir konfiguratsiyani, qayta-qayta o'qish.
❌ Bu, har bir so'rov uchun keraksiz, takrorlanuvchi fayl operatsiyalarini keltirib chiqaradi, bu esa, katta trafik ostida, sezilarli unumdorlik yo'qotishiga olib kelishi mumkin.
✅ To'g'ri: sozlamalarni, `@lru_cache` orqali, ilova ishga tushganda **bir marta** yuklab, keshlab qo'ying — bu, 3.2-darsda ko'rilgan Dependency Injection bilan birga, samarali va toza kodni ta'minlaydi.

## Mashq/topshiriq

**(Oson)** Oddiy `lifespan` funksiya yozing, u ilova ishga tushganda `"Salom, ilova ishga tushdi!"`, to'xtaganda esa `"Xayr, ilova to'xtadi!"` deb konsolga chop etsin.

**(O'rtacha)** `time.sleep(2)` ishlatuvchi, **noto'g'ri** yozilgan `async def` endpoint yarating, so'ng uni `asyncio.sleep(2)` bilan **to'g'irlang**. Ikkalasi orasidagi amaliy farqni (bir vaqtning o'zida ikkita so'rov yuborilganda nima sodir bo'lishini) tushuntiring.

**(Qiyin)** `@lru_cache` bilan keshlangan sozlamalar funksiyasini yarating, va uni `Depends()` orqali endpoint'da ishlatib ko'ring. Keyin, `lru_cache`ning **testlarda** muammo tug'dirishi mumkinligini (masalan, turli testlar, turli sozlamalarni sinab ko'rmoqchi bo'lsa) va buni FastAPI'ning `dependency_overrides` mexanizmi (6.2-darsda ko'rilgan) orqali qanday hal qilish mumkinligini tushuntirib bering.

## Qisqacha xulosa

`lifespan` context manager (`@asynccontextmanager`) — eskirgan `@app.on_event`ning zamonaviy o'rnini bosib, ilova ishga tushganda va to'xtaganda bajariladigan kodni (ma'lumotlar bazasi ulanishi, tashqi xizmatlar bilan bog'lanish/uzilish) toza, `yield` asosidagi naqsh orqali boshqarish imkonini beradi. Asinxron FastAPI kodida eng muhim tamoyil — `async def` ichida hech qachon sinxron, bloklovchi chaqiruvlar (`time.sleep()`, sinxron HTTP so'rovlar) ishlatmaslik, buning o'rniga ularning asinxron muqobillaridan (`asyncio.sleep()`, `httpx.AsyncClient`) foydalanish, yoki og'ir CPU ishlari uchun oddiy `def`ni tanlash kerak. `@lru_cache` bilan sozlamalarni bir marta yuklash — takrorlanuvchi operatsiyalarni kamaytiradi, lekin testlarda `dependency_overrides` bilan ehtiyotkorlik talab qiladi. Bu bilan 6-bob yakunlanadi — keyingi, yakuniy bobda, FastAPI ilovasini Docker orqali konteynerlashtirish, production'ga tayyorlash va CI/CD bilan avtomatlashtirishni o'rganamiz.
