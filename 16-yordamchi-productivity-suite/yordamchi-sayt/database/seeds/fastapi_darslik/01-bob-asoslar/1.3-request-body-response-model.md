# Request Body va Response Model

## Bu darsda nimalarni o'rganasiz

- Pydantic modellari orqali murakkab kiruvchi ma'lumotlarni (request body) qabul qilishni o'rganasiz
- `response_model` orqali API javobini nazorat qilishni bilasiz
- Status kodlarni to'g'ri tanlashni o'rganasiz
- Path, query va body parametrlarni birgalikda qo'llashni tushunasiz

## Nazariy qism

### Request Body nima

**Request Body** — mijoz (client) tomonidan serverga, so'rov **tanasida** (odatda JSON formatida) yuboriladigan ma'lumot. Bu — ayniqsa `POST`, `PUT`, `PATCH` so'rovlarida, yangi resurs yaratish yoki mavjudini yangilashda ishlatiladi.

FastAPI'da request body — **Pydantic modeli** orqali e'lon qilinadi:

```python
from pydantic import BaseModel
from fastapi import FastAPI

app = FastAPI()

class Mahsulot(BaseModel):
    nomi: str
    narx: float
    mavjud: bool = True

@app.post("/mahsulotlar")
def yangi_mahsulot(mahsulot: Mahsulot):
    return mahsulot
```

Endi `POST /mahsulotlar` so'rovi, tanasida JSON bilan yuborilganda:

```json
{
  "nomi": "Noutbuk",
  "narx": 8500000
}
```

FastAPI — avtomatik ravishda: JSON'ni o'qiydi, uni `Mahsulot` modeliga mos ravishda validatsiya qiladi (`nomi` — matn, `narx` — son bo'lishi shart, `mavjud` — ko'rsatilmasa `True`), va funksiyaga to'liq, tur-xavfsiz Python obyekti sifatida uzatadi.

> 📌 **Pydantic modellari haqida chuqurroq:** ushbu darsda Pydantic modellarining eng asosiy qo'llanilishini ko'ramiz; ularning to'liq imkoniyatlari (validatorlar, ichma-ich modellar, `Field`) 2-bobda batafsil o'rganiladi.

### Request body validatsiyasi — amalda

```bash
curl -X POST http://127.0.0.1:8000/mahsulotlar \
  -H "Content-Type: application/json" \
  -d '{"nomi": "Noutbuk", "narx": "notogri"}'
```

Natija — `422 Unprocessable Entity`, va xato javobida **aniq**, qaysi maydonda (`narx`) va nima sababdan (`narx` son bo'lishi kerak edi, matn kelgan) xato ekani ko'rsatiladi. Bu — validatsiya kodini qo'lda yozishning butunlay o'rnini bosadi.

### Bir nechta parametr manbasini birlashtirish

FastAPI — path, query va body parametrlarni **bitta funksiyada birgalikda** ishlatish imkonini beradi, va ularni avtomatik ajratib oladi:

```python
@app.put("/mahsulotlar/{mahsulot_id}")
def mahsulotni_yangilash(
    mahsulot_id: int,           # path parametr (URL'da bor)
    mahsulot: Mahsulot,          # request body (Pydantic modeli)
    tasdiqlash: bool = False,    # query parametr (oddiy tur, standart qiymat bilan)
):
    return {
        "mahsulot_id": mahsulot_id,
        "yangilangan_malumot": mahsulot,
        "tasdiqlangan": tasdiqlash,
    }
```

FastAPI qanday qilib bularni ajratadi:

| Parametr turi | Qачон aniqlanadi |
|---|---|
| Path parametr | Agar parametr nomi, URL yo'lidagi `{...}`ga mos kelsa |
| Request body | Agar parametr turi — Pydantic modeli (`BaseModel`dan meros olgan) bo'lsa |
| Query parametr | Qolgan barcha oddiy turlar (`str`, `int`, `bool`, va h.k.) |

### `response_model` — javobni nazorat qilish

Ba'zan, funksiyadan qaytariladigan ma'lumot va API **tashqariga ko'rsatishi kerak bo'lgan** ma'lumot — bir xil bo'lmasligi kerak. Klassik misol: foydalanuvchi paroli — ma'lumotlar bazasida saqlanadi, lekin API javobida **hech qachon** qaytarilmasligi kerak.

```python
from pydantic import BaseModel

class FoydalanuvchiYaratish(BaseModel):
    ism: str
    email: str
    parol: str

class FoydalanuvchiJavob(BaseModel):
    ism: str
    email: str
    # parol - ATAYLAB kiritilmagan

@app.post("/foydalanuvchilar", response_model=FoydalanuvchiJavob)
def foydalanuvchi_yaratish(foydalanuvchi: FoydalanuvchiYaratish):
    # (haqiqiy loyihada, bu yerda foydalanuvchi ma'lumotlar bazasiga saqlanadi)
    return foydalanuvchi
```

Garchi funksiya ichida `foydalanuvchi` obyekti `parol` maydonini o'z ichiga olsa ham, `response_model=FoydalanuvchiJavob` tufayli, API javobida **faqat** `ism` va `email` qaytariladi — `parol` avtomatik ravishda filtrlanadi.

> ⚠️ **Xavfsizlik uchun muhim:** `response_model` — maxfiy ma'lumotlarni (parol, ichki ID'lar, tizim maydonlari) tasodifan API orqali "chiqib ketishining" oldini olishning eng ishonchli usullaridan biri. Bu naqsh (ikkita alohida model — biri kirish, biri chiqish uchun) amaliyotda juda keng qo'llaniladi.

### To'g'ri status kodlarni tanlash

| Vaziyat | Status kod | FastAPI'da |
|---|---|---|
| Muvaffaqiyatli `GET` | `200 OK` | Standart (qo'shimcha kod kerak emas) |
| Muvaffaqiyatli `POST` (yangi resurs yaratildi) | `201 Created` | `status_code=status.HTTP_201_CREATED` |
| Muvaffaqiyatli `DELETE` | `204 No Content` | `status_code=status.HTTP_204_NO_CONTENT` |
| Resurs topilmadi | `404 Not Found` | `HTTPException(status_code=404, ...)` (2-bobda ko'riladi) |
| Noto'g'ri kiruvchi ma'lumot | `422 Unprocessable Entity` | Avtomatik (Pydantic validatsiyasi) |

```python
from fastapi import status

@app.post("/mahsulotlar", status_code=status.HTTP_201_CREATED)
def yangi_mahsulot(mahsulot: Mahsulot):
    return mahsulot

@app.delete("/mahsulotlar/{mahsulot_id}", status_code=status.HTTP_204_NO_CONTENT)
def mahsulotni_ochirish(mahsulot_id: int):
    return None
```

### `Body()` — oddiy turlarni ham request body qismi qilish

Kamdan-kam holatlarda, oddiy turni (Pydantic modeli emas) request body sifatida belgilash kerak bo'lishi mumkin — bu uchun `Body()` ishlatiladi:

```python
from typing import Annotated
from fastapi import Body

@app.post("/baholash")
def baholash(ball: Annotated[int, Body(ge=1, le=5)]):
    return {"ball": ball}
```

## Amaliy misol

To'liq CRUD (Create, Read) endpoint'lari — request body va response model birgalikda:

```python
from typing import Annotated
from pydantic import BaseModel
from fastapi import FastAPI, status

app = FastAPI()

class KitobYaratish(BaseModel):
    nomi: str
    muallif: str
    narx: float
    ombordagi_soni: int = 0

class KitobJavob(BaseModel):
    id: int
    nomi: str
    muallif: str
    narx: float

# Vaqtinchalik "ma'lumotlar bazasi" (4-bobda haqiqiy DB bilan almashtiriladi)
KITOBLAR_BAZASI: dict[int, dict] = {}
KEYINGI_ID = 1

@app.post("/kitoblar", response_model=KitobJavob, status_code=status.HTTP_201_CREATED)
def kitob_qoshish(kitob: KitobYaratish):
    global KEYINGI_ID
    yangi_kitob = {"id": KEYINGI_ID, **kitob.model_dump()}
    KITOBLAR_BAZASI[KEYINGI_ID] = yangi_kitob
    KEYINGI_ID += 1
    return yangi_kitob

@app.get("/kitoblar/{kitob_id}", response_model=KitobJavob)
def kitob_olish(kitob_id: int):
    return KITOBLAR_BAZASI.get(kitob_id, {})

@app.get("/kitoblar", response_model=list[KitobJavob])
def barcha_kitoblar():
    return list(KITOBLAR_BAZASI.values())
```

Sinash:

```bash
curl -X POST http://127.0.0.1:8000/kitoblar \
  -H "Content-Type: application/json" \
  -d '{"nomi": "O'\''tkan kunlar", "muallif": "Abdulla Qodiriy", "narx": 45000, "ombordagi_soni": 12}'
# {"id":1,"nomi":"O'tkan kunlar","muallif":"Abdulla Qodiriy","narx":45000.0}
# E'tibor bering: ombordagi_soni javobda YO'Q, chunki KitobJavob modelida u yo'q
```

`model_dump()` — Pydantic modelini oddiy Python `dict`iga aylantiradi (2-bobda batafsil ko'riladi), bu — bazaga saqlash yoki boshqa maqsadlar uchun qulay.

## Keng tarqalgan xatolar

**Xato 1:** request body uchun Pydantic modeli o'rniga, oddiy `dict` turini ishlatishga urinish.
❌ `def f(malumot: dict)` — ishlaydi, lekin FastAPI'ning eng katta afzalligi (avtomatik validatsiya, IDE autocomplete, aniq hujjat) butunlay yo'qoladi — bu, mohiyatan, FastAPI ishlatishning ma'nosini yo'qqa chiqaradi.
✅ To'g'ri: har doim kiruvchi ma'lumot strukturasi uchun aniq Pydantic modelini (`BaseModel`dan meros oluvchi klass) e'lon qiling.

**Xato 2:** bitta Pydantic modelini, ham kiruvchi (masalan, parol bilan), ham chiquvchi (parolsiz) ma'lumot uchun ishlatish, `response_model`ni butunlay unutish.
❌ Bu — maxfiy ma'lumotlarning (parol, ichki tizim maydonlari) tasodifan API javobida "chiqib ketishiga" olib kelishi mumkin — jiddiy xavfsizlik xatosi.
✅ To'g'ri: kirish va chiqish uchun har doim **alohida** Pydantic modellarini yarating (masalan, `FoydalanuvchiYaratish` va `FoydalanuvchiJavob`), va `response_model` parametrini har bir endpoint'da aniq belgilang.

**Xato 3:** `POST` so'rovi orqali yangi resurs yaratilganda, standart `200 OK` status kodini o'zgartirmasdan qoldirish.
❌ REST amaliyotiga ko'ra, bu — texnik jihatdan noto'g'ri emas, lekin API'dan foydalanuvchi (boshqa dasturchi yoki frontend) uchun, "resurs muvaffaqiyatli **yaratildi**" degan aniqroq signalni yo'qotadi.
✅ To'g'ri: yangi resurs yaratuvchi `POST` endpoint'larida, har doim `status_code=status.HTTP_201_CREATED` ni aniq belgilang — bu, REST API konvensiyalariga to'liq mos keladi va API'dan foydalanuvchilar uchun aniqroq.

## Mashq/topshiriq

**(Oson)** `Foydalanuvchi` nomli Pydantic modelini (`ism: str`, `yosh: int`) yarating va `POST /foydalanuvchilar` endpoint'ida uni request body sifatida qabul qiluvchi funksiya yozing.

**(O'rtacha)** Yuqoridagi vazifani kengaytirib, ikkita alohida model yarating: `FoydalanuvchiYaratish` (`ism`, `yosh`, `parol`) va `FoydalanuvchiJavob` (`ism`, `yosh`). `response_model=FoydalanuvchiJavob` orqali, `parol` maydoni javobda hech qachon ko'rinmasligini ta'minlang.

**(Qiyin)** `PUT /mahsulotlar/{mahsulot_id}` endpoint'ini yozing, unda: `mahsulot_id` — path parametr (`int`, `gt=0`), request body — `Mahsulot` Pydantic modeli (`nomi`, `narx`), va `bildirishnoma_yuborish` — ixtiyoriy `bool` query parametr (standart `False`). Funksiya, barcha uchta manbadan kelgan ma'lumotni birlashtirib qaytarsin, va status kod `200 OK` bo'lishi kerakligini asoslab bering (nima uchun `201` emas).

## Qisqacha xulosa

Request body — Pydantic modeli orqali e'lon qilinib, FastAPI kiruvchi JSON'ni avtomatik validatsiya qilib, funksiyaga tur-xavfsiz Python obyekti sifatida uzatadi; FastAPI, funksiya parametrlarining turiga qarab (path'dagi nomga mosligi, Pydantic modeli ekanligi yoki oddiy tur ekanligi), path, query va body parametrlarni avtomatik ajrata oladi. `response_model` — API javobini nazorat qilish, xususan maxfiy ma'lumotlarni (parol kabi) tasodifan chiqib ketishidan himoya qilishning asosiy vositasi hisoblanadi; to'g'ri status kodlarni (`201` yangi resurs uchun, `204` o'chirish uchun) tanlash esa, REST API konvensiyalariga rioya qilishning muhim qismi. Keyingi bobda, Pydantic modellarining chuqurroq imkoniyatlarini (validatorlar, ichma-ich modellar, `Field`) o'rganamiz.
