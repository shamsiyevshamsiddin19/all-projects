# Ruxsatlarni boshqarish (Role-Based Access Control)

## Bu darsda nimalarni o'rganasiz

- Role-Based Access Control (RBAC) tushunchasini o'rganasiz
- Foydalanuvchi modeliga rol qo'shishni va uni JWT ichida tashishni bilasiz
- Rol tekshiruvchi maxsus dependency'larni yaratasiz
- Faol/nofaol foydalanuvchi va ko'p darajali ruxsat tizimini quramiz

## Nazariy qism

### RBAC nima

**Role-Based Access Control (RBAC)** — foydalanuvchilarga **rol** (masalan, `"admin"`, `"moderator"`, `"foydalanuvchi"`) tayinlash va API endpoint'lariga kirishni, shu rollar asosida cheklash usuli. Bu — 5.1-darsda ko'rilgan autentifikatsiya ("siz kimsiz")dan farqli, **avtorizatsiya** ("sizga bu amalni bajarishga ruxsat bormi") masalasini hal qiladi.

### Foydalanuvchi modeliga rol qo'shish

```python
from enum import Enum
from sqlmodel import SQLModel, Field

class Rol(str, Enum):
    foydalanuvchi = "foydalanuvchi"
    moderator = "moderator"
    admin = "admin"

class Foydalanuvchi(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    ism: str
    email: str = Field(unique=True)
    parol_xeshi: str
    rol: Rol = Field(default=Rol.foydalanuvchi)
    faol: bool = Field(default=True)
```

`Rol` — 1.2-darsda ko'rilgan `Enum` naqshiga to'liq mos: bu, ma'lumotlar bazasida ham, API validatsiyasida ham, faqat oldindan belgilangan qiymatlarga ruxsat berishni ta'minlaydi.

### Rolni JWT ichiga qo'shish

5.1-darsda, token faqat `{"sub": foydalanuvchi_id}` ni saqlagan edi. Endi, rolni ham qo'shamiz — bu, har bir so'rovda, rolni **qayta bazadan o'qimasdan**, to'g'ridan-to'g'ri tokendan olish imkonini beradi:

```python
def token_yaratish(foydalanuvchi: Foydalanuvchi) -> str:
    tugash = datetime.now(timezone.utc) + timedelta(minutes=30)
    return jwt.encode(
        {
            "sub": str(foydalanuvchi.id),
            "rol": foydalanuvchi.rol.value,
            "exp": tugash,
        },
        MAXFIY_KALIT,
        algorithm="HS256",
    )
```

> ⚠️ **Muvozanat:** rolni tokenga qo'shish — samaradorlikni oshiradi (har safar bazaga murojaat qilish shart emas), lekin bu, agar administrator, tizimda foydalanuvchi rolini o'zgartirsa, **eski token, yangi rol o'zgarishini darhol aks ettirmasligini** anglatadi (token o'z muddati tugagunicha, eski rol bilan "ishlaydi"). Ko'p amaliy tizimlar, shu sababli, tokenlarning muddatini nisbatan qisqa (5.1-darsda ko'rilganidek, 15-30 daqiqa) qilib belgilaydi.

### Rol tekshiruvchi dependency — asosiy naqsh

3.2-darsda ko'rilgan dependency zanjirlash, bu yerda yanada rivojlantiriladi — endi, **parametrlashtirilgan** dependency yaratamiz:

```python
from typing import Annotated
from fastapi import Depends, HTTPException, status

def rol_talab_qilish(*ruxsat_etilgan_rollar: Rol):
    def tekshiruvchi(
        foydalanuvchi: Annotated["Foydalanuvchi", Depends(joriy_foydalanuvchini_olish)],
    ) -> "Foydalanuvchi":
        if foydalanuvchi.rol not in ruxsat_etilgan_rollar:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"Bu amal uchun quyidagi rollardan biri kerak: {[r.value for r in ruxsat_etilgan_rollar]}",
            )
        return foydalanuvchi
    return tekshiruvchi
```

Bu — **"dependency yaratuvchi funksiya"** naqshi: `rol_talab_qilish(Rol.admin)` chaqirilganda, u, o'z navbatida, yangi dependency funksiyasini (`tekshiruvchi`) qaytaradi, va aynan shu funksiya `Depends()` ichida ishlatiladi.

### Amaliyotda ishlatilishi

```python
@router.delete("/foydalanuvchilar/{foydalanuvchi_id}")
def foydalanuvchi_ochirish(
    foydalanuvchi_id: int,
    _: Annotated["Foydalanuvchi", Depends(rol_talab_qilish(Rol.admin))],
):
    return {"xabar": f"Foydalanuvchi {foydalanuvchi_id} o'chirildi"}

@router.post("/maqolalar/{maqola_id}/tasdiqlash")
def maqolani_tasdiqlash(
    maqola_id: int,
    _: Annotated["Foydalanuvchi", Depends(rol_talab_qilish(Rol.admin, Rol.moderator))],
):
    return {"xabar": "Maqola tasdiqlandi"}
```

E'tibor bering: `foydalanuvchi_ochirish` — faqat `Rol.admin`ga, `maqolani_tasdiqlash` esa — `Rol.admin` **yoki** `Rol.moderator`ga ruxsat beradi. Bu — bitta umumiy `rol_talab_qilish()` funksiyasidan, turli endpoint'lar uchun turli talablarni **moslashuvchan** tarzda yaratish imkonini beradi.

### Faol/nofaol foydalanuvchi tekshiruvi

RBAC'dan tashqari, ko'pincha foydalanuvchi hisobi "faolligini" ham tekshirish kerak bo'ladi (masalan, bloklangan foydalanuvchi):

```python
def faol_foydalanuvchini_olish(
    foydalanuvchi: Annotated["Foydalanuvchi", Depends(joriy_foydalanuvchini_olish)],
) -> "Foydalanuvchi":
    if not foydalanuvchi.faol:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="Hisobingiz bloklangan. Administrator bilan bog'laning",
        )
    return foydalanuvchi
```

Bu — yana bir zanjirlash misoli: `faol_foydalanuvchini_olish` → `joriy_foydalanuvchini_olish` → `oauth2_schema`. Barcha himoyalangan endpoint'lar, endi `faol_foydalanuvchini_olish`ga bog'lanishi mumkin, bu esa avtomatik ravishda **butun zanjirni** (token bormi? → yaroqlimi? → foydalanuvchi mavjudmi? → faolmi?) tekshiradi.

### O'z resursiga egalik tekshiruvi (ownership check)

Ba'zan, ruxsat — faqat rolga emas, balki "bu resurs sizniki yoki yo'qligiga" bog'liq bo'ladi (masalan, foydalanuvchi faqat **o'zining** buyurtmasini ko'ra oladi, admin esa — hammasini):

```python
@router.get("/buyurtmalar/{buyurtma_id}")
def buyurtma_korish(
    buyurtma_id: int,
    joriy: Annotated["Foydalanuvchi", Depends(faol_foydalanuvchini_olish)],
    session: Annotated[Session, Depends(session_olish)],
):
    buyurtma = session.get(Buyurtma, buyurtma_id)
    if not buyurtma:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Buyurtma topilmadi")

    if buyurtma.foydalanuvchi_id != joriy.id and joriy.rol != Rol.admin:
        raise HTTPException(status.HTTP_403_FORBIDDEN, "Bu buyurtmani ko'rishga ruxsatingiz yo'q")

    return buyurtma
```

## Amaliy misol

To'liq, ko'p darajali ruxsat tizimi:

```python
# app/dependencies.py
from typing import Annotated
from fastapi import Depends, HTTPException, status
from app.models import Foydalanuvchi, Rol
from app.security import joriy_foydalanuvchini_olish

def faol_foydalanuvchini_olish(
    foydalanuvchi: Annotated[Foydalanuvchi, Depends(joriy_foydalanuvchini_olish)],
) -> Foydalanuvchi:
    if not foydalanuvchi.faol:
        raise HTTPException(status.HTTP_403_FORBIDDEN, "Hisob bloklangan")
    return foydalanuvchi

def rol_talab_qilish(*ruxsat_etilgan_rollar: Rol):
    def tekshiruvchi(
        foydalanuvchi: Annotated[Foydalanuvchi, Depends(faol_foydalanuvchini_olish)],
    ) -> Foydalanuvchi:
        if foydalanuvchi.rol not in ruxsat_etilgan_rollar:
            raise HTTPException(
                status.HTTP_403_FORBIDDEN,
                f"Talab qilinadigan rollar: {[r.value for r in ruxsat_etilgan_rollar]}",
            )
        return foydalanuvchi
    return tekshiruvchi

# Tez-tez ishlatiladigan kombinatsiyalar uchun qulay yorliqlar
FaqatAdmin = Depends(rol_talab_qilish(Rol.admin))
AdminYokiModerator = Depends(rol_talab_qilish(Rol.admin, Rol.moderator))
```

```python
# app/routers/admin.py
from typing import Annotated
from fastapi import APIRouter, Depends
from app.dependencies import FaqatAdmin, AdminYokiModerator
from app.models import Foydalanuvchi

router = APIRouter(prefix="/admin", tags=["Admin"])

@router.get("/statistika")
def statistika(_foydalanuvchi: Annotated[Foydalanuvchi, FaqatAdmin]):
    return {"jami_foydalanuvchilar": 1204, "faol": 1150}

@router.post("/maqolalar/{maqola_id}/blok")
def maqolani_bloklash(
    maqola_id: int,
    _foydalanuvchi: Annotated[Foydalanuvchi, AdminYokiModerator],
):
    return {"xabar": f"Maqola {maqola_id} bloklandi"}
```

Sinash — turli rollar bilan:

```bash
# Oddiy foydalanuvchi tokeni bilan admin endpoint'iga urinish
curl http://127.0.0.1:8000/admin/statistika \
  -H "Authorization: Bearer <oddiy_foydalanuvchi_tokeni>"
# 403 Forbidden

# Admin tokeni bilan
curl http://127.0.0.1:8000/admin/statistika \
  -H "Authorization: Bearer <admin_tokeni>"
# 200 OK, statistika qaytariladi
```

## Keng tarqalgan xatolar

**Xato 1:** rolni tekshirishni, backend'da emas, faqat frontend'da (masalan, admin tugmasini "yashirish" orqali) amalga oshirish.
❌ Frontend tekshiruvi — faqat **foydalanuvchi tajribasi** uchun, u haqiqiy xavfsizlik chorasi emas; istalgan kishi, brauzer konsoli yoki `curl` orqali, to'g'ridan-to'g'ri API'ga so'rov yuborib, frontend cheklovini butunlay chetlab o'tishi mumkin.
✅ To'g'ri: ruxsat tekshiruvi har doim **backend'da**, har bir himoyalangan endpoint'da, `Depends(rol_talab_qilish(...))` orqali amalga oshirilishi shart — frontend cheklovi, bu tekshiruvni **almashtirmaydi**, faqat qo'shimcha, foydalanuvchi tajribasini yaxshilaydigan qatlam hisoblanadi.

**Xato 2:** faqat rolni tekshirib, foydalanuvchining `faol` maydonini (bloklangan-bloklanmaganini) e'tiborsiz qoldirish.
❌ Bu, bloklangan (masalan, qoidabuzarlik uchun) foydalanuvchi, hali amal qiladigan eski tokeni bilan, tizimdan to'liq foydalanishda davom etishiga olib kelishi mumkin.
✅ To'g'ri: har doim, rol tekshiruvidan **oldin**, `faol_foydalanuvchini_olish` kabi dependency orqali, foydalanuvchi hisobi hali faol ekanini tasdiqlang (yuqoridagi zanjirlash naqshida ko'rsatilganidek).

**Xato 3:** "o'z resursiga egalik" tekshiruvini unutib, faqat autentifikatsiyani (token yaroqliligini) tekshirish bilan cheklanish.
❌ Bu, istalgan autentifikatsiyadan o'tgan foydalanuvchi, boshqa foydalanuvchining shaxsiy ma'lumotlariga (masalan, `GET /buyurtmalar/{id}` orqali, boshqa birovning buyurtmasini) kira olishiga olib kelishi mumkin — bu, "IDOR" (Insecure Direct Object Reference) deb ataladigan, keng tarqalgan xavfsizlik zaifligi.
✅ To'g'ri: shaxsiy ma'lumotlarga tegishli har bir endpoint'da, resursning haqiqatan **so'rovchi foydalanuvchiga tegishli** ekanini (yoki so'rovchi — yetarlicha yuqori rolga ega ekanini) alohida tekshiring.

## Mashq/topshiriq

**(Oson)** `Foydalanuvchi` modeliga, `Rol` enum'i (`foydalanuvchi`, `admin`) va `faol: bool` maydonlarini qo'shing.

**(O'rtacha)** `rol_talab_qilish(*rollar)` funksiyasini yozing (yuqoridagi naqshga asosan), va uni `GET /maxfiy-malumot` endpoint'ida, faqat `Rol.admin` uchun ishlating; boshqa rol bilan so'rov yuborilganda `403` xatosi qaytishini tekshiring.

**(Qiyin)** `PUT /foydalanuvchilar/{foydalanuvchi_id}/profil` endpoint'ini yozing — u, foydalanuvchi faqat **o'zining** profilini yangilashi mumkinligini ta'minlashi kerak (`joriy.id == foydalanuvchi_id`), **lekin** agar `joriy.rol == Rol.admin` bo'lsa, u istalgan foydalanuvchining profilini yangilay olishi kerak. Bu ikki shartli mantiqni (`or` operatori bilan) yozing va nima uchun bu "egalik + rol" kombinatsiyasi, real loyihalarda sof rol-asosidagi tekshiruvdan ko'ra ko'proq uchrashini tushuntirib bering.

## Qisqacha xulosa

Role-Based Access Control (RBAC) — foydalanuvchilarga rol tayinlab (`Enum` orqali), API endpoint'lariga kirishni shu rollar asosida cheklash usuli; rol — JWT tokenga qo'shilib, har bir so'rovda samarali tekshirilishi mumkin. `rol_talab_qilish(*rollar)` — "dependency yaratuvchi funksiya" naqshi orqali, turli endpoint'lar uchun turli rol talablarini moslashuvchan tarzda ifodalash imkonini beradi; bu, 3.2-darsda ko'rilgan dependency zanjirlash bilan birlashib (autentifikatsiya → faollik tekshiruvi → rol tekshiruvi), to'liq, ko'p qatlamli avtorizatsiya tizimini tashkil etadi. Muhim xavfsizlik tamoyili — bunday tekshiruvlar har doim **backend'da**, hech qachon faqat frontend'da amalga oshirilishi, va zarur bo'lganda, "resursga egalik" tekshiruvi ham rol tekshiruvi bilan birga qo'llanilishi kerak. Bu bilan 5-bob (Autentifikatsiya) yakunlanadi — keyingi bobda, Background Tasks, WebSocket va testing kabi ilg'or mavzularni o'rganamiz.
