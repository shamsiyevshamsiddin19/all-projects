# Interactive rebase va commit'ni tuzatish (amend)

## Bu darsda nimalarni o'rganasiz

- `git commit --amend` orqali oxirgi commit'ni tuzatishni o'rganasiz
- Interactive rebase (`git rebase -i`) nima ekanini va uning imkoniyatlarini bilasiz
- Commit'larni birlashtirish (squash), qayta nomlash (reword) va tartiblashni o'rganasiz
- Nima uchun bu vositalar **faqat shaxsiy** tarixda xavfsiz ekanini chuqurroq tushunasiz

## Nazariy qism

### ⚠️ Muhim ogohlantirish — avvalgi darslardagi qoidaning davomi

Ushbu darsda o'rganiladigan ikkala vosita (`--amend` va interactive rebase) — commit **tarixini qayta yozadi** (yangi hash'lar yaratiladi). 2.3-darsda (Rebase asoslari) ko'rilgan oltin qoida bu yerda ham **to'liq amal qiladi**: bu vositalarni faqat **shaxsiy, hali boshqalar bilan bo'lishilmagan (push qilinmagan)** commit'larda ishlating.

### `git commit --amend` — oxirgi commit'ni tuzatish

Eng oddiy holat: commit qildingiz, lekin darhol kichik xato (unutilgan fayl yoki noto'g'ri yozilgan izoh) sezib qoldingiz.

```bash
# Faqat commit izohini o'zgartirish
git commit --amend -m "To'g'irlangan commit izohi"

# Unutilgan faylni ham qo'shib, oxirgi commit'ga "birlashtirish"
git add unutilgan_fayl.py
git commit --amend --no-edit
```

`--no-edit` — commit izohini o'zgartirmasdan, faqat yangi fayl(lar)ni oxirgi commit'ga qo'shadi.

> 📌 **Muhim tushuncha:** `--amend` — texnik jihatdan yangi commit yaratmaydi, balki oxirgi commit'ni **butunlay yangi hash bilan almashtiradi**. Shuning uchun, agar bu commit allaqachon push qilingan bo'lsa, `--amend`dan keyin qayta push qilish uchun `--force` kerak bo'ladi — bu esa yuqoridagi oltin qoidaga zid.

### Interactive rebase — nima uchun kerak

Oddiy `git rebase <branch>` (2.3-darsda ko'rilgan) — commit'larni boshqa branch ustiga "ko'chiradi". **Interactive rebase** (`-i` bayrog'i bilan) — bundan tashqari, commit'larning **o'zini** qayta tashkil etish imkonini beradi: ularni birlashtirish, qayta nomlash, tartibini o'zgartirish, hatto o'chirish.

```bash
# Oxirgi 3 ta commit ustida interactive rebase
git rebase -i HEAD~3
```

Bu buyruq — matn muharririda (masalan, `nano`, agar shunday sozlangan bo'lsa) ro'yxatni ochadi:

```
pick a1b2c3d Login formasi qo'shildi
pick e4f5g6h Xato: unutilgan import
pick f7g8h9i Yana kichik tuzatish

# Rebase a1b2c3d..f7g8h9i onto a1b2c3d
#
# Buyruqlar:
# p, pick = commit'ni o'z holicha qoldirish
# r, reword = commit'ni qoldirish, lekin izohini o'zgartirish
# e, edit = commit'ni qoldirish, lekin to'xtab, uni tahrirlash imkonini berish
# s, squash = commit'ni OLDINGI commit bilan birlashtirish (ikkala izoh saqlanadi)
# f, fixup = squash kabi, lekin bu commit'ning izohi butunlay tashlanadi
# d, drop = commit'ni butunlay o'chirish
```

### Interactive rebase buyruqlari batafsil

| Buyruq | Vazifasi |
|---|---|
| `pick` | Commit'ni o'zgarishsiz qoldirish |
| `reword` | Commit izohini o'zgartirish (kod o'zgarmaydi) |
| `edit` | Commit'da to'xtab, uning tarkibini (fayllarni ham) o'zgartirish imkonini berish |
| `squash` | Oldingi commit bilan birlashtirish, ikkala izohni birlashtirib tahrirlash imkoni beriladi |
| `fixup` | `squash`ga o'xshash, lekin bu commit'ning izohi shunchaki tashlab yuboriladi |
| `drop` | Commit'ni butunlay olib tashlash |

### Amaliy holat: bir nechta "WIP" commit'larni bitta toza commit'ga birlashtirish

Ishlash jarayonida, ko'pincha ko'plab kichik, "beparvo" commit'lar hosil bo'ladi:

```
pick a1b2c3d Login formasi - boshlanishi
pick e4f5g6h wip
pick f7g8h9i yana tuzatish
pick k1l2m3n nihoyat ishladi
```

PR ochishdan oldin, bularni bitta toza commit'ga birlashtirish uchun:

```
pick a1b2c3d Login formasi - boshlanishi
fixup e4f5g6h wip
fixup f7g8h9i yana tuzatish
fixup k1l2m3n nihoyat ishladi
```

Natijada — faqat bitta commit qoladi: `Login formasi - boshlanishi`, ammo u endi barcha to'rtta commit'ning **jamlangan o'zgarishlarini** o'z ichiga oladi.

> 📌 **Alternativ:** ko'p jamoalar, bu muammoni interactive rebase o'rniga, shunchaki GitHub'dagi PR'ni **"Squash and merge"** (3.3-darsda ko'rilgan) orqali hal qiladi — bu, aslida, xuddi shu natijani, avtomatik tarzda beradi.

### Konflikt yuzaga kelsa

Interactive rebase paytida ham (oddiy rebase kabi) konflikt yuzaga kelishi mumkin:

```bash
git add <hal-qilingan-fayl>
git rebase --continue

# yoki, butunlay voz kechish uchun
git rebase --abort
```

## Amaliy misol

To'liq jarayon — bir nechta "beparvo" commit'ni PR'dan oldin tozalash:

```bash
mkdir amend-rebase-mashqi && cd amend-rebase-mashqi && git init
echo "v1" > kod.py
git add kod.py
git commit -m "Boshlang'ich"

# Ishlash jarayonida uchta "beparvo" commit
echo "v2" > kod.py
git add kod.py
git commit -m "wip"

echo "v3" > kod.py
git add kod.py
git commit -m "yana tuzatish"

echo "v4 - final" > kod.py
git add kod.py
git commit -m "ishladi nihoyat"

git log --oneline
# d4e5f6a ishladi nihoyat
# c3d4e5f yana tuzatish
# b2c3d4e wip
# a1b2c3d Boshlang'ich

# Oxirgi 3 tasini birlashtiramiz
git rebase -i HEAD~3
```

Ochilgan muharrirda:

```
pick b2c3d4e wip
pick c3d4e5f yana tuzatish
pick d4e5f6a ishladi nihoyat
```

quyidagicha o'zgartiriladi:

```
pick b2c3d4e wip
fixup c3d4e5f yana tuzatish
fixup d4e5f6a ishladi nihoyat
```

Saqlab chiqilgach:

```bash
git log --oneline
# f9g8h7i wip                  <- endi barcha 3 ta o'zgarish shu yerda
# a1b2c3d Boshlang'ich
```

So'ng, `reword` bilan izohni ham to'g'irlash mumkin (`pick`ni `reword`ga o'zgartirib, saqlashda yangi izoh matnini kiritish):

```
Kod fayliga v4 versiyasigacha ishlanmalar kiritildi
```

`--amend` bilan tezkor tuzatish misoli:

```bash
echo "kichik tuzatish" >> kod.py
git add kod.py
git commit --amend --no-edit
# Oxirgi commit yangilandi, yangi alohida commit yaratilmadi
```

## Keng tarqalgan xatolar

**Xato 1:** `git commit --amend` yoki interactive rebase'ni, **allaqachon GitHub'ga push qilingan va boshqalar tomonidan `pull` qilingan** commit'larda ishlatish.
❌ Bu — hash'larni o'zgartiradi, natijada `git push` oddiy usulda rad etiladi ("rejected — non-fast-forward"), va agar `--force` bilan majburlansa, boshqa dasturchilarning tarixi bilan jiddiy nomuvofiqlik yuzaga keladi.
✅ To'g'ri: bu vositalarni faqat hali `push` qilinmagan (yoki faqat sizga tegishli, boshqa hech kim ishlatmagan feature branch'dagi) commit'larda ishlating.

**Xato 2:** interactive rebase paytida `pick`/`squash`/`fixup` buyruqlarining **tartibini** buzib qo'yish (masalan, `fixup`ni `pick`dan oldin qoldirish).
❌ Git — ro'yxatni yuqoridan pastga, aynan yozilgan tartibda qo'llaydi; noto'g'ri tartib xato yoki kutilmagan natijaga olib kelishi mumkin.
✅ To'g'ri: `fixup`/`squash` buyruqlari har doim, ular birlashtirilishi kerak bo'lgan **asosiy (`pick`) commit'dan keyin** joylashtirilishi kerak; agar chalkashib ketsangiz, `git rebase --abort` bilan xavfsiz orqaga qayting va qaytadan urinib ko'ring.

**Xato 3:** `--amend`ni juda ko'p marta, mustaqil, bog'liq bo'lmagan o'zgarishlar uchun ishlatib, natijada bitta "gigant" commit hosil qilish.
❌ Bu — code review'ni qiyinlashtiradi (4.2-darsda ko'rilgan "kichik, aniq maqsadli commit'lar" tamoyiliga zid) va muammo yuzaga kelganda, aynan qaysi o'zgarish xatoga sabab bo'lganini aniqlashni murakkablashtiradi.
✅ To'g'ri: `--amend`ni faqat **darhol, oxirgi commit bilan bevosita bog'liq** kichik tuzatishlar uchun ishlating (unutilgan fayl, imlo xatosi); mustaqil o'zgarishlar uchun har doim **yangi, alohida commit** yarating.

## Mashq/topshiriq

**(Oson)** Fayl yaratib commit qiling, so'ng darhol yana bir kichik o'zgartirish kiritib, uni `git commit --amend --no-edit` orqali oxirgi commit'ga qo'shing. `git log --oneline` orqali commit'lar sonini tekshiring (bitta bo'lishi kerak, ikkita emas).

**(O'rtacha)** Ketma-ket 4 ta kichik commit qiling (masalan, "wip1", "wip2", "wip3", "yakuniy"), so'ng `git rebase -i HEAD~4` orqali barchasini bitta, tushunarli izohli commit'ga birlashtiring.

**(Qiyin)** Beshta commit qiling. Interactive rebase orqali: ikkinchi va uchinchi commit'larni birlashtiring (`fixup`), to'rtinchi commit'ning izohini `reword` orqali o'zgartiring, beshinchi commit'ni esa `drop` orqali butunlay olib tashlang. Yakuniy `git log --oneline` natijasi necha ta commit ko'rsatishini oldindan hisoblang, so'ng amalda tekshiring.

<details>
<summary>Javoblarni ko'rish</summary>

1. `git commit -m "birinchi"`, keyin `echo "..." >> fayl && git add fayl && git commit --amend --no-edit`, `git log --oneline` — faqat 1 ta commit ko'rsatadi.
2. To'rtta commit qilingandan so'ng `git rebase -i HEAD~4`, birinchi qatorda `pick`, qolgan uchtasida `fixup` qoldirib saqlash — natijada `git log --oneline` bitta commit ko'rsatadi.
3. Beshta commit: 1-pick, 2-fixup (3-ga birlashadi), 3-pick, 4-reword, 5-drop. Boshlang'ich 5 tadan: 2-commit fixup orqali 1-commit(yo'q, aslida navbatdagi asosiy commit)ga qo'shiladi — agar tartib 1,2,3,4,5 bo'lib, "2-va-3-ni birlashtirish" ko'zda tutilgan bo'lsa, ro'yxatda 2-qatorga `pick`, 3-qatorga `fixup` qo'yiladi (3, 2ga qo'shiladi); natijada: 1, (2+3 birlashgan), 4 (izohi o'zgargan), va 5 o'chirilgan — yakunda jami **3 ta commit** qoladi (5 tadan: 1 ta birlashish orqali 1 ta kamayadi, 1 ta drop orqali yana 1 ta kamayadi: 5 - 1 - 1 = 3).

</details>

## Qisqacha xulosa

`git commit --amend` — oxirgi commit'ni (izohi yoki tarkibini) tezkor tuzatish uchun, `git rebase -i` esa — bir nechta commit'ni birlashtirish (`squash`/`fixup`), qayta nomlash (`reword`), tartibini o'zgartirish yoki o'chirish (`drop`) orqali, PR ochishdan oldin tarixni "toza va tushunarli" ko'rinishga keltirish uchun ishlatiladi. Ikkala vosita ham commit hash'larini o'zgartiradi, shuning uchun oldingi darsda o'rganilgan oltin qoida bu yerda ham amal qiladi: **faqat shaxsiy, hali push qilinmagan** commit'larda xavfsiz ishlatiladi — allaqachon boshqalar bilan bo'lishilgan tarixni qayta yozish jamoaviy ishlashda jiddiy muammolarga olib keladi.
