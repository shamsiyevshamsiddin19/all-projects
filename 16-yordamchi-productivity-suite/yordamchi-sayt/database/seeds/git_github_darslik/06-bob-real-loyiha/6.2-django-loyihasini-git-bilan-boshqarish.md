# Django/Python loyihasini Git bilan boshqarish — amaliy misol

## Bu darsda nimalarni o'rganasiz

- To'liq Django loyihasini noldan Git bilan qanday boshqarishni ko'rasiz
- Real jamoaviy workflow'ni (branch, commit, PR) amaliyotda qo'llaysiz
- Migratsiyalar va `.env` fayllarini Git bilan qanday to'g'ri boshqarishni bilasiz
- Butun kursda o'rgangan barcha bilimlarni bitta amaliy stsenariyda birlashtirasiz

## Nazariy qism

### Nima uchun bu dars muhim

Ushbu kursning oldingi darslarida, Git va GitHub'ning har bir vositasi **alohida** o'rganildi. Ammo amaliyotda, real loyiha ustida ishlash — bu vositalarning barchasini **birgalikda**, tabiiy ravishda qo'llashni talab qiladi. Ushbu dars — Python darsligi va Django bilimlariga tayangan holda, to'liq, boshidan oxirigacha bo'lgan real ish jarayonini ko'rsatadi.

### Django loyihasida odatiy `.gitignore`

Django loyihasi — o'ziga xos fayllar (migratsiyalar, statik fayllar, maxfiy sozlamalar) bilan ishlaydi, shuning uchun `.gitignore` (1.2-darsda ko'rilgan) alohida e'tiborni talab qiladi:

```gitignore
# Python
__pycache__/
*.pyc
venv/
.venv/

# Django
*.sqlite3
/media/
/staticfiles/
local_settings.py

# Maxfiy ma'lumotlar
.env

# IDE
.vscode/
.idea/
```

> ⚠️ **Migratsiyalar haqida muhim nuqta:** Django'ning `migrations/` papkasidagi fayllar — **odatda `.gitignore`ga qo'shilmaydi**. Ular — ma'lumotlar bazasi sxemasining tarixini o'z ichiga oladi va jamoaning barcha a'zolari uchun **bir xil** bo'lishi shart, shuning uchun ular Git'da kuzatilishi kerak.

### `.env` fayli va `.env.example`

Maxfiy ma'lumotlar (`SECRET_KEY`, ma'lumotlar bazasi parollari) — `.env` faylida saqlanadi va **hech qachon** commit qilinmaydi. Ammo, boshqa dasturchilar qanday o'zgaruvchilar kerakligini bilishi uchun, odatda **namuna** fayl commit qilinadi:

```bash
# .env - HAQIQIY qiymatlar (gitignore qilingan)
SECRET_KEY=juda-maxfiy-kalit-12345
DATABASE_URL=postgres://user:parol@localhost/dbname
DEBUG=True
```

```bash
# .env.example - NAMUNA (Git'ga commit qilinadi)
SECRET_KEY=your-secret-key-here
DATABASE_URL=postgres://user:password@localhost/dbname
DEBUG=True
```

Yangi jamoadosh loyihaga qo'shilganda, shunchaki `cp .env.example .env` qilib, o'z qiymatlarini kiritadi.

### Real loyiha branch strategiyasi

Kichik-o'rta Django loyihasi uchun, 4.1-darsda ko'rilgan **GitHub Flow** odatda eng mos yechim:

```
main (har doim deploy qilishga tayyor)
```

## Amaliy misol

To'liq, boshidan oxirigacha bo'lgan ish jarayoni — yangi Django funksiyasini qo'shish:

```bash
# 1. Loyihani GitHub'dan klonlaymiz (yoki yangi boshlaymiz)
git clone git@github.com:shamsiddin/mening-django-loyiham.git
cd mening-django-loyiham

# 2. Virtual muhitni faollashtiramiz (Python darsligi, 0-bob)
source venv/bin/activate

# 3. .env faylini sozlaymiz (namunadan nusxalab)
cp .env.example .env
nano .env   # shaxsiy qiymatlarni kiritamiz

# 4. main'ni yangilaymiz
git switch main
git pull origin main

# 5. Yangi funksiya uchun branch ochamiz
git switch -c feature/mahsulot-sharhlari

# 6. Django modelini qo'shamiz
cat >> mahsulotlar/models.py << 'EOF'

class Sharh(models.Model):
    mahsulot = models.ForeignKey(Mahsulot, on_delete=models.CASCADE)
    matn = models.TextField()
    baho = models.IntegerField()
    yaratilgan_vaqt = models.DateTimeField(auto_now_add=True)
EOF

# 7. Migratsiya yaratamiz (Django darsligida ko'rilgan)
python manage.py makemigrations

# 8. O'zgarishlarni tekshiramiz
git status
# modified:   mahsulotlar/models.py
# new file:   mahsulotlar/migrations/0007_sharh.py

git diff mahsulotlar/models.py

# 9. Bosqichma-bosqich, mantiqiy commit'lar qilamiz
git add mahsulotlar/models.py mahsulotlar/migrations/0007_sharh.py
git commit -m "Mahsulot sharhlari uchun Sharh modeli qo'shildi"

# 10. Test yozamiz va commit qilamiz (Python darsligi, pytest darsi)
cat > mahsulotlar/tests/test_sharh.py << 'EOF'
def test_sharh_yaratish():
    sharh = Sharh.objects.create(matn="Yaxshi mahsulot", baho=5)
    assert sharh.baho == 5
EOF

git add mahsulotlar/tests/test_sharh.py
git commit -m "Sharh modeli uchun test qo'shildi"

# 11. Testlarni lokalda ishga tushiramiz (push qilishdan oldin!)
pytest

# 12. Branch'ni GitHub'ga yuklaymiz
git push -u origin feature/mahsulot-sharhlari

# 13. Pull Request yaratamiz
gh pr create \
  --title "Mahsulot sharhlari funksiyasi" \
  --body "## Nima o'zgardi
Foydalanuvchilar endi mahsulotlarga sharh va baho qoldira oladi.

## Qanday sinovdan o'tkazildi
- Yangi unit test qo'shildi (test_sharh.py)
- Lokalda pytest orqali tekshirildi
- Admin panelda qo'lda sinovdan o'tkazildi

Closes #34"

# 14. CI (GitHub Actions) avtomatik testlarni ishga tushiradi (6.1-darsda ko'rilgan)
# 15. Jamoadosh review qiladi, Approve beradi
# 16. Squash and merge qilinadi, Issue #34 avtomatik yopiladi

# 17. Lokal main'ni yangilaymiz, keraksiz branch'ni tozalaymiz
git switch main
git pull origin main
git branch -d feature/mahsulot-sharhlari
```

### Migratsiya konfliktlari — Django'ga xos muammo

Agar ikkita dasturchi, bir vaqtda, bir xil raqamli migratsiya yaratsa (masalan, ikkalasi ham `0007_...`), `main`ga merge qilishda **migratsiya konflikti** yuzaga kelishi mumkin (ikkita turli `0007` fayli).

Yechim:

```bash
# main'ni yangilaymiz
git switch main
git pull origin main

# O'z branch'imizni qayta rebase qilamiz (2.3-darsda ko'rilgan)
git switch feature/mening-funksiyam
git rebase main

# Agar migratsiya raqami takrorlansa, Django buyrug'i bilan qayta raqamlaymiz
python manage.py makemigrations --merge
```

## Keng tarqalgan xatolar

**Xato 1:** `.env` faylini, ichida haqiqiy `SECRET_KEY` va parollar bo'lgan holda, tasodifan commit qilib yuborish.
❌ Bu — 1.2-darsda batafsil ko'rilgan jiddiy xavfsizlik xatosi, ayniqsa ochiq (public) repository'larda katta muammo.
✅ To'g'ri: loyihani boshlashning **birinchi qadami** sifatida `.env`ni `.gitignore`ga qo'shing, va `.env.example` orqali qaysi o'zgaruvchilar kerakligini jamoaga ko'rsating.

**Xato 2:** migratsiya fayllarini `.gitignore`ga qo'shib, ularni Git'dan yashirish.
❌ Bu — boshqa dasturchilarning ma'lumotlar bazasi sxemasi, sizniki bilan **mos kelmasligiga** olib keladi, chunki ular migratsiya tarixini butunlay ko'rmaydi.
✅ To'g'ri: `migrations/` papkasidagi fayllar har doim Git'da kuzatilishi kerak — faqat `*.sqlite3` (haqiqiy ma'lumotlar bazasi fayli) e'tiborsiz qoldiriladi, migratsiya **fayllari** emas.

**Xato 3:** kod o'zgarishlari va migratsiyani, tegishli test bilan birga emas, balki alohida, aloqasiz commit'larda qilish.
❌ Bu — keyinchalik, qaysi test qaysi funksiyaga tegishli ekanini kuzatishni qiyinlashtiradi (4.2-darsda ko'rilgan "aniq maqsadli commit" tamoyiliga zid).
✅ To'g'ri: yangi model + uning migratsiyasi + uning testi — mantiqiy jihatdan bog'liq bo'lgan holda, yo bitta, yo ketma-ket, aniq izohli commit'larda qilinishi kerak.

## Mashq/topshiriq

**(Oson)** Oddiy Django loyihasi (yoki Python darsligidagi mashqlaringizdan biri) uchun to'liq `.gitignore` va `.env.example` fayllarini yarating.

**(O'rtacha)** Yangi branch oching, Django modeliga yangi maydon qo'shing, migratsiya yarating, va ularni ikkita mantiqiy, alohida commit sifatida (model o'zgarishi + migratsiya birga, keyin — agar test qo'shilsa, alohida) saqlang.

**(Qiyin)** Ikki xayoliy dasturchi stsenariysini simulyatsiya qiling: ikkala "dasturchi" ham `main`dan branch ochib, bir xil modelga turli maydon qo'shib, migratsiya yaratadi (ikkalasi ham `0007_...` nomlanadi). Birinchisi `main`ga birlashtiriladi. Ikkinchisi endi `git rebase main` qilganda nima sodir bo'lishini, va `makemigrations --merge` qanday yordam berishini tushuntirib bering.

## Qisqacha xulosa

Real Django loyihasida Git bilan ishlash — kursda o'rganilgan barcha vositalarni (branch, commit, `.gitignore`, PR, CI) tabiiy ravishda birlashtiradi: `.env` maxfiy ma'lumotlari hech qachon commit qilinmaydi (`.env.example` orqali namuna ko'rsatiladi), migratsiya fayllari esa, aksincha, har doim Git'da kuzatiladi va jamoa a'zolari orasida bir xil bo'lishi shart. Har bir yangi funksiya — alohida branch, mantiqiy commit'lar (model + migratsiya + test) va Pull Request orqali `main`ga qo'shiladi; migratsiya raqamlari konfliktga uchraganda, Django'ning `--merge` bayrog'i Git'ning rebase/merge mexanizmlari bilan birgalikda muammoni hal qiladi.
