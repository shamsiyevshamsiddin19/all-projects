# Keng tarqalgan Git muammolari va ularni hal qilish (Troubleshooting)

## Bu darsda nimalarni o'rganasiz

- Eng ko'p uchraydigan Git xatolarini va ularning sabablarini tanib olasiz
- Har bir muammo uchun aniq, amaliy yechimni bilasiz
- "Vahima qilmasdan" muammoni diagnostika qilish odatini shakllantirasiz
- Kursda o'rgangan bilimlaringizni real muammolarni hal qilishda qo'llaysiz

## Nazariy qism

Ushbu dars — boshqalardan farqli, yangi buyruqni emas, balki **amaliyotda eng ko'p uchraydigan real muammolarni** va ularning tekshirilgan yechimlarini taqdim etadi. Har bir bo'lim: **muammo → sabab → yechim** tartibida tuzilgan.

### Muammo 1: "fatal: not a git repository"

**Sabab:** buyruq, `.git` papkasi mavjud bo'lmagan joyda (yoki `.git` papkasidan tashqarida) ishga tushirilgan.

```bash
git status
# fatal: not a git repository (or any of the parent directories): .git
```

**Yechim:**
```bash
# Joriy papkada loyiha bormi tekshiring
ls -la
# Agar .git yo'q bo'lsa, yo to'g'ri papkaga o'ting, yo yangi repository yarating
cd to'g'ri-loyiha-papkasi
# yoki
git init
```

### Muammo 2: "Your branch is ahead of 'origin/main' by N commits"

**Sabab:** lokal branch'da, remote'ga hali yuborilmagan commit'lar bor.

**Yechim:** bu — xato emas, oddiy holat. Shunchaki push qilish kifoya:
```bash
git push origin main
```

### Muammo 3: "Updates were rejected because the remote contains work that you do not have"

**Sabab:** remote'da, sizning lokal nusxangizda yo'q yangi commit'lar bor (masalan, boshqa dasturchi push qilgan).

**Yechim:**
```bash
# Avval remote'dagi o'zgarishlarni oling
git pull origin main

# Agar konflikt bo'lmasa, keyin push qiling
git push origin main
```

> ⚠️ Bu yerda `git push --force` ishlatish **noto'g'ri** — bu boshqa dasturchining ishini yo'qotib yuborishi mumkin (2.3 va 5.2-darslardagi oltin qoida).

### Muammo 4: "error: Your local changes... would be overwritten by checkout"

**Sabab:** branch almashtirilmoqchi, lekin joriy branch'da commit qilinmagan o'zgarishlar bor, va ular yangi branch'dagi fayllar bilan to'qnashadi.

**Yechim (uch variant):**
```bash
# 1-variant: o'zgarishlarni commit qilish
git add .
git commit -m "Vaqtinchalik saqlash"

# 2-variant: stash qilish (5.1-darsda ko'rilgan)
git stash
git switch boshqa-branch
# ... keyinroq: git stash pop

# 3-variant: o'zgarishlardan butunlay voz kechish (EHTIYOT BO'LING!)
git checkout -- .
```

### Muammo 5: Tasodifan noto'g'ri branch'da commit qilib qo'yish

**Sabab:** `main`da ishlash kerak emas edi, lekin branch almashtirilmagan holda commit qilingan.

**Yechim:**
```bash
# Commit hali push qilinmagan bo'lsa:
# 1. To'g'ri branch yarating (hozirgi holatdan)
git branch to'g'ri-branch-nomi

# 2. Joriy branch'ni (masalan, main'ni) oxirgi to'g'ri commit'ga qaytaring
git reset --hard HEAD~1

# 3. To'g'ri branch'ga o'ting - commit u yerda saqlanib qoladi
git switch to'g'ri-branch-nomi
```

### Muammo 6: Katta faylni tasodifan commit qilib yuborish

**Sabab:** `.gitignore`da yo'q, katta (masalan, video yoki ma'lumotlar bazasi) fayl tasodifan `git add .` bilan qo'shilgan.

**Yechim (agar hali push qilinmagan bo'lsa):**
```bash
# Faylni kuzatuvdan chiqarish, lekin diskda saqlab qolish
git rm --cached katta_fayl.zip
echo "katta_fayl.zip" >> .gitignore
git add .gitignore
git commit -m "Katta faylni kuzatuvdan olib tashlash"
```

> 📌 Agar fayl **allaqachon push qilingan** bo'lsa, uni tarixdan butunlay olib tashlash ancha murakkabroq (`git filter-repo` kabi maxsus vositalar talab qilinadi) — bu holatlarning oldini olish uchun, katta fayllarni **hech qachon** `git add .` bilan tekshirmasdan qo'shmaslik tavsiya etiladi.

### Muammo 7: Noto'g'ri commit izohi yozib yuborish

**Sabab:** shoshilib, xato yoki noaniq izoh bilan commit qilingan.

**Yechim (agar bu — oxirgi commit va hali push qilinmagan bo'lsa, 5.2-darsda ko'rilgan):**
```bash
git commit --amend -m "To'g'irlangan, aniq izoh"
```

Agar bu — bir necha commit orqadagi, hali push qilinmagan bo'lsa: interactive rebase (`git rebase -i`) orqali `reword`.

Agar bu — **allaqachon push qilingan** bo'lsa: odatda, izohni tarixiy jihatdan o'zgartirmaslik, kelajakdagi commit'larda aniqroq yozishga e'tibor qaratish tavsiya etiladi (chunki tuzatish uchun force-push kerak bo'ladi).

### Muammo 8: "detached HEAD" holati

**Sabab:** biror branch'ga emas, balki to'g'ridan-to'g'ri muayyan commit'ga o'tilgan (masalan, `git checkout a1b2c3d`).

```bash
git status
# HEAD detached at a1b2c3d
```

**Yechim:**
```bash
# Agar bu yerda hech narsa o'zgartirmagan bo'lsangiz - shunchaki biror branch'ga qayting
git switch main

# Agar bu yerda YANGI commit qilib qo'ygan bo'lsangiz va uni saqlab qolmoqchi bo'lsangiz
git switch -c yangi-branch-nomi
# (bu - "detached" holatdagi commit'larni yangi, "haqiqiy" branch'ga bog'laydi)
```

### Muammo 9: SSH orqali GitHub'ga ulanib bo'lmayapti

**Sabab:** SSH kalit sozlanmagan yoki GitHub'ga qo'shilmagan (3.1-darsda ko'rilgan).

**Yechim:**
```bash
# Ulanishni tekshirish
ssh -T git@github.com

# Agar "Permission denied (publickey)" chiqsa:
# 1. Kalit mavjudligini tekshiring
ls -la ~/.ssh

# 2. Agar yo'q bo'lsa, yangi kalit yarating va GitHub'ga qo'shing (3.1-darsdagi kabi)
ssh-keygen -t ed25519 -C "email@example.com"

# 3. SSH agentga qo'shilganini tekshiring
ssh-add -l
```

### Muammo 10: Merge yoki rebase paytida "adashib qolish"

**Sabab:** konflikt murakkablashib ketgan, qaysi holatda ekanligi noaniq bo'lib qolgan.

**Yechim — har doim xavfsiz "qayta boshlash" nuqtasi mavjud:**
```bash
# Merge jarayonida bo'lsangiz
git merge --abort

# Rebase jarayonida bo'lsangiz
git rebase --abort

# Umuman qaysi holatda ekaningizni bilmasangiz
git status   # bu har doim aniq ko'rsatma beradi
```

## Amaliy misol

Real diagnostika jarayoni — muammoni bosqichma-bosqich hal qilish:

```bash
# Vaziyat: git push qilishga urinilganda xato chiqdi
git push origin main
# ! [rejected]        main -> main (fetch first)
# error: failed to push some refs

# 1-qadam: vaziyatni tushunish
git status
# Your branch is ahead of 'origin/main' by 1 commit
# (lekin remote'da ham yangi commit'lar bor bo'lishi mumkin)

# 2-qadam: remote'dagi holatni ko'rish (2-3-darsda ko'rilgan fetch)
git fetch origin
git log origin/main --oneline -3

# 3-qadam: xavfsiz birlashtirish
git pull origin main
# (agar konflikt chiqsa - 2.2-darsdagi qadamlarni bajaramiz)

# 4-qadam: endi push qilamiz
git push origin main
# muvaffaqiyatli
```

### Umumiy diagnostika qoidasi

Har qanday noaniq vaziyatda, birinchi va eng muhim buyruq — har doim:

```bash
git status
```

Bu buyruq — deyarli har doim, keyingi qadam nima ekanini aniq ko'rsatadigan maslahat beradi (masalan, "use 'git pull' to merge the remote changes" yoki "use 'git add <file>...' to mark resolution").

## Keng tarqalgan xatolar

**Xato 1:** noaniq xato xabarini o'qimasdan, darhol `git push --force` yoki `git reset --hard` kabi **halokatli** buyruqlarga murojaat qilish.
❌ Bu — ko'pincha muammoni hal qilish o'rniga, uni yanada kattalashtiradi (masalan, boshqa dasturchining ishini yo'qotish).
✅ To'g'ri: har doim avval `git status` bilan aniq vaziyatni tushuning, xato xabarini diqqat bilan o'qing (Git — odatda, nima qilish kerakligini o'zi taklif qiladi), va faqat shundan keyin mos yechimni tanlang.

**Xato 2:** muammoni hal qilishda, internet'dan topilgan **tushunmagan** buyruqni, nima qilishini bilmasdan nusxalab ishlatish.
❌ Ayniqsa `--force`, `--hard` kabi bayroqlarga ega buyruqlar — noto'g'ri kontekstda ishlatilsa, qaytarib bo'lmaydigan yo'qotishlarga olib kelishi mumkin.
✅ To'g'ri: har qanday yangi buyruqni ishlatishdan oldin, uning **aynan nima qilishini** tushuning (kerak bo'lsa, ushbu kursning tegishli darsiga qayting); ishonchingiz komil bo'lmasa, avval mashq repository'sida sinab ko'ring.

**Xato 3:** muammoni "qo'rqib", hal qilishga urinmasdan, butun loyihani o'chirib, qaytadan `clone` qilish.
❌ Bu — agar lokal, hali push qilinmagan o'zgarishlar bo'lsa, ularni butunlay yo'qotadi.
✅ To'g'ri: Git — deyarli har doim, xatoni **yo'qotmasdan** tuzatish imkonini beradi (`reflog` orqali hatto "yo'qolgan" commit'larni ham tiklash mumkin — bu ilg'or mavzu bo'lib, `git reflog` buyrug'i orqali HEAD'ning barcha oldingi holatlarini ko'rish mumkin); shoshilib, radikal qadamlar qo'yishdan oldin, muammoni tinch tahlil qiling.

## Mashq/topshiriq

**(Oson)** Yangi papkada, `.git` papkasisiz turib, `git status` ishga tushiring va xato xabarini o'qib, uni qanday hal qilishni yozing.

**(O'rtacha)** Ataylab "Updates were rejected" vaziyatini yarating: bitta repository'ni ikki xil joyga klonlab (yoki ikkita "foydalanuvchi" simulyatsiya qilib), birida push qiling, ikkinchisida — remote'ni yangilamasdan push qilishga urining. Xatoni to'g'ri tartibda (`fetch`/`pull`, keyin `push`) hal qiling.

**(Qiyin)** `git reflog` buyrug'ini o'rganib chiqing (kursda alohida darsda ko'rilmagan, lekin muhim "xavfsizlik tarmog'i" vositasi). Ataylab `git reset --hard HEAD~2` bilan ikkita commit'ni "yo'qotib qo'ying", so'ng `git reflog` yordamida ularni qanday tiklash mumkinligini toping va amalda sinab ko'ring.

<details>
<summary>Javoblarni ko'rish</summary>

1. `git status` — "fatal: not a git repository" xatosini beradi; hal qilish: yo to'g'ri (`.git`ga ega) papkaga o'tish, yo `git init` bilan yangi repository yaratish.
2. Ikkita alohida papkaga bir xil repository'ni klonlab, birinchisida commit+push qilish, ikkinchisida (yangilanmagan holda) commit+push qilishga urinish — "rejected" xatosi chiqadi; yechim: `git pull origin main` (yoki `fetch`+`merge`), so'ng `git push origin main`.
3. `git reflog` — HEAD'ning barcha o'tgan holatlarini (hatto `reset --hard` bilan "yo'qotilgan" commit'larni ham) ko'rsatadi, chunki Git odatda hech narsani darhol butunlay o'chirmaydi; kerakli commit hash'ini `git reflog` natijasidan topib, `git reset --hard <hash>` (yoki `git cherry-pick <hash>`) orqali uni tiklash mumkin — bu, Git'ning "hech narsa osongina abadiy yo'qolmaydi" degan muhim xavfsizlik xususiyatini namoyish etadi.

## Qisqacha xulosa

Git bilan ishlashda uchraydigan aksariyat muammolar — aslida, ushbu kursda o'rganilgan tushunchalarning (branch, remote, stash, reset/revert) tabiiy davomi bo'lib, ularning barchasi uchun **aniq, xavfsiz yechim** mavjud: noaniq vaziyatda birinchi qadam har doim `git status`, konflikt yoki chalkash jarayonlarda esa `--abort` orqali xavfsiz orqaga qaytish mumkin. Eng muhim umumiy tamoyil — vahima qilib, halokatli (`--force`, `--hard`) buyruqlarga darhol murojaat qilmaslik, aksincha vaziyatni tinch tahlil qilib, Git'ning deyarli har doim mavjud bo'lgan xavfsiz yo'lini (jumladan, `git reflog` orqali "yo'qolgan" ishni ham tiklash imkoniyatini) topish. Shu bilan, ushbu kurs — Git'ning asosiy tushunchalaridan tortib, to'liq jamoaviy GitHub workflow'i va real muammolarni hal qilishgacha bo'lgan yo'lni yakunlaydi.
