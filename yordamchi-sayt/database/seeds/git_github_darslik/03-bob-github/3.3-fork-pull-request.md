# Fork va Pull Request workflow

## Bu darsda nimalarni o'rganasiz

- Fork nima ekanini va u clone'dan nima bilan farqlanishini tushunasiz
- Ochiq-manba (open-source) loyihaga hissa qo'shish jarayonini o'rganasiz
- Pull Request (PR) yaratish va uning tarkibiy qismlarini bilasiz
- GitHub CLI orqali PR yaratishni o'rganasiz

## Nazariy qism

### Fork nima

**Fork** — boshqa foydalanuvchining GitHub'dagi repository'sidan, **o'z akkauntingizda mustaqil nusxa** yaratish. Bu — ayniqsa siz o'sha loyihaga to'g'ridan-to'g'ri yozish huquqiga ega bo'lmaganingizda (masalan, mashhur ochiq-manba loyihalarga hissa qo'shmoqchi bo'lganingizda) ishlatiladi.

| Amal | Nima qiladi |
|---|---|
| **Clone** | Repository'ni **kompyuteringizga** yuklab oladi (akkauntda yangi nusxa yaratmaydi) |
| **Fork** | Repository'ning **GitHub'dagi o'z akkauntingizga** to'liq nusxasini yaratadi (keyin uni yana `clone` qilish mumkin) |

Fork qilish — GitHub veb-saytida, loyiha sahifasidagi **Fork** tugmasi orqali amalga oshiriladi (bir necha soniyada, brauzerda).

### Standart ochiq-manba hissa qo'shish (contribution) jarayoni

```
1. Asl loyihani FORK qilasiz (GitHub'da, o'z akkauntingizga)
2. O'z fork'ingizni kompyuteringizga CLONE qilasiz
3. Yangi BRANCH ochasiz (masalan, feature/xato-tuzatish)
4. O'zgarishlarni kiritib, COMMIT qilasiz
5. O'zgarishlarni o'z fork'ingizga PUSH qilasiz
6. Asl loyihaga PULL REQUEST ochasiz - "mening o'zgarishlarimni ko'rib chiqing" so'rovi
7. Loyiha egasi kod review qiladi, izoh qoldiradi (kerak bo'lsa)
8. Tasdiqlansa - PR asl loyihaga MERGE qilinadi
```

### Pull Request (PR) nima

**Pull Request** — "mening branch'imdagi o'zgarishlarni, sizning branch'ingizga qo'shishni so'rayman" degan **rasmiy so'rov**. PR — shunchaki kodni birlashtirish emas, balki:

- O'zgarishlarni **muhokama qilish** maydoni (izohlar, savol-javoblar)
- **Kod review** jarayoni (boshqa dasturchilar tekshiradi, taklif beradi)
- Avtomatik **testlar/CI** ishga tushirish nuqtasi (Docker darsligining 6.3-darsida ko'rilgan GitHub Actions shu yerda ishga tushadi)
- O'zgarishlar tarixining **hujjatlashtirilgan** yozuvi

### PR yaratish (GitHub veb-interfeysi orqali)

Branch'ni fork'ingizga `push` qilgandan so'ng, GitHub avtomatik ravishda "Compare & pull request" tugmasini taklif qiladi. Yoki qo'lda:

1. Loyiha sahifasida **Pull requests** bo'limi → **New pull request**
2. **base** (qayerga qo'shilsin — odatda asl loyihaning `main`i) va **compare** (sizning branch'ingiz) tanlanadi
3. Sarlavha va tavsif yoziladi (nima o'zgargani, nima uchun)
4. **Create pull request** tugmasi bosiladi

### Yaxshi PR tavsifi qanday bo'lishi kerak

| Yomon | Yaxshi |
|---|---|
| "fix" | "Login formasidagi email validatsiyasi xatosini tuzatish" |
| Tavsif yo'q | Nima o'zgargani, nima uchun, qanday sinovdan o'tkazilgani yozilgan |
| Bitta PR'da 10 xil narsa | Har bir PR — bitta aniq, mustaqil maqsadga xizmat qiladi |

Ko'pchilik loyihalar — PR shabloni (`.github/PULL_REQUEST_TEMPLATE.md`) orqali, qanday ma'lumot kerakligini oldindan belgilab qo'yadi.

### GitHub CLI orqali PR yaratish

`gh` vositasi — PR yaratishni terminaldan chiqmasdan bajarish imkonini beradi:

```bash
gh pr create --title "Login xatosini tuzatish" --body "Email validatsiyasidagi regex xatosi tuzatildi"

# Yoki interaktiv rejimda (savollar beriladi)
gh pr create
```

PR'larni ko'rish va boshqarish:

```bash
gh pr list              # ochiq PR'lar ro'yxati
gh pr view 42            # 42-raqamli PR tafsilotlari
gh pr checkout 42        # boshqa birovning PR'ini lokalda sinab ko'rish
gh pr merge 42            # PR'ni birlashtirish (huquq bo'lsa)
```

### Fork'ni asl loyiha bilan sinxronlashtirish

Fork qilingandan keyin, asl loyiha (`upstream`) rivojlanishda davom etadi, sizning fork'ingiz esa "muzlab" qoladi. Uni yangilash uchun (3.2-darsda ko'rilgan `upstream` remote orqali):

```bash
git remote add upstream git@github.com:asl-muallif/loyiha.git
git fetch upstream
git switch main
git merge upstream/main
git push origin main
```

### PR birlashtirish usullari (GitHub'da)

GitHub — PR'ni asl branch'ga qo'shishning uch usulini taklif qiladi:

| Usul | Natija |
|---|---|
| **Merge commit** | Barcha commit'lar saqlanadi + yangi merge commit qo'shiladi |
| **Squash and merge** | PR'dagi barcha commit'lar **bitta** commit'ga siqiladi (toza tarix) |
| **Rebase and merge** | Commit'lar alohida saqlanadi, lekin merge commit'siz, tekis tarix hosil bo'ladi |

Ko'p jamoalar — kichik, ko'p sonli "WIP" commit'lardan iborat feature branch'lar uchun **Squash and merge**ni afzal ko'radi (natijada `main`da har bir PR — bitta, aniq commit sifatida ko'rinadi).

## Amaliy misol

To'liq hissa qo'shish (contribution) jarayoni simulyatsiyasi:

```bash
# 1. GitHub'da "ochiq-loyiha" ni fork qildik deb faraz qilamiz
# (brauzerda Fork tugmasi bosildi, natijada
#  github.com/shamsiddin/ochiq-loyiha paydo bo'ldi)

# 2. O'z fork'imizni klonlaymiz
git clone git@github.com:shamsiddin/ochiq-loyiha.git
cd ochiq-loyiha

# 3. Asl loyihani ham upstream sifatida qo'shamiz
git remote add upstream git@github.com:asl-muallif/ochiq-loyiha.git
git remote -v
# origin    git@github.com:shamsiddin/ochiq-loyiha.git
# upstream  git@github.com:asl-muallif/ochiq-loyiha.git

# 4. Yangi branch ochamiz
git switch -c fix/readme-xatosi

# 5. O'zgartirish kiritamiz
echo "Tuzatilgan matn" >> README.md
git add README.md
git commit -m "README'dagi imlo xatosini tuzatish"

# 6. O'z fork'imizga yuklaymiz
git push -u origin fix/readme-xatosi

# 7. PR yaratamiz (GitHub CLI orqali)
gh pr create --title "README imlo xatosini tuzatish" \
  --body "README.md faylidagi kichik imlo xatosi tuzatildi." \
  --base main --head shamsiddin:fix/readme-xatosi

# 8. Loyiha egasi PR'ni ko'rib chiqib, tasdiqlaydi va Squash and merge qiladi
```

## Keng tarqalgan xatolar

**Xato 1:** to'g'ridan-to'g'ri asl loyihaning `main` branch'ida o'zgartirish qilib, uni `push` qilishga urinish (fork/branch ochmasdan).
❌ Agar sizda yozish huquqi bo'lmasa, bu — "Permission denied" xatosi bilan rad etiladi; huquq bo'lgan taqdirda ham, bu jamoaviy amaliyotga zid (review jarayonini chetlab o'tadi).
✅ To'g'ri: har doim avval fork qiling (yoki, agar loyiha ichidagi a'zo bo'lsangiz, alohida branch oching), o'zgarishni alohida branch'da qilib, PR orqali taklif qiling.

**Xato 2:** PR'ni juda katta, ko'plab bog'liq bo'lmagan o'zgarishlar bilan yaratish.
❌ Bunday PR'ni review qilish — reviewer uchun juda qiyin va vaqt talab qiladi, ko'pincha rad etiladi yoki uzoq vaqt "osilib" qoladi.
✅ To'g'ri: har bir PR — bitta aniq, mustaqil maqsadga (bitta xato tuzatish, bitta kichik funksiya) xizmat qilishi kerak; katta o'zgarishlarni bir nechta kichik PR'larga bo'lib yuboring.

**Xato 3:** fork'ni uzoq vaqt yangilamasdan, asl loyihadan juda "orqada qolib ketish", so'ng katta konfliktlar bilan PR ochish.
❌ Bu — PR review jarayonini murakkablashtiradi, ko'plab keraksiz konfliktlarni keltirib chiqaradi.
✅ To'g'ri: yangi branch ochishdan oldin, doimo `upstream/main`ni fork'ingiz `main`iga sinxronlashtiring (`git fetch upstream && git merge upstream/main`), so'ng shundan **yangi** branch oching.

## Mashq/topshiriq

**(Oson)** GitHub'da istalgan kichik ochiq-manba loyihani (masalan, o'zingizning oldingi mashq repository'ingizni, boshqa akkaunt bilan) fork qiling va uni lokalga klonlang.

**(O'rtacha)** Fork qilingan loyihada yangi branch oching, kichik o'zgartirish (masalan, README'ga bitta qator) kiriting, commit qiling va o'z fork'ingizga push qiling. So'ng GitHub veb-interfeysida (yoki `gh pr create` orqali) Pull Request yarating.

**(Qiyin)** `upstream` remote qo'shib, uni `git fetch upstream` bilan yangilang, so'ng `git merge upstream/main` orqali fork'ingizni sinxronlashtiring. Squash and merge, Merge commit va Rebase and merge usullarining har birini tarixiy grafikda (`git log --graph`) qanday ko'rinish berishini tushuntirib bering.

## Qisqacha xulosa

Fork — boshqa foydalanuvchining repository'sidan o'z GitHub akkauntingizda mustaqil nusxa yaratish bo'lib, odatda yozish huquqingiz bo'lmagan (masalan, ochiq-manba) loyihalarga hissa qo'shish uchun ishlatiladi; standart jarayon — fork → clone → branch → commit → push → Pull Request. Pull Request — nafaqat kodni birlashtirish, balki muhokama, kod review va CI testlarini ishga tushirish uchun markaziy vosita; GitHub uchta birlashtirish usulini (Merge commit, Squash and merge, Rebase and merge) taklif etadi, ular tarix qanday ko'rinishi bilan farqlanadi. `upstream` remote — fork'ni asl loyihaning so'nggi holati bilan muntazam sinxronlashtirib turish uchun ishlatiladi.
