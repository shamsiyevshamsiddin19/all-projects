# Rebase asoslari va merge vs rebase

## Bu darsda nimalarni o'rganasiz

- `git rebase` nima ekanini va u `merge`dan nima bilan farqlanishini tushunasiz
- Rebase jarayonini amaliyotda qo'llashni o'rganasiz
- Rebase paytida konfliktlarni qanday hal qilishni bilasiz
- Qaysi holatda merge, qaysi holatda rebase ishlatilishi kerakligini tushunasiz

## Nazariy qism

### Rebase nima

**Rebase** — branch tarixini qayta yozish orqali, bir branch'ning commit'larini boshqa branch'ning **oxiriga** "ko'chirish" jarayoni. Natijada, tarix — merge commit'larsiz, **tekis chiziq** ko'rinishini oladi, xuddi feature branch boshidan buyon `main`ning eng oxirgi holatidan boshlangandek.

```bash
git switch feature/yangi-funksiya
git rebase main
```

### Merge vs Rebase — vizual farq

```
Boshlang'ich holat:
main:              A---B---E
                        \
feature:                 C---D

MERGE natijasi (yangi merge commit F, tarmoqlangan tarix saqlanadi):
main:              A---B---E---F
                        \       /
feature:                 C-----D

REBASE natijasi (C va D commit'lari E'dan keyinga "ko'chiriladi", tekis tarix):
main:              A---B---E---C'---D'
```

> 📌 **Muhim nuance:** rebase paytida commit'lar **aynan nusxalanmaydi** — ular texnik jihatdan **yangi hash'larga ega yangi commit'lar** sifatida qayta yaratiladi (shuning uchun yuqorida `C'` va `D'` — apostrof bilan belgilangan).

### Rebase qachon ishlatiladi

Odatiy stsenariy: siz `feature` branch'ida ishlayapsiz, shu orada `main`ga boshqa dasturchilar tomonidan yangi commit'lar qo'shildi. Ishni yakunlashdan oldin, o'z branch'ingizni `main`ning **eng so'nggi** holati ustiga "yangilash" uchun:

```bash
git switch feature/mening-ishim
git rebase main
```

Bu — `git merge main`ga alternativ, lekin natijada **toza, chiziqli tarix** hosil qiladi (merge commit'lar bilan "chalkash" bo'lmagan).

### Rebase paytida konfliktlarni hal qilish

Rebase — commit'larni birma-bir qayta qo'llaganligi sabab, konflikt yuzaga kelsa, jarayon **har bir commit'da alohida** to'xtaydi:

```bash
git rebase main
# CONFLICT (content): Merge conflict in narxlar.py
```

Konfliktni hal qilish qadamlari (merge'dan biroz farqli):

```bash
# 1. Konflikt fayllarni qo'lda tahrirlab, hal qilamiz
nano narxlar.py

# 2. Hal qilingan faylni qo'shamiz
git add narxlar.py

# 3. COMMIT emas - "continue" bilan davom ettiramiz!
git rebase --continue
```

Agar jarayon jonini yig'ib, undan butunlay voz kechmoqchi bo'lsangiz:

```bash
git rebase --abort
```

| Buyruq | Merge'da | Rebase'da |
|---|---|---|
| Hal qilingandan keyin | `git commit` | `git rebase --continue` |
| Bekor qilish | `git merge --abort` | `git rebase --abort` |

### ⚠️ Oltin qoida: ommaviy (public) branch'larni qayta yozmang

Rebase — commit tarixini **qayta yozadi** (yangi hash'lar bilan). Agar branch allaqachon boshqa dasturchilar tomonidan `pull` qilingan (ya'ni ular bilan **umumiy**) bo'lsa, uni rebase qilish — ularning lokal nusxasi bilan tarixiy nomuvofiqlik keltirib chiqaradi, bu esa jamoada katta chalkashlikka olib kelishi mumkin.

> ⚠️ **Qoida:** faqat **shaxsiy, hali boshqalar bilan bo'lishilmagan** (masalan, hali GitHub'ga push qilinmagan yoki faqat sizga tegishli feature branch'idagi) commit'larni rebase qiling. `main` yoki umumiy branch'larni **hech qachon** rebase qilmang.

### Merge vs Rebase — qачон nimani tanlash

| Vaziyat | Tavsiya etiladi |
|---|---|
| Shaxsiy feature branch'ni `main`ning so'nggi holati bilan yangilash | Rebase (toza tarix) |
| Jamoaviy/umumiy branch'larni birlashtirish | Merge (xavfsizroq, tarix o'zgarmaydi) |
| Loyiha tarixida "qachon nima birlashtirilgani" muhim bo'lsa | Merge (`--no-ff` bilan) |
| Pull Request'ni GitHub'da toza tarix bilan birlashtirish | Rebase yoki "Squash and merge" (3-bobda ko'ramiz) |

Ko'p jamoalar amaliyotda ikkalasini birga qo'llaydi: shaxsiy branch'da ishlashda `rebase` bilan tarixni toza saqlash, so'ng `main`ga qo'shishda GitHub'ning Pull Request interfeysi orqali (odatda "Squash and merge" tugmasi bilan).

## Amaliy misol

To'liq ish jarayoni — feature branch'ni `main`ning yangi holatiga rebase qilish:

```bash
mkdir rebase-mashqi && cd rebase-mashqi && git init
echo "v1" > versiya.txt
git add versiya.txt
git commit -m "Boshlang'ich versiya"

# Feature branch ochamiz
git switch -c feature/yangilanish
echo "v1 + feature qatori" > versiya.txt
git add versiya.txt
git commit -m "Feature: yangi qator qo'shildi"

# main'ga qaytib, u yerda BOSHQA commit qilamiz (masalan, boshqa dasturchi qilgandek)
git switch main
echo "v1 + main tuzatish" > versiya.txt
git add versiya.txt
git commit -m "main: kichik tuzatish"

# Endi feature branch'ni main'ning YANGI holati ustiga rebase qilamiz
git switch feature/yangilanish
git rebase main
# CONFLICT (ikkala branch bir xil faylni o'zgartirgani uchun)

cat versiya.txt
# <<<<<<< HEAD
# v1 + main tuzatish
# =======
# v1 + feature qatori
# >>>>>>> Feature: yangi qator qo'shildi

# Qo'lda hal qilamiz
echo "v1 + main tuzatish + feature qatori" > versiya.txt
git add versiya.txt
git rebase --continue

# Natijada - tekis, chiziqli tarix
git log --oneline --graph
```

## Keng tarqalgan xatolar

**Xato 1:** allaqachon boshqa dasturchilar `pull` qilib olgan umumiy branch'ni (masalan, `main`ni) rebase qilish.
❌ Bu — commit hash'larini o'zgartiradi, natijada boshqa dasturchilarning lokal nusxasi bilan tarix "ajralib ketadi", keyingi `push`/`pull`larda og'ir, chalkash konfliktlar yuzaga keladi.
✅ To'g'ri: faqat **shaxsiy** (hali boshqa hech kim bilan bo'lishilmagan) branch'larni rebase qiling; umumiy branch'lar uchun har doim `merge` ishlating.

**Xato 2:** konflikt hal qilingandan keyin, odat bo'yicha `git commit` yozish (merge'dagidek).
❌ Rebase jarayonida `git commit` — noto'g'ri, chunki rebase o'zining ichki mexanizmiga ega; bu xato buyruqqa olib kelishi yoki jarayonni chalkashtirishi mumkin.
✅ To'g'ri: rebase paytida konflikt hal qilingandan so'ng, har doim `git rebase --continue` ishlatiladi (`git commit` emas).

**Xato 3:** rebase jarayonida bir nechta ketma-ket konfliktga duch kelganda, adashib, qaysi bosqichda ekanini yo'qotib qo'yish.
❌ Rebase — har bir commit uchun alohida to'xtashi mumkin, bu esa uzoq feature branch'larda charchatuvchi bo'lishi mumkin.
✅ To'g'ri: har bir bosqichda `git status` ishga tushirib, qaysi faylda konflikt borligini va necha commit qolganini kuzatib boring; agar jarayon judayam murakkablashib ketsa, `git rebase --abort` bilan xavfsiz to'xtatib, muammoni boshqacha yondashuv (masalan, oddiy merge) bilan hal qiling.

## Mashq/topshiriq

**(Oson)** `main`dan yangi branch oching, unda bitta commit qiling, so'ng `main`ga hech narsa qo'shmasdan, `git rebase main` buyrug'ini ishga tushiring. Natijani (`git log --oneline`) kuzating va nima uchun konflikt bo'lmaganini tushuntiring.

**(O'rtacha)** Amaliy misoldagi kabi, ataylab rebase konfliktini yarating (ikkala branch bir xil faylni o'zgartirsin) va uni `git rebase --continue` orqali hal qiling.

**(Qiyin)** Bir xil boshlang'ich holatdan ikkita alohida sinov o'tkazing: birinchisida `git merge` bilan, ikkinchisida `git rebase` bilan birlashtiring (ikkala holatda ham bir xil konflikt sharoitini yarating). `git log --oneline --graph` orqali ikkala natijaning tarixiy ko'rinishini solishtiring va farqni o'z so'zlaringiz bilan tushuntirib bering.

Yangi branch'da bitta commit qilib, `main`ga hech narsa qo'shilmagan bo'lsa, `git rebase main` — hech qanday konflikt keltirib chiqarmaydi, chunki "ko'chiriladigan" faqat bitta commit bor va u bilan taqqoslanadigan yangi `main` commit'lari yo'q; natijada shunchaki branch "asos"i (base) `main`ning oxirgi commit'iga to'g'rilanadi (bu holatda bu deyarli fast-forward bilan bir xil natija beradi).
2. Amaliy misoldagi qadamlarni bajarish — konfliktni hal qilib, `git add` va `git rebase --continue` bilan yakunlash kerak.
3. Merge natijasida `git log --graph` — ikkita "shoxcha" alohida chiziqlar sifatida ko'rinib, ular bitta merge commit'da qo'shiladi (tarmoqlangan, ammo asl tarix saqlangan ko'rinish). Rebase natijasida esa — barcha commit'lar **bitta tekis, vertikal chiziq** sifatida ko'rinadi, xuddi feature branch boshidanoq `main`ning yangi holatidan boshlangandek; farq shundaki, rebase — "kim qachon nima qilgani" tarixini yashiradi (tekislaydi), merge esa uni to'liq saqlaydi.

## Qisqacha xulosa

`git rebase <branch>` — joriy branch'ning commit'larini ko'rsatilgan branch'ning oxiriga "qayta qo'yib", tekis, chiziqli tarix hosil qiladi (merge commit'larsiz), lekin bu jarayon commit'larning hash'larini o'zgartiradi, shuning uchun faqat **shaxsiy, boshqalar bilan bo'lishilmagan** branch'larda ishlatilishi kerak; konflikt yuzaga kelganda `git add` + `git rebase --continue` (yoki butunlay voz kechish uchun `git rebase --abort`) ishlatiladi. Umumiy qoida: shaxsiy ishni yangilashda rebase, jamoaviy/umumiy tarixni birlashtirishda esa merge — bu ikkisi bir-birini istisno qilmaydigan, balki turli vaziyatlar uchun mo'ljallangan ikkita vosita.
