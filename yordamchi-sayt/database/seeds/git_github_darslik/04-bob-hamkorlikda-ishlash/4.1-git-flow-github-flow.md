# Jamoaviy ishlash workflow'lari: Git Flow va GitHub Flow

## Bu darsda nimalarni o'rganasiz

- Nima uchun jamoalarga aniq "workflow" (ish tartibi) kerakligini tushunasiz
- GitHub Flow — sodda va zamonaviy yondashuvni o'rganasiz
- Git Flow — an'anaviy, murakkabroq modelni tushunasiz
- Qaysi loyiha uchun qaysi workflow mosligini bilib olasiz

## Nazariy qism

### Nima uchun workflow kerak

Bir necha dasturchi bir loyiha ustida ishlaganda, "kim qachon qaysi branch'ni ochadi, qachon `main`ga birlashtiradi, qachon deploy qilinadi" — degan savollarga **aniq, hamma tomonidan tushuniladigan javob** kerak bo'ladi. Aks holda, xaos yuzaga keladi: kim tugallanmagan kodni `main`ga qo'shib yuboradi, kim qaysi branch ustida ishlayotgani noaniq bo'lib qoladi.

**Workflow** — jamoa tomonidan qabul qilingan, branch'lar va release'lar bilan qanday ishlash kerakligi haqidagi **kelishilgan qoidalar to'plami**.

### GitHub Flow — sodda va zamonaviy

**GitHub Flow** — eng sodda va hozirda eng keng tarqalgan workflow, ayniqsa veb-ilovalar va tez-tez deploy qilinadigan loyihalar uchun mos:

```
1. main branch - har doim DEPLOY QILISHGA TAYYOR holatda
2. Har qanday yangi ish uchun - main'dan yangi branch ochiladi
   (nomi tavsiflovchi: feature/foydalanuvchi-profili)
3. Branch'da commit qilinadi, muntazam push qilinadi
4. Ishlash tugagach - Pull Request ochiladi
5. Kod review va (agar sozlangan bo'lsa) avtomatik testlar (CI) o'tkaziladi
6. Tasdiqlansa - main'ga MERGE qilinadi
7. main'ga merge qilingach - DARHOL (yoki avtomatik) production'ga deploy qilinadi
```

| Xususiyat | Tavsif |
|---|---|
| Branch'lar soni | Kam — asosan `main` + qisqa muddatli feature branch'lar |
| Release siklga | Yo'q — istalgan vaqtda deploy qilish mumkin |
| Murakkablik | Past — o'rganish va qo'llash oson |
| Mos keladi | Veb-ilovalar, tez-tez yangilanadigan xizmatlar, kichik-o'rta jamoalar |

### Git Flow — an'anaviy, murakkabroq model

**Git Flow** — 2010-yilda Vincent Driessen tomonidan taklif qilingan, ancha rasmiylashtirilgan model bo'lib, bir nechta doimiy branch turini o'z ichiga oladi:

| Branch | Vazifasi |
|---|---|
| `main` (yoki `master`) | Faqat **rasmiy chiqarilgan** (released) versiyalar |
| `develop` | Keyingi release uchun tayyorlanayotgan, birlashtirilgan kod |
| `feature/*` | Yangi funksiyalar (`develop`dan ochiladi, `develop`ga qaytadi) |
| `release/*` | Chiqarishga tayyorgarlik (versiya raqami, oxirgi tuzatishlar) |
| `hotfix/*` | Production'dagi shoshilinch xatoni tuzatish (`main`dan ochiladi) |

```
main:      ----A--------------------H (release)
                \                  /
develop:         B---C---D---E---F---G
                      \         /
feature/x:             --------
```

| Xususiyat | Tavsif |
|---|---|
| Branch'lar soni | Ko'p — aniq belgilangan turlar (develop, release, hotfix) |
| Release siklga | Ha — versiyalangan, rejalashtirilgan chiqarishlar |
| Murakkablik | Yuqori — ko'proq qoidalar, ko'proq branch boshqaruvi |
| Mos keladi | Versiyalangan dasturiy ta'minot (masalan, mobil ilova, desktop dastur), aniq release sikliga ega yirik loyihalar |

### Qaysi birini tanlash kerak

| Loyiha turi | Tavsiya etiladigan workflow |
|---|---|
| Veb-sayt, API xizmat (uzluksiz deploy qilinadi) | GitHub Flow |
| Mobil ilova (App Store/Play Market orqali versiyalangan chiqariladi) | Git Flow (yoki soddalashtirilgan varianti) |
| Kichik jamoaviy yoki shaxsiy loyiha | GitHub Flow (soddaligi tufayli) |
| Katta korporativ dasturiy ta'minot, qat'iy versiyalash talab qilinadigan | Git Flow |

> 📌 **Amaliy kuzatuv:** so'nggi yillarda ko'pchilik jamoalar (ayniqsa veb va bulut xizmatlari sohasida) GitHub Flow'ning soddaligini afzal ko'rmoqda, chunki uzluksiz integratsiya/uzluksiz yetkazib berish (CI/CD — Docker darsligining 6.3-darsida ko'rilgan) bilan tabiiy uyg'unlashadi. Git Flow esa, aniq "versiya 1.0, 2.0" tushunchasiga ega mahsulotlarda hali ham keng qo'llaniladi.

### Trunk-Based Development — yana bir muqobil

Qisqacha tilga olish lozim bo'lgan uchinchi yondashuv — **Trunk-Based Development**: bunda dasturchilar juda **qisqa muddatli** (bir necha soatlik) branch'larda ishlab, tez-tez to'g'ridan-to'g'ri `main`ga (yoki "trunk"ga) birlashtiradi, katta feature'lar esa "feature flag" (kod ichida yoqish/o'chirish imkoniyati) orqali boshqariladi. Bu — GitHub Flow'ning yanada "agressiv" versiyasi hisoblanadi, juda katta jamoalar (masalan, Google) tomonidan qo'llaniladi.

## Amaliy misol

GitHub Flow'ni amalda qo'llash — kichik jamoa stsenariysi:

```bash
# 1. main - doim tayyor holatda
git switch main
git pull origin main

# 2. Yangi vazifa uchun branch ochamiz
git switch -c feature/parol-tiklash

# 3. Ishlaymiz, commit qilamiz
echo "def parol_tiklash(): pass" >> auth.py
git add auth.py
git commit -m "Parolni tiklash funksiyasi qo'shildi (hozircha bo'sh)"

# 4. Muntazam push qilib boramiz (jamoaga ko'rinadigan bo'lish uchun)
git push -u origin feature/parol-tiklash

# 5. Funksiya tayyor bo'lgach - PR ochamiz
gh pr create --title "Parolni tiklash funksiyasi" --body "Email orqali parol tiklash qo'shildi"

# 6. Jamoadosh review qiladi, CI testlari o'tadi, PR tasdiqlanadi

# 7. Squash and merge - main'ga qo'shiladi

# 8. main - avtomatik CI/CD orqali production'ga deploy qilinadi (GitHub Actions)

# 9. Branch endi kerak emas - tozalaymiz
git switch main
git pull origin main
git branch -d feature/parol-tiklash
```

## Keng tarqalgan xatolar

**Xato 1:** kichik veb-loyihada, keraksiz murakkab Git Flow'ni (barcha `develop`, `release/*`, `hotfix/*` branch'lari bilan) qo'llashga urinish.
❌ Bu — kichik jamoa uchun ortiqcha byurokratiya keltirib chiqaradi, tez ish qilish o'rniga branch boshqaruviga ko'p vaqt sarflanadi.
✅ To'g'ri: loyiha hajmi va deploy chastotasiga qarab workflow tanlang — kichik, tez-tez yangilanadigan loyihalar uchun GitHub Flow odatda yetarli.

**Xato 2:** workflow'ni jamoada **yozma ravishda kelishmasdan**, har kim o'zicha ishlashda davom etish.
❌ Bu — ba'zi a'zolar to'g'ridan-to'g'ri `main`ga push qilsa, boshqalari PR orqali ishlasa, natijada nomuvofiqlik va xatolar yuzaga keladi.
✅ To'g'ri: loyiha boshida workflow'ni aniq belgilab, uni loyihaning `CONTRIBUTING.md` faylida hujjatlashtirish, va GitHub'da branch himoya qoidalari (branch protection rules) orqali (masalan, "to'g'ridan-to'g'ri `main`ga push taqiqlangan, faqat PR orqali") texnik jihatdan mustahkamlash tavsiya etiladi.

**Xato 3:** `main` branch'ni "har doim ishlaydigan" deb hisoblab, uni sinovdan o'tkazmasdan darhol production'ga deploy qilish (GitHub Flow'da CI bosqichini o'tkazib yuborish).
❌ Agar avtomatik testlar bo'lmasa, `main`ga qo'shilgan xato kod to'g'ridan-to'g'ri foydalanuvchilarga yetib boradi.
✅ To'g'ri: GitHub Flow — CI (avtomatik test) bosqichisiz to'liq ishlamaydi; PR review va avtomatik testlar (GitHub Actions) — `main`ning "har doim tayyor" holatini ta'minlaydigan asosiy vosita hisoblanadi.

## Mashq/topshiriq

**(Oson)** GitHub Flow'ning yetti bosqichini o'z so'zlaringiz bilan tartib bilan yozib chiqing.

**(O'rtacha)** Git Flow'dagi besh xil branch turini (`main`, `develop`, `feature/*`, `release/*`, `hotfix/*`) va ularning har biri qachon ishlatilishini tushuntiring.

**(Qiyin)** Farazan, siz 3 kishilik jamoada, haftada bir necha marta production'ga deploy qiladigan veb-ilova ustida ishlayapsiz. Qaysi workflow'ni (GitHub Flow, Git Flow yoki Trunk-Based Development) tanlagan bo'lardingiz va nima uchun? Keyin, agar bu — mobil ilova bo'lib, App Store orqali oyiga bir marta versiyalangan chiqarilsa, javobingiz qanday o'zgarishini tushuntiring.

<details>
<summary>Javoblarni ko'rish</summary>

1. main tayyor holatda → branch ochish → commit va push → PR ochish → review/CI → merge → deploy.
2. `main` — faqat rasmiy chiqarilgan versiyalar; `develop` — keyingi release uchun birlashtirilayotgan kod; `feature/*` — yangi funksiyalar, `develop`dan ochilib, `develop`ga qaytadi; `release/*` — chiqarishga tayyorgarlik (versiya, oxirgi tuzatish); `hotfix/*` — production'dagi shoshilinch xatoni to'g'ridan-to'g'ri `main`dan tuzatish uchun.
3. Tez-tez deploy qilinadigan veb-ilova uchun — GitHub Flow (yoki Trunk-Based) mos, chunki u tez, uzluksiz deploy siklini qo'llab-quvvatlaydi, ortiqcha branch murakkabligisiz. Agar bu — oyiga bir marta versiyalangan chiqariladigan mobil ilova bo'lsa — Git Flow ko'proq mos keladi, chunki u aniq "release 2.4.0" kabi versiyalarni tayyorlash, sinovdan o'tkazish va alohida `hotfix` orqali shoshilinch tuzatishlarni boshqarish uchun maxsus mo'ljallangan.

</details>

## Qisqacha xulosa

Jamoaviy ishlashda "workflow" — branch'lar va release'lar bilan qanday ishlash kerakligi haqidagi kelishilgan qoidalar to'plami; **GitHub Flow** — sodda, `main` doimo tayyor holatda bo'lgan, tez-tez deploy qilinadigan loyihalar uchun mos zamonaviy yondashuv, **Git Flow** esa — `develop`, `release/*`, `hotfix/*` kabi qo'shimcha branch turlariga ega, aniq versiyalangan chiqarishlarni talab qiladigan yirik loyihalar uchun mo'ljallangan an'anaviy model. To'g'ri workflow tanlash — loyiha hajmi, deploy chastotasi va jamoa tarkibiga bog'liq bo'lib, bu tanlov keyingi ikki darsda ko'riladigan code review va Issues/Projects amaliyotlari bilan chambarchas bog'liq.
