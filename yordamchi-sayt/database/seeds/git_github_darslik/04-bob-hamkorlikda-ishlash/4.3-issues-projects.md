# GitHub Issues va Projects

## Bu darsda nimalarni o'rganasiz

- Issues nima ekanini va uni qanday ishlatishni o'rganasiz
- Label, Milestone va Assignee tushunchalarini bilasiz
- Issue'ni commit/PR bilan avtomatik bog'lashni o'rganasiz
- GitHub Projects orqali vazifalarni boshqarishni tushunasiz

## Nazariy qism

### Issues nima

**Issues** — GitHub'ning ichki vazifa/xato kuzatish (task/bug tracking) tizimi. Har bir Issue — bitta aniq muammo, so'rov yoki vazifani ifodalaydi: xato haqida xabar, yangi funksiya taklifi, yoki bajarilishi kerak bo'lgan ish.

Issue yaratish — repository sahifasida **Issues → New issue** orqali amalga oshiriladi. Har bir Issue quyidagilarga ega bo'ladi:

| Element | Tavsifi |
|---|---|
| Sarlavha va tavsif | Muammo yoki vazifaning tafsiloti (Markdown formatida yozish mumkin) |
| Raqam (`#42`) | Har bir Issue'ga avtomatik beriladigan noyob identifikator |
| Label | Kategoriya belgisi (masalan, `bug`, `enhancement`, `documentation`) |
| Assignee | Kim bu ish ustida ishlashi belgilanadi |
| Milestone | Qaysi release/bosqichga tegishli ekani |
| Comments | Muhokama joyi |

### Yaxshi Issue qanday yoziladi

Xato haqida xabar (bug report) uchun yaxshi Issue odatda quyidagilarni o'z ichiga oladi:

```markdown
## Muammo tavsifi
Login formasida, email maydoniga katta harflar bilan yozilsa, xato chiqadi.

## Qayta ishlab chiqarish qadamlari
1. /login sahifasiga o'ting
2. Email maydoniga "TEST@GMAIL.COM" kiriting
3. "Kirish" tugmasini bosing

## Kutilgan natija
Foydalanuvchi tizimga kirishi kerak (email katta-kichik harfga sezgir bo'lmasligi kerak)

## Haqiqiy natija
"Foydalanuvchi topilmadi" xatosi chiqadi

## Muhit
- Brauzer: Chrome 128
- OS: Ubuntu 24.04
```

Ko'p loyihalar — **Issue shablonlari** (`.github/ISSUE_TEMPLATE/`) orqali, ushbu tuzilmani oldindan tayyorlab qo'yadi, foydalanuvchi shunchaki maydonlarni to'ldiradi.

### Label — kategoriyalash tizimi

Label'lar — Issue'larni tez saralash va filtrlash imkonini beradi. Standart GitHub label'lari:

| Label | Ma'nosi |
|---|---|
| `bug` | Dasturdagi xato |
| `enhancement` | Yangi funksiya so'rovi |
| `documentation` | Hujjatlarga oid |
| `good first issue` | Yangi hissa qo'shuvchilar uchun mos, sodda vazifa |
| `help wanted` | Jamoa yordam so'rayapti |
| `wontfix` | Ataylab hal qilinmaydi deb qaror qilingan |

### Issue'ni commit yoki PR bilan bog'lash

GitHub — commit izohlarida yoki PR tavsifida maxsus kalit so'zlar orqali, Issue'larni **avtomatik yopish** imkonini beradi:

```bash
git commit -m "Login email katta-kichik harf xatosini tuzatish

Closes #42"
```

| Kalit so'z | Ta'siri |
|---|---|
| `Closes #42`, `Fixes #42`, `Resolves #42` | PR merge qilinganda, Issue #42 **avtomatik yopiladi** |
| `Related to #42` | Bog'liqlik ko'rsatiladi, lekin avtomatik yopilmaydi |

Bu — qo'lda Issue'larni yopib yurishning o'rnini bosadi va loyiha tarixida "qaysi commit qaysi muammoni hal qilgani"ni aniq izlash imkonini beradi.

### GitHub Projects — vazifalarni vizual boshqarish

**GitHub Projects** — Issues va PR'larni **Kanban-uslubidagi taxta** (board) ko'rinishida tashkil etish vositasi. Odatiy ustunlar:

```
Todo  →  In Progress  →  In Review  →  Done
```

Har bir Issue yoki PR — kartochka sifatida, ustunlar orasida (ish holati o'zgarishi bilan) sudralib ko'chiriladi. Bu — jamoaga, loyihaning umumiy holatini **bir qarashda** ko'rish imkonini beradi.

GitHub Projects — avtomatlashtirish qoidalarini ham qo'llab-quvvatlaydi, masalan: "PR merge qilinganda, bog'liq Issue avtomatik 'Done' ustuniga ko'chirilsin".

### Milestone — bosqichlarni belgilash

**Milestone** — bir nechta Issue/PR'ni, umumiy maqsad yoki release atrofida guruhlash usuli (masalan, "v2.0 chiqarilishi", muddati bilan). Milestone sahifasida, shu maqsadga tegishli barcha vazifalarning necha foizi bajarilgani avtomatik ko'rsatiladi.

### GitHub CLI orqali Issue bilan ishlash

```bash
gh issue create --title "Login xatosi" --body "Email katta harf bilan ishlamayapti"
gh issue list
gh issue view 42
gh issue close 42
```

## Amaliy misol

To'liq jarayon — Issue ochishdan, uni PR orqali yopishgacha:

```bash
# 1. Xato topildi - Issue ochamiz
gh issue create \
  --title "Parol tiklash email yuborilmayapti" \
  --body "## Muammo
Foydalanuvchi 'parolni unutdim' tugmasini bosganda, email kelmayapti.

## Qadamlar
1. /parol-tiklash sahifasiga o'tish
2. Email kiritish
3. Yuborish tugmasini bosish

## Kutilgan natija
Email yuborilishi kerak
## Haqiqiy natija
Hech qanday xabar chiqmaydi, email ham kelmaydi" \
  --label bug

# GitHub natija: Issue #58 yaratildi

# 2. Vazifa ustida ishlash uchun branch ochamiz
git switch -c fix/parol-tiklash-email

# 3. Muammoni tuzatamiz
echo "# tuzatilgan email yuborish kodi" >> email_service.py
git add email_service.py

# 4. Commit - Issue'ga bog'lab
git commit -m "Parol tiklash email yuborish xatosini tuzatish

Closes #58"

git push -u origin fix/parol-tiklash-email

# 5. PR yaratamiz
gh pr create --title "Parol tiklash emailini tuzatish" --body "Closes #58"

# 6. PR review'dan o'tib, merge qilinganda,
#    Issue #58 GitHub tomonidan AVTOMATIK yopiladi
```

## Keng tarqalgan xatolar

**Xato 1:** xato haqida Issue'ni juda qisqa, tafsilotsiz yozish (masalan, faqat "ishlamayapti" deb).
❌ Bu — boshqa dasturchi (yoki hatto siz, bir necha kundan keyin) muammoni qayta ishlab chiqarishga (reproduce qilishga) va tushunishga qiynaladi.
✅ To'g'ri: har doim "qayta ishlab chiqarish qadamlari", "kutilgan" va "haqiqiy" natijalarni aniq yozing — bu review va tuzatish jarayonini sezilarli tezlashtiradi.

**Xato 2:** `Closes #42` kabi kalit so'zlarni faqat PR tavsifida emas, balki oddiy izohda ishlatib, keyin Issue avtomatik yopilmasligidan hayron bo'lish.
❌ Avtomatik yopish faqat, ushbu kalit so'z **default branch'ga qo'shiladigan commit yoki merge qilinadigan PR tavsifida** bo'lgandagina ishlaydi.
✅ To'g'ri: `Closes #42` iborasini yo commit izohida, yo PR tavsifida (`--body` maydonida) ishlating, va u faqat PR asosiy (`main`) branch'ga merge qilingandan keyin amalga oshishini yodda tuting.

**Xato 3:** ko'plab Issues to'planib, ularni label yoki Project taxtasi orqali tashkil qilmasdan, tartibsiz holatda qoldirish.
❌ Vaqt o'tishi bilan, qaysi Issue muhim, qaysi biri hal qilingan yoki eskirgan ekanini aniqlash qiyinlashadi.
✅ To'g'ri: har bir Issue'ga tegishli label qo'shing, muhim vazifalarni Milestone'larga bog'lang, va GitHub Projects taxtasi orqali umumiy holatni doimiy kuzatib boring.

## Mashq/topshiriq

**(Oson)** O'z repository'ingizda (yoki mashq uchun) yangi Issue yarating, unga `bug` yoki `enhancement` label qo'shing.

**(O'rtacha)** Yangi branch ochib, kichik o'zgartirish kiritib, commit izohida `Closes #<Issue-raqami>` iborasi bilan bog'lang, so'ng PR yaratib, uni merge qiling (yoki simulyatsiya qiling) va Issue avtomatik yopilishini kuzating.

**(Qiyin)** GitHub Projects'da yangi taxta (board) yarating, "Todo", "In Progress", "Done" ustunlarini sozlang, va kamida 3 ta Issue'ni turli ustunlarga joylashtiring. Milestone tushunchasi Project taxtasidan nima bilan farqlanishini tushuntirib bering.

## Qisqacha xulosa

GitHub Issues — xato, vazifa va funksiya so'rovlarini kuzatish uchun ichki tizim bo'lib, label, assignee va milestone orqali tashkil etiladi; commit yoki PR tavsifida `Closes #<raqam>` kabi kalit so'zlar ishlatilsa, Issue merge qilingandan so'ng **avtomatik yopiladi** — bu kod o'zgarishlarini muammolar bilan aniq bog'lab turadi. GitHub Projects esa — Issues va PR'larni Kanban-uslubidagi vizual taxtada tashkil etish orqali, jamoaga loyihaning umumiy holatini bir qarashda ko'rish imkonini beradi.
