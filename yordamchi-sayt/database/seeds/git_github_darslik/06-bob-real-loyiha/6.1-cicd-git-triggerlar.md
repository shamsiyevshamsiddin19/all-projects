# CI/CD va Git trigger'lari (GitHub Actions bilan)

## Bu darsda nimalarni o'rganasiz

- Git voqealari (push, PR, tag) CI/CD jarayonlarini qanday ishga tushirishini tushunasiz
- GitHub Actions workflow faylining Git bilan bog'liq qismlarini o'rganasiz
- Branch va tag asosida turli xil avtomatlashtirishni sozlashni bilasiz
- Docker darsligi bilan bog'liq holda, to'liq CI/CD zanjirini tushunasiz

## Nazariy qism

### CI/CD va Git — bog'liqlik

**CI/CD** (Continuous Integration / Continuous Deployment) — kod o'zgarishlari avtomatik tarzda tekshirilishi (test), qurilishi (build) va joylashtirilishi (deploy) jarayoni. Bu — Docker darsligining 6.3-darsida GitHub Actions orqali batafsil ko'rilgan edi. Ushbu darsda biz, aynan **Git voqealari** (push, PR, tag) bu jarayonlarni qanday "ishga tushirishi" (trigger qilishi)ga chuqurroq e'tibor qaratamiz.

Muhim tushuncha: CI/CD tizimlari (GitHub Actions, va boshqalar) — Git'ning o'zi emas, balki **Git voqealariga obuna bo'lgan tashqi tizimlar**. Git — shunchaki "nimadir sodir bo'ldi" (push, PR ochildi) degan signalni beradi, CI/CD tizimi esa shu signalga javoban harakat qiladi.

### GitHub Actions workflow'ining `on:` bo'limi

Har bir GitHub Actions workflow fayli (`.github/workflows/*.yml`) — `on:` kaliti orqali, **qaysi Git voqeasi** uni ishga tushirishini belgilaydi:

```yaml
name: CI Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
```

Bu — `main` branch'ga push qilinganda **yoki** `main`ga yo'naltirilgan Pull Request ochilganda/yangilanganda, workflow avtomatik ishga tushishini bildiradi.

### Turli Git voqealari uchun turli trigger'lar

| Trigger | Qачон ishga tushadi |
|---|---|
| `push` | Muayyan branch'ga (yoki barcha branch'larga) commit push qilinganda |
| `pull_request` | PR ochilganda, yangilanganda yoki qayta ochilganda |
| `push` + `tags` | Muayyan naqshga mos tag push qilinganda (5.3-darsda ko'rilgan) |
| `release` | GitHub Release yaratilganda/nashr qilinganda |
| `workflow_dispatch` | Qo'lda, GitHub interfeysi orqali ishga tushirilganda |
| `schedule` | Belgilangan vaqt jadvali bo'yicha (cron sintaksisi) |

### Branch'ga qarab turli xil avtomatlashtirish

Amaliy loyihalarda, ko'pincha turli branch'lar uchun **turli** ishlar bajariladi:

```yaml
name: To'liq CI/CD zanjiri

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Testlarni ishga tushirish
        run: pytest

  deploy-staging:
    needs: test
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest
    steps:
      - name: Staging serverga deploy qilish
        run: echo "Staging'ga deploy qilinmoqda..."

  deploy-production:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - name: Production serverga deploy qilish
        run: echo "Production'ga deploy qilinmoqda..."
```

Bu misolda: **har qanday** push/PR uchun testlar ishga tushadi, lekin real deploy — faqat `develop` (staging muhitga) yoki `main` (production muhitga) branch'iga push qilinganda, **va faqat testlar muvaffaqiyatli o'tgandan keyin** (`needs: test`) sodir bo'ladi.

### Tag asosida release avtomatlashtirish

5.3-darsda ko'rilganidek, tag'lar ko'pincha rasmiy release jarayonini ishga tushiradi:

```yaml
on:
  push:
    tags:
      - 'v*.*.*'

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Docker image qurish va yuklash
        run: |
          docker build -t foydalanuvchi/dastur:${{ github.ref_name }} .
          docker push foydalanuvchi/dastur:${{ github.ref_name }}
```

`github.ref_name` — bu yerda push qilingan tag nomini (masalan, `v1.2.0`) avtomatik oladi, va shu nom bilan Docker image tegi qo'yiladi (Docker darsligining Docker Hub bilan ishlash darsiga bevosita bog'liq).

### GitHub Flow + CI/CD — to'liq zanjir

4.1-darsda ko'rilgan GitHter Flow bilan birlashtirilganda, to'liq avtomatlashtirilgan zanjir quyidagicha ko'rinadi:

```
1. Dasturchi feature branch ochadi, ishlaydi, push qiladi
   → CI: testlar avtomatik ishga tushadi (pull_request trigger)
2. PR ochiladi, review qilinadi, testlar "yashil" bo'lgach
3. main'ga merge qilinadi
   → CI: main uchun testlar yana ishga tushadi (push trigger)
4. Testlar o'tgach, avtomatik deploy sodir bo'ladi
5. Muhim versiya tayyor bo'lganda, tag qo'yiladi (v1.2.0)
   → CI: Docker image quriladi va Docker Hub'ga yuklanadi, GitHub Release yaratiladi
```

Bu — zamonaviy dasturiy ta'minot yetkazib berishning (software delivery) asosiy avtomatlashtirilgan sikli hisoblanadi.

### Branch protection + CI status checks — bog'liqlik

4.2-darsda ko'rilgan **Require status checks to pass** qoidasi — aynan shu CI workflow'lariga bog'liq: agar `test` job muvaffaqiyatsiz tugasa, GitHub avtomatik ravishda PR'ni **merge qilishga yo'l qo'ymaydi** (agar shunday sozlangan bo'lsa). Bu — Git (branch protection) va CI/CD (GitHub Actions) tizimlarining birgalikda ishlashiga yaqqol misol.

## Amaliy misol

To'liq, amaliy CI/CD workflow fayli — Python/Django loyihasi uchun (3-bob va Python darsligiga bog'liq holda):

```yaml
# .github/workflows/ci-cd.yml
name: Django CI/CD

on:
  push:
    branches: [main]
    tags: ['v*']
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Python o'rnatish
        uses: actions/setup-python@v5
        with:
          python-version: '3.13'

      - name: Kutubxonalarni o'rnatish
        run: pip install -r requirements.txt

      - name: Testlarni ishga tushirish
        run: pytest

  build-and-push:
    needs: test
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Docker Hub'ga kirish
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Image qurish va yuklash
        run: |
          docker build -t foydalanuvchi/django-app:${{ github.ref_name }} .
          docker push foydalanuvchi/django-app:${{ github.ref_name }}
```

Ushbu fayl — loyiha ildizidagi `.github/workflows/` papkasiga joylashtiriladi, so'ng oddiy `git add`, `git commit`, `git push` orqali GitHub'ga yuboriladi — shu paytdan boshlab, u avtomatik ishlay boshlaydi.

```bash
git add .github/workflows/ci-cd.yml
git commit -m "CI/CD workflow qo'shildi: test + tag asosida Docker build"
git push origin main

# Keyinroq, versiya tayyor bo'lganda
git tag -a v1.0.0 -m "Birinchi barqaror versiya"
git push origin v1.0.0
# ^ shu buyruq - avtomatik ravishda build-and-push job'ini ishga tushiradi
```

## Keng tarqalgan xatolar

**Xato 1:** `on:` bo'limida `branches` cheklovisiz, workflow'ni **har qanday** branch'ga push uchun ishga tushirish.
❌ Bu — har bir kichik, eksperimental feature branch uchun ham to'liq test/build/deploy zanjirini ishga tushiradi, resurslarni behuda sarflaydi va CI navbatini keraksiz to'ldiradi.
✅ To'g'ri: `on.push.branches` orqali, faqat kerakli branch'larni (masalan, faqat `main`, `develop`) ko'rsating; feature branch'lar uchun odatda faqat `pull_request` trigger'i yetarli.

**Xato 2:** Docker Hub parolini yoki API kalitlarini, workflow faylida **ochiq matn** sifatida yozish.
❌ Bu — 1.2-darsda (`.gitignore`) ko'rilgan xavfsizlik muammosining CI/CD kontekstidagi ko'rinishi: maxfiy ma'lumot ochiq repository'da hammaga ko'rinadi.
✅ To'g'ri: har doim GitHub'ning **Secrets** mexanizmidan (`Settings → Secrets and variables → Actions`) foydalaning, workflow faylida esa faqat `${{ secrets.NOM }}` ko'rinishida murojaat qiling — bu, Docker darsligining 6.1-darsida ko'rilgan xavfsizlik tamoyillariga to'g'ridan-to'g'ri mos keladi.

**Xato 3:** `needs: test` kabi bog'liqlikni belgilamasdan, deploy job'ini test job'idan **mustaqil** ishga tushirish.
❌ Bu — testlar muvaffaqiyatsiz tugagan taqdirda ham, xato kod avtomatik ravishda production'ga deploy qilinishiga olib kelishi mumkin.
✅ To'g'ri: deploy job'lari har doim `needs: test` (yoki tegishli test job nomi) orqali, testlar muvaffaqiyatli yakunlangandan **keyingina** ishga tushishini ta'minlang.

## Mashq/topshiriq

**(Oson)** GitHub Actions workflow faylida, faqat `main` branch'ga push qilinganda ishga tushadigan, oddiy "Hello World" chop etuvchi job yozing.

**(O'rtacha)** Yuqoridagi workflow'ni kengaytirib, `pull_request` trigger'ini ham qo'shing, va `test` nomli job faqat testlarni (`pytest` chaqiruvi) ishga tushirishini ta'minlang.

**(Qiyin)** To'liq ikki bosqichli workflow yozing: birinchi job — testlarni ishga tushiradi; ikkinchi job — faqat tag (`v*` naqshiga mos) push qilinganda **va** birinchi job muvaffaqiyatli yakunlangandan keyin, Docker image qurib, Docker Hub'ga yuklaydi (maxfiy ma'lumotlarni GitHub Secrets orqali ishlatgan holda). Nima uchun `needs:` va `if: startsWith(...)` shartlarining ikkalasi ham zarurligini tushuntiring.

## Qisqacha xulosa

CI/CD tizimlari (GitHub Actions) — Git voqealariga (push, pull_request, tag push) obuna bo'lib, ularga avtomatik javob beradi: `on:` bo'limi qaysi voqea workflow'ni ishga tushirishini, `branches`/`tags` cheklovlari esa qaysi branch yoki tag naqshi uchun ishlashini belgilaydi. Amaliyotda, testlar har bir push/PR'da ishga tushiriladi, og'ir deploy jarayonlari esa odatda faqat `main`/`develop`ga push yoki rasmiy tag qo'yilganda amalga oshiriladi (`needs:` va shart operatorlari orqali boshqariladi) — bu, Git'ning branch/tag mexanizmini, Docker darsligida ko'rilgan konteynerizatsiya va deploy jarayonlari bilan to'liq avtomatlashtirilgan bitta zanjirga bog'laydi.
