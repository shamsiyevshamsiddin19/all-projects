# Konteyner ichiga kirish, loglar va monitoring

## Bu darsda nimalarni o'rganasiz

- `docker logs` orqali konteyner chiqishini (output) kuzata olasiz
- `docker exec` orqali ishlayotgan konteyner ichida diagnostika o'tkaza olasiz
- `docker inspect` va `docker stats` yordamida konteyner haqida batafsil ma'lumot ola olasiz
- Konteyner nima uchun to'xtab qolganini (crash) aniqlash usullarini bilasiz

## Nazariy qism

### `docker logs` — konteyner "chiqishi"ni ko'rish

Har bir konteyner ichida ishlayotgan dastur odatda konsolga (`stdout`/`stderr`) xabar chiqaradi — Docker bu xabarlarni avtomatik "log" sifatida saqlaydi:

```bash
docker logs mening_veb_server
```

Foydali bayroqlar:

```bash
docker logs -f mening_veb_server        # -f (follow) — real vaqtda, yangi loglar chiqishi bilan kuzatish
docker logs --tail 50 mening_veb_server   # faqat OXIRGI 50 qatorni ko'rsatish
docker logs --since 10m mening_veb_server  # oxirgi 10 daqiqadagi loglarni ko'rsatish
docker logs -t mening_veb_server            # har bir log qatoriga VAQT BELGISI (timestamp) qo'shish
```

`-f` bayrog'i — real vaqtda log oqimini kuzatish uchun ayniqsa foydali (masalan, Django yoki Aiogram bot konteynerida real vaqtda nima sodir bo'layotganini ko'rish uchun, avvalgi Django darsligidagi `runserver`/`runbot` loglariga o'xshash).

### `docker exec` — ishlayotgan konteyner ichida diagnostika

1.1-darsda ko'rgan `docker exec`ni endi **muammolarni aniqlash** (troubleshooting) kontekstida ko'ramiz:

```bash
docker exec -it mening_konteyner bash        # interaktiv terminal ochish
docker exec mening_konteyner ps aux            # konteyner ichida qanday jarayonlar ishlayotganini ko'rish
docker exec mening_konteyner env                # konteyner ichidagi muhit o'zgaruvchilarini ko'rish
docker exec mening_konteyner cat /etc/hosts      # konfiguratsiya faylini tekshirish
```

> 📌 **Ba'zi minimalistik image'larda (`alpine`, `slim`) `bash` mavjud emas.** Bunday hollarda `sh` ishlatiladi:
```bash
docker exec -it mening_konteyner sh
```

### `docker inspect` — konteyner haqida to'liq texnik ma'lumot

```bash
docker inspect mening_veb_server
```

Bu buyruq — konteyner haqida **juda batafsil** JSON formatidagi ma'lumotni chiqaradi (IP manzil, ulangan volume'lar, muhit o'zgaruvchilari, tarmoq sozlamalari va h.k.). Odatda butun natijani emas, faqat kerakli qismini ko'rish uchun `--format` (yoki `grep`) bilan birga ishlatiladi:

```bash
docker inspect --format='{{.NetworkSettings.IPAddress}}' mening_veb_server    # faqat IP manzilni chiqarish
docker inspect --format='{{.State.Status}}' mening_veb_server                   # faqat holatni chiqarish
```

### `docker stats` — resurs sarfini real vaqtda kuzatish

```bash
docker stats
```

Natija (real vaqtda yangilanib turadi):

```
CONTAINER ID   NAME                CPU %     MEM USAGE / LIMIT     MEM %     NET I/O
a1b2c3d4e5f6   mening_veb_server   0.05%     12.5MiB / 1.943GiB     0.63%     1.2kB / 0B
```

Bu — qaysi konteyner qancha CPU va xotira ishlatayotganini kuzatish, resurs "sizib chiqishi" (memory leak) yoki g'ayritabiiy yuklamani aniqlashda foydali.

### Konteyner nega to'xtab qoldi — diagnostika ketma-ketligi

Konteyner kutilmaganda to'xtab qolganda (yoki umuman ishga tushmasa), quyidagi tekshiruv ketma-ketligi tavsiya etiladi:

```bash
# 1. Holatini tekshirish
docker ps -a

# 2. Chiqish kodini (exit code) ko'rish
docker inspect --format='{{.State.ExitCode}}' mening_konteyner

# 3. Eng muhimi — loglarni o'qish (odatda xato sababi shu yerda ko'rinadi)
docker logs mening_konteyner
```

| Exit kod | Ma'nosi |
|---|---|
| `0` | Muvaffaqiyatli tugadi (xato yo'q) |
| `1` | Umumiy xato (dastur ichida istisno/xato yuz berdi) |
| `137` | Konteyner **majburan o'chirildi** (odatda xotira yetishmasligi — `OOM killed`, yoki `docker kill`) |
| `143` | `SIGTERM` orqali "yumshoq" to'xtatildi (`docker stop`) |

### `docker top` — konteyner ichidagi jarayonlarni host'dan ko'rish

```bash
docker top mening_veb_server
```

`docker exec ... ps aux`ga o'xshaydi, lekin konteyner ichiga "kirmasdan", to'g'ridan-to'g'ri host'dan konteyner ichidagi jarayonlar ro'yxatini ko'rsatadi.

## Amaliy misol

Muvaffaqiyatsiz konteynerni diagnostika qilish — to'liq stsenariy:

```bash
# 1. Ataylab xato beradigan konteyner ishga tushiramiz (mavjud bo'lmagan buyruq bilan)
docker run --name xatoli_konteyner python:3.13-slim python3 -c "import mavjud_bolmagan_modul"

# 2. Holatini tekshiramiz
docker ps -a
# STATUS ustunida "Exited (1)" kabi natija ko'rinadi

# 3. Chiqish kodini aniqlaymiz
docker inspect --format='{{.State.ExitCode}}' xatoli_konteyner
# 1

# 4. ENG MUHIMI — loglarni o'qib, sababni topamiz
docker logs xatoli_konteyner
# Traceback (most recent call last):
#   File "<string>", line 1, in <module>
# ModuleNotFoundError: No module named 'mavjud_bolmagan_modul'

# 5. Muammoni tuzatib qayta sinaymiz (to'g'ri modul bilan)
docker rm xatoli_konteyner
docker run --rm python:3.13-slim python3 -c "import json; print('Modul topildi!')"
# Modul topildi!
```

Bu misol — 5.1-darsdagi (Python kursidan) istisnolarni boshqarish tushunchasini Docker kontekstida qo'llaydi: xatoning **haqiqiy sababi** deyarli har doim `docker logs` orqali topiladi, chunki konteyner ichidagi dastur o'z xatolarini standart chiqishga (`stdout`/`stderr`) yozadi, va Docker buni "eslab qoladi".

## Keng tarqalgan xatolar

**Xato 1:** konteyner ishlamay qolganda darhol uni o'chirib, sababini tekshirmaslik.
❌ `docker rm -f xatoli_konteyner` — muammoni "ko'rmaslikka" urinish, lekin sabab hal qilinmagani uchun xato **qayta** takrorlanadi.
✅ To'g'ri: har doim avval `docker logs`ni o'qing — bu deyarli har doim aniq sababni ko'rsatadi, o'chirish esa ma'lumotni yo'qotadi.

**Xato 2:** `docker logs`ni `-f` bilan cheksiz kuzatib, terminalni "band" qilib qo'yish va uni to'xtatishni bilmaslik.
❌ `docker logs -f ...` ishga tushirilgach, terminal navbatdagi buyruqni kutmaydi (loglar oqimi tugamaguncha).
✅ To'g'ri: `Ctrl+C` bosib, log kuzatishni to'xtatish mumkin — bu **konteynerni to'xtatmaydi**, faqat log ko'rsatishni tugatadi (bu — muhim farq, chunki ba'zi boshlovchilar `Ctrl+C` konteynerni ham o'chiradi deb o'ylashadi).

**Xato 3:** `docker exec` orqali kirib, konteyner ichida qo'lda o'zgartirish kiritib, "muammo hal bo'ldi" deb o'ylash.
❌ `docker exec -it konteyner bash` orqali kirib, ichida faylni qo'lda tahrirlash — bu **vaqtinchalik** yechim, chunki konteyner o'chirilsa yoki qayta yaratilsa, bu o'zgarish **yo'qoladi** (konteyner — o'zgarmas image'dan yaratilgan, unga qilingan o'zgarishlar image'ning o'ziga ta'sir qilmaydi).
✅ To'g'ri: doimiy o'zgarishlar har doim **Dockerfile** (2-bobda) orqali, image qurish bosqichida qilinishi kerak — bu image qayta ishlatilganda ham o'zgarish saqlanishini kafolatlaydi.

## Mashq/topshiriq

**(Oson)** `nginx` konteynerini ishga tushiring, `docker logs -f` bilan real vaqtda loglarni kuzating, boshqa terminalda (yoki brauzerda) unga bir necha marta so'rov yuboring (`curl localhost:8080`) va loglarda yangi qatorlar paydo bo'lishini kuzating.

**(O'rtacha)** `docker stats` buyrug'ini ishga tushirib, kamida ikkita konteynerning (masalan, `nginx` va `postgres`) CPU va xotira sarfini solishtiring, so'ng natijani izohlab bering.

**(Qiyin)** Ataylab xato beradigan Python konteyner ishga tushiring (masalan, `1/0` bo'linish xatosi bilan: `docker run --name xato_test python:3.13-slim python3 -c "1/0"`), so'ng to'liq diagnostika ketma-ketligini (`docker ps -a` → `docker inspect --format='{{.State.ExitCode}}'` → `docker logs`) bajarib, chiqish kodi va xato sababini yozib qoldiring.

## Qisqacha xulosa

`docker logs` (ayniqsa `-f` bayrog'i bilan) — konteyner ichidagi dastur chiqishini kuzatishning asosiy vositasi bo'lib, muammolarni diagnostika qilishda **birinchi** murojaat qilinadigan joy; `docker exec` — ishlayotgan konteyner ichida buyruq bajarish yoki interaktiv tekshirish uchun, `docker inspect` va `docker stats` esa konteyner haqida texnik tafsilotlar va resurs sarfini ko'rsatadi; muhim tamoyil — konteyner ichida qo'lda qilingan o'zgarishlar vaqtinchalik bo'lib, doimiy o'zgarishlar har doim Dockerfile orqali (keyingi bobda ko'riladi) amalga oshirilishi kerak.
