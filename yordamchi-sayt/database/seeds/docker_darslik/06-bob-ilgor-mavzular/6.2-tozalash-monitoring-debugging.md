# Tozalash, monitoring va debugging buyruqlari

## Bu darsda nimalarni o'rganasiz

- Disk joyini egallab qolgan eskirgan Docker resurslarini tozalay olasiz
- `docker system df`/`prune` buyruqlari orqali resurs sarfini boshqara olasiz
- Konteyner ichiga kirmasdan muammolarni tashqaridan diagnostika qila olasiz
- Docker bilan bog'liq eng keng tarqalgan production muammolarini hal qila olasiz

## Nazariy qism

### Muammo — Docker vaqt o'tishi bilan ko'p disk joyini egallaydi

Har safar `docker build` bajarilganda, eski qatlamlar (2.2-darsda ko'rgan tushuncha) ba'zan **ishlatilmay** qoladi ("dangling" image'lar). Har safar konteyner yaratilib, o'chirilganda, ba'zi izlar qolishi mumkin. Vaqt o'tishi bilan bu — sezilarli disk joyini egallashi mumkin.

### `docker system df` — umumiy holatni ko'rish

```bash
docker system df
```

Natija:

```
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          15        5         4.2GB     2.8GB (66%)
Containers      8         3         120MB     45MB (37%)
Local Volumes   6         4         850MB     150MB (17%)
Build Cache     42        0         1.1GB     1.1GB (100%)
```

`RECLAIMABLE` ustuni — qancha joy **tozalash orqali qaytarib olinishi mumkinligini** ko'rsatadi. Batafsil ko'rish uchun:

```bash
docker system df -v    # har bir image/konteyner/volume alohida ko'rsatiladi
```

### Tozalash buyruqlari — bosqichma-bosqich, ehtiyotkorlik bilan

```bash
# 1. Faqat TO'XTATILGAN konteynerlarni o'chirish
docker container prune

# 2. Faqat ISHLATILMAYOTGAN (hech qanday konteyner bilan bog'lanmagan) image'larni o'chirish
docker image prune

# 3. FAOL bo'lmagan (istalgan konteyner ishlatmayotgan) BARCHA image'larni o'chirish (ehtiyotkorlik!)
docker image prune -a

# 4. Ishlatilmayotgan tarmoqlarni o'chirish
docker network prune

# 5. Ishlatilmayotgan volume'larni o'chirish (ENG XAVFLI — ma'lumot yo'qolishi mumkin!)
docker volume prune

# 6. HAMMASINI birdaniga tozalash (konteyner, image, tarmoq, build cache)
docker system prune

# 7. + VOLUME'LARNI HAM (juda ehtiyotkorlik bilan!)
docker system prune -a --volumes
```

> ⚠️ **`docker system prune -a --volumes` — eng kuchli, eng xavfli buyruq.** Bu **barcha** ishlatilmayotgan resurslarni, jumladan volume'lardagi ma'lumotlarni **butunlay va qaytarib bo'lmas tarzda** o'chiradi. Production serverida bu buyruqni ishlatishdan oldin, qaysi konteynerlar/volume'lar **hozir kerak** ekanini **ikki marta** tekshiring.

### Filtr bilan tanlab tozalash

```bash
# faqat 24 soatdan eskiroq narsalarni tozalash
docker image prune -a --filter "until=24h"

# faqat ma'lum belgi (label) bilan belgilangan resurslarni tozalash
docker container prune --filter "label=vaqtinchalik=true"
```

### Monitoring — `docker stats` (1.3-darsning davomi, chuqurroq)

```bash
docker stats --no-stream    # bir martalik "suratga olish" (real vaqtda yangilanmasdan)
docker stats mening_konteyner1 mening_konteyner2   # faqat ma'lum konteynerlar
```

### `docker events` — real vaqtda Docker hodisalarini kuzatish

```bash
docker events
```

Bu buyruq — kompyuteringizda **har qanday** Docker hodisasini (konteyner yaratildi, to'xtatildi, image qurildi va h.k.) real vaqtda ko'rsatadi. Bu ayniqsa "nima uchun konteyner kutilmaganda to'xtadi" kabi savollarga javob topishda foydali — masalan, boshqa jarayon (masalan, avtomatik xotira nazoratchisi) konteynerni o'chirib qo'yganini aniqlash mumkin.

### Production'da eng ko'p uchraydigan muammolar va ularni diagnostika qilish

**Muammo 1: konteyner doimo qayta ishga tushib turadi (restart loop)**

```bash
docker ps -a
# STATUS: "Restarting (1) 5 seconds ago"

docker logs mening_konteyner --tail 50
# Xato sababini bu yerda qidiring
```

Bu — odatda konteyner ichidagi dastur ishga tushish paytida darhol xato berib to'xtayotganini bildiradi (masalan, ma'lumotlar bazasiga ulanish muvaffaqiyatsiz, muhim muhit o'zgaruvchisi yo'q).

**Muammo 2: "out of memory" (OOM) — konteyner xotira yetishmasligi tufayli o'chirilgan**

```bash
docker inspect mening_konteyner --format='{{.State.OOMKilled}}'
# true
```

Agar bu `true` bo'lsa — konteynerga ajratilgan xotira chegarasidan (agar `mem_limit` sozlangan bo'lsa) yoki host'ning umumiy xotirasidan oshib ketilgan. Yechim — konteynerga ko'proq xotira ajratish, yoki dastur ichidagi xotira sarfini optimallashtirish (masalan, Python kursining 5.3-darsida ko'rgan generatorlar — katta ma'lumotlarni bir vaqtda xotiraga yuklamaslik).

**Muammo 3: disk joyi tugab qolgan**

```bash
df -h    # host kompyuterning umumiy disk holatini ko'rish (Docker'siz, oddiy Linux buyrug'i)
docker system df    # Docker qancha joy egallaganini ko'rish
```

Agar host diski to'lib qolgan bo'lsa, yangi konteyner yaratib bo'lmaydi va build muvaffaqiyatsiz tugaydi — bu holatda yuqorida ko'rgan `prune` buyruqlari yordam beradi.

**Muammo 4: konteynerlar orasida tarmoq aloqasi yo'q**

```bash
docker network inspect <tarmoq_nomi>
# "Containers" bo'limida ikkala konteyner ham RO'YXATDA bormi?
```

3.2-darsda ko'rganimizdek, agar konteynerlar bir xil maxsus tarmoqda bo'lmasa, ular bir-birini nom orqali topa olmaydi — bu tekshiruv muammoning aynan shu sababdan ekanini tasdiqlaydi yoki rad etadi.

### Konteyner ichiga "kirmasdan" tashqaridan diagnostika — `docker cp`

```bash
docker cp mening_konteyner:/app/log.txt ./log.txt    # konteynerdan HOST'ga fayl nusxalash
docker cp ./config.json mening_konteyner:/app/config.json   # HOST'dan konteynerga
```

`docker cp` — `docker exec` orqali konteyner ichiga kirmasdan, kerakli faylni tashqariga (yoki ichkariga) nusxalash imkonini beradi — bu konteyner ichida `bash`/`sh` umuman mavjud bo'lmagan (masalan, "distroless" — juda minimalistik) image'larda ham ishlaydi.

## Amaliy misol

To'liq "salomatlik tekshiruvi" (health check) va tozalash rutinasi — production serverida muntazam bajariladigan:

```bash
#!/bin/bash
# docker_tozalash.sh — haftalik tozalash skripti (Python kursining 3-bobidagi
# skriptlash tushunchasiga o'xshash, endi Bash'da)

echo "=== Docker holati (tozalashdan OLDIN) ==="
docker system df

echo ""
echo "=== To'xtatilgan konteynerlarni tozalash ==="
docker container prune -f

echo ""
echo "=== Ishlatilmayotgan image'larni tozalash (24 soatdan eski) ==="
docker image prune -af --filter "until=24h"

echo ""
echo "=== Ishlatilmayotgan tarmoqlarni tozalash ==="
docker network prune -f

echo ""
echo "=== Docker holati (tozalashdan KEYIN) ==="
docker system df
```

Diqqat qiling: `-f` (force) bayrog'i — tasdiqlash so'ralmasdan avtomatik bajarish uchun (bu skriptni cron orqali avtomatik ishga tushirish uchun zarur, chunki interaktiv tasdiqlash kutish kutilmagan holat). Bu skriptda **ataylab `docker volume prune` ishlatilmagan** — ma'lumotlar bazasi kabi doimiy ma'lumotlarni tozalash har doim **qo'lda, aniq maqsad bilan** bajarilishi kerak, avtomatik skriptga ishonib topshirilmasligi kerak.

Konteyner muammosini diagnostika qilish — to'liq ketma-ketlik:

```bash
# 1. Umumiy holatni ko'rish
docker compose ps

# 2. Muammoli xizmatni aniqlash (masalan, "bot" doimo qayta ishga tushmoqda)
docker compose logs --tail 100 bot

# 3. Xotira/CPU sarfini tekshirish
docker stats bot --no-stream

# 4. OOM (xotira yetishmasligi) ekanini tekshirish
docker inspect $(docker compose ps -q bot) --format='{{.State.OOMKilled}}'

# 5. Tarmoq ulanishini tekshirish
docker network inspect $(docker compose ps -q bot | xargs docker inspect --format='{{range .NetworkSettings.Networks}}{{.NetworkID}}{{end}}')
```

## Keng tarqalgan xatolar

**Xato 1:** `docker system prune -a --volumes`ni tekshirmasdan, "hammasini tozalash" niyatida ishlatish.
❌ Bu buyruq production serverida ishga tushirilsa, **hozirda ishlamayotgan, lekin muhim** volume'lar (masalan, vaqtincha to'xtatilgan xizmatning ma'lumotlar bazasi) ham o'chirilishi mumkin.
✅ To'g'ri: har doim avval `docker system df -v` bilan **nima o'chirilishini** ko'ring, va `--volumes` bayrog'ini faqat **aniq bilib**, kerak bo'lmagan ma'lumotlarni tozalamoqchi bo'lganda qo'shing.

**Xato 2:** konteyner muammosini "qayta ishga tushirish" bilan "hal qilish", asl sababni tekshirmasdan.
❌ `docker restart mening_konteyner` — agar muammo (masalan, muhim muhit o'zgaruvchisi yo'qligi) hal qilinmagan bo'lsa, konteyner **xuddi shu xato bilan** yana to'xtaydi, va bu tsikl (restart loop) davom etadi.
✅ To'g'ri: har doim avval `docker logs` orqali **asl sababni** toping (1.3-darsda ko'rgan diagnostika tamoyili), va faqat sabab tuzatilgandan keyin konteynerni qayta ishga tushiring.

**Xato 3:** disk joyi muammosini faqat Docker darajasida qidirish, host darajasini unutish.
❌ `docker system df` "hammasi yaxshi" ko'rsatsa-yu, baribir "no space left on device" xatosi chiqsa — muammo Docker'dan tashqarida (masalan, boshqa dasturlar egallagan disk joyi, yoki `/var/log` katta log fayllari) bo'lishi mumkin.
✅ To'g'ri: Docker bilan bir qatorda, oddiy `df -h` (host darajasidagi umumiy disk holati) va `du -sh /var/log/*` kabi buyruqlar bilan ham tekshiring — muammo har doim ham Docker'ning o'zida bo'lavermaydi.

## Mashq/topshiriq

**(Oson)** `docker system df` va `docker system df -v` buyruqlarini ishga tushiring, natijalarni solishtiring va qaysi turdagi resurs (image, konteyner, volume) eng ko'p joy egallayotganini toping.

**(O'rtacha)** Ataylab bir nechta ishlatilmayotgan image va to'xtatilgan konteyner yarating (masalan, bir necha marta turli tag bilan kichik image quring, ishlatmang), so'ng `docker container prune` va `docker image prune`ni bajarib, `docker system df` orqali qancha joy bo'shaganini solishtiring.

**(Qiyin)** Ataylab restart loop holatini simulyatsiya qiling (masalan, `docker run -d --restart unless-stopped python:3.13-slim python3 -c "import mavjud_bolmagan_modul"`), so'ng to'liq diagnostika ketma-ketligini (`docker ps -a` → `docker logs` → sababni aniqlash) bajarib, muammoni tavsiflab yozing, so'ng konteynerni to'xtatib, sababi tuzatilgan (masalan, `import json`) versiyasi bilan qayta ishga tushiring.

<details>
<summary>Javoblarni ko'rish</summary>

1. `docker system df -v` — har bir alohida image/konteyner/volume nomi va hajmini ko'rsatadi; odatda `Images` yoki `Build Cache` eng ko'p joy egallaydi, ayniqsa ko'p marta qurilgan (`docker build`) loyihalarda.
2. Bir nechta `docker build -t test:v1 .`, `test:v2 .` va h.k. qurib (ishlatmasdan), `docker container prune -f`, `docker image prune -f`, so'ng `docker system df` — `RECLAIMABLE` ustuni kamayganini (bo'shagan joy asl joyga qo'shilganini) ko'rish mumkin.
3. `docker run -d --name restart_test --restart unless-stopped python:3.13-slim python3 -c "import mavjud_bolmagan_modul"`, `docker ps -a` — `Restarting` holatini ko'rsatadi, `docker logs restart_test` — `ModuleNotFoundError: No module named 'mavjud_bolmagan_modul'` xatosini ko'rsatadi; muammoni tuzatib, `docker rm -f restart_test` so'ng `docker run -d --name restart_test --restart unless-stopped python:3.13-slim python3 -c "import json; print('OK')"` — endi konteyner muvaffaqiyatli tugaydi (`Exited (0)`, `restart` siyosati muvaffaqiyatli tugagan konteynerni qayta ishga tushirmaydi, chunki bu xato emas).

</details>

## Qisqacha xulosa

Docker vaqt o'tishi bilan diskda ko'p joy egallashi mumkin — `docker system df` orqali holatni ko'rish, `docker container/image/network/volume prune` (va ularning barchasini birlashtiruvchi `docker system prune`) orqali ehtiyotkorlik bilan tozalash mumkin, `--volumes` bayrog'i esa **eng xavfli**, faqat aniq maqsad bilan ishlatilishi kerak; production muammolarini diagnostika qilishda har doim `docker logs` (asl sababni topish uchun) birinchi qadam bo'lib, `docker stats`, `docker inspect --format='{{.State.OOMKilled}}'`, `docker network inspect` kabi vositalar xotira, tarmoq va boshqa resurslar bilan bog'liq muammolarni aniqlashtiradi — bu vositalar to'plami Docker bilan ishlaydigan har qanday production tizimini ishonchli boshqarishning zarur qismidir.
