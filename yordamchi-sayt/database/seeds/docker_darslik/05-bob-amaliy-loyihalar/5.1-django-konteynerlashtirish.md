# Python/Django ilovasini konteynerlashtirish

## Bu darsda nimalarni o'rganasiz

- To'liq Django loyihasini noldan Docker'ga moslashtira olasiz
- Django'ning maxsus Docker talablarini (statik fayllar, migratsiyalar, `ALLOWED_HOSTS`) bilasiz
- `entrypoint.sh` skripti orqali konteyner ishga tushishidan oldingi tayyorgarlikni avtomatlashtira olasiz
- Development va production uchun alohida Compose fayllarini tashkil qila olasiz

## Nazariy qism

### Django loyihasini Docker uchun tayyorlash — o'ziga xos jihatlar

Django loyihasini konteynerlashtirish, oddiy Python skriptidan farqli o'laroq, bir necha maxsus jihatlarni hisobga olishni talab qiladi:

1. **`ALLOWED_HOSTS`** — Docker konteynerida ilova IP manzili har safar o'zgarishi mumkin, shuning uchun `settings.py`da bu sozlama muhit o'zgaruvchisi orqali moslashuvchan bo'lishi kerak.
2. **Statik fayllar** (`STATIC_ROOT`) — production'da Django o'zi statik fayllarni xizmat qilmaydi (bu Nginx yoki boshqa veb-server vazifasi), shuning uchun ularni alohida volume'ga yig'ish kerak.
3. **Migratsiyalar** — konteyner har safar ishga tushganda, ma'lumotlar bazasi sxemasi eng so'nggi holatda ekanligini ta'minlash kerak.
4. **`SECRET_KEY` va parollar** — 4.2-darsda ko'rganimizdek, `.env` orqali boshqariladi.

### `settings.py`ni muhit o'zgaruvchilariga moslashtirish

```python
# settings.py
import os

SECRET_KEY = os.environ.get("DJANGO_SECRET_KEY", "faqat-development-uchun-xavfsiz-emas")
DEBUG = os.environ.get("DEBUG", "False") == "True"
ALLOWED_HOSTS = os.environ.get("ALLOWED_HOSTS", "localhost,127.0.0.1").split(",")

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ.get("POSTGRES_DB"),
        "USER": os.environ.get("POSTGRES_USER"),
        "PASSWORD": os.environ.get("POSTGRES_PASSWORD"),
        "HOST": os.environ.get("DATABASE_HOST", "db"),
        "PORT": os.environ.get("DATABASE_PORT", "5432"),
    }
}

STATIC_URL = "/static/"
STATIC_ROOT = "/app/staticfiles"
```

Bu — Python kursining 5.5-darsida ko'rgan `os.environ` bilan ishlashning to'g'ridan-to'g'ri davomi: barcha muhit-bog'liq sozlamalar kod ichiga "qattiq yozilgan" (hardcoded) emas, muhit o'zgaruvchilaridan olinadi.

### `entrypoint.sh` — konteyner ishga tushishidan oldingi tayyorgarlik

Ko'p Django loyihalarida konteyner ishga tushganda avtomatik bajarilishi kerak bo'lgan bir nechta qadam bo'ladi (migratsiyalarni kutish, ularni bajarish, statik fayllarni yig'ish). Bu — alohida **entrypoint skripti** orqali tashkil qilinadi:

`entrypoint.sh`:

```bash
#!/bin/bash
set -e    # istalgan buyruq xato bersa, skript darhol to'xtaydi

echo "Migratsiyalarni bajarish..."
python3 manage.py migrate --noinput

echo "Statik fayllarni yig'ish..."
python3 manage.py collectstatic --noinput

echo "Gunicorn ishga tushmoqda..."
exec gunicorn --bind 0.0.0.0:8000 --workers 3 loyiha.wsgi:application
```

`set -e` — Bash'ning maxsus rejimi: agar ichidagi **istalgan** buyruq muvaffaqiyatsiz (nolinchi bo'lmagan chiqish kodi bilan) tugasa, skript darhol to'xtaydi — bu, masalan, migratsiya muvaffaqiyatsiz bo'lsa, Gunicorn'ning noto'g'ri holatda ishga tushishining oldini oladi.

`exec` — oxirgi buyruq oldida `exec` ishlatilishi muhim: bu joriy skript jarayonini **Gunicorn jarayoniga almashtiradi** (yangi jarayon yaratmasdan), bu Docker'ning signal boshqaruvi (masalan, `docker stop` yuboradigan `SIGTERM`) to'g'ri ishlashi uchun zarur (2.1-darsda ko'rgan exec forma tushunchasining bevosita davomi).

### Dockerfile'da `entrypoint.sh`ni ishlatish

```dockerfile
FROM python:3.13-slim

WORKDIR /app

RUN apt-get update && \
    apt-get install -y --no-install-recommends libpq5 && \
    rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN chmod +x entrypoint.sh    # skriptga bajarilish huquqini berish

ENTRYPOINT ["./entrypoint.sh"]
```

`RUN chmod +x entrypoint.sh` — Linux'da skript fayllarini bajarish uchun **bajarilish huquqi** (execute permission) kerak, aks holda `Permission denied` xatosi chiqadi.

### Development va production uchun alohida Compose fayllari

Real loyihalarda development (kod jonli o'zgarishi, `DEBUG=True`) va production (optimallashtirilgan, `DEBUG=False`) sozlamalari sezilarli farq qiladi. Buning uchun **bir nechta compose fayl** ishlatiladi:

`compose.yaml` (umumiy, ikkalasida ham ishlatiladigan qism):

```yaml
services:
  veb:
    build: .
    env_file:
      - .env
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16
    env_file:
      - .env
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER}"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pg_data:
```

`compose.override.yaml` (**development** uchun — Docker Compose bu faylni `compose.yaml` bilan **avtomatik birlashtiradi**, agar u ayni shu nomda mavjud bo'lsa):

```yaml
services:
  veb:
    volumes:
      - .:/app          # bind mount — kodni jonli tahrirlash
    ports:
      - "8000:8000"
    environment:
      - DEBUG=True
    command: python3 manage.py runserver 0.0.0.0:8000    # entrypoint.sh o'rniga oddiy dev-server
```

`compose.prod.yaml` (**production** uchun — aniq ko'rsatilishi kerak):

```yaml
services:
  veb:
    ports:
      - "8000:8000"
    environment:
      - DEBUG=False
    restart: unless-stopped
```

```bash
# Development — compose.yaml + compose.override.yaml AVTOMATIK birlashadi
docker compose up

# Production — aniq ikkala faylni ko'rsatish kerak
docker compose -f compose.yaml -f compose.prod.yaml up -d
```

## Amaliy misol

To'liq loyiha strukturasi va ishga tushirish jarayoni:

```
django-docker-loyiha/
├── compose.yaml
├── compose.override.yaml
├── compose.prod.yaml
├── Dockerfile
├── entrypoint.sh
├── .env
├── .dockerignore
├── requirements.txt
└── loyiha/
    ├── manage.py
    ├── loyiha/
    │   ├── settings.py
    │   ├── urls.py
    │   └── wsgi.py
    └── asosiy_ilova/
        └── ...
```

```bash
# 1. Development rejimida ishga tushirish
docker compose up --build

# 2. Yangi terminal oynasida — migratsiya yaratish (agar model o'zgargan bo'lsa)
docker compose exec veb python3 manage.py makemigrations
docker compose exec veb python3 manage.py migrate

# 3. Superuser yaratish
docker compose exec veb python3 manage.py createsuperuser

# 4. Kodni HOST'da (bind mount tufayli) tahrirlab, natijani darhol ko'rish
# (runserver avtomatik qayta yuklaydi — Python kursining tanish workflow'i)

# 5. Production rejimiga o'tish (masalan, serverda)
docker compose -f compose.yaml -f compose.prod.yaml up --build -d
docker compose -f compose.yaml -f compose.prod.yaml exec veb python3 manage.py migrate
```

Bu tuzilma — 6-bobda ko'radigan CI/CD jarayonlarida ham asos bo'lib xizmat qiladi: test/staging/production muhitlari uchun bir xil bazaviy `compose.yaml` ustiga, har biriga xos qo'shimcha fayllar qo'shiladi.

## Keng tarqalgan xatolar

**Xato 1:** production'da `DEBUG=True` qoldirish.
❌ `.env`da yoki `compose.prod.yaml`da `DEBUG=True` unutilib qolsa — bu Django xatolarini **batafsil, maxfiy ma'lumotlar** (kod, sozlamalar) bilan birga foydalanuvchiga ko'rsatadi, bu jiddiy xavfsizlik xatari.
✅ To'g'ri: production konfiguratsiyasida har doim `DEBUG=False` bo'lishini alohida tekshiring, va bu qiymat production `.env`da aniq belgilangan bo'lsin.

**Xato 2:** `entrypoint.sh` faylida Windows qator tugash belgilarini (CRLF) qoldirish.
❌ Agar `entrypoint.sh` fayli Windows'da tahrirlangan bo'lsa (yoki noto'g'ri sozlangan matn muharririda saqlansa), Linux konteynerida `exec ./entrypoint.sh: /bin/bash^M: bad interpreter` kabi tushunarsiz xato chiqishi mumkin.
✅ To'g'ri: `entrypoint.sh` faylini har doim Unix (LF) qator tugash formatida saqlang — VS Code'da pastki panelda "CRLF"/"LF" ko'rsatkichini tekshiring va kerak bo'lsa "LF"ga o'zgartiring.

**Xato 3:** `collectstatic`ni unutib, production'da statik fayllar (CSS, JS) ko'rinmasligi.
❌ `DEBUG=False` bo'lganda, Django o'zi statik fayllarni xizmat qilmaydi (bu xavfsizlik va samaradorlik uchun ataylab shunday), va agar `collectstatic` bajarilmagan bo'lsa, sayt "yalang'och" (stilsiz) ko'rinadi.
✅ To'g'ri: `entrypoint.sh`da har doim `collectstatic --noinput`ni migratsiyadan keyin, Gunicorn ishga tushishidan oldin bajaring (yuqoridagi misolda ko'rganimizdek).

## Mashq/topshiriq

**(Oson)** Oddiy, bo'sh Django loyihasi yarating (`django-admin startproject loyiha`), unga oddiy `Dockerfile` va `compose.yaml` (faqat `veb` xizmati, `db`siz, SQLite bilan) yozing, `docker compose up --build` orqali ishga tushiring.

**(O'rtacha)** Yuqoridagi loyihaga PostgreSQL xizmatini (4.2-darsdagi kabi, `healthcheck` bilan) qo'shing, `settings.py`ni muhit o'zgaruvchilariga moslashtiring, va `docker compose exec veb python3 manage.py migrate` orqali migratsiyalarni bajaring.

**(Qiyin)** `entrypoint.sh` skripti yozing (migratsiya + collectstatic + gunicorn), uni `Dockerfile`ga qo'shing, so'ng `compose.override.yaml` (development, `runserver` bilan) va `compose.prod.yaml` (production, `entrypoint.sh`/Gunicorn bilan) fayllarini alohida yaratib, ikkalasini ham sinab ko'ring.

## Qisqacha xulosa

Django loyihasini konteynerlashtirish — `settings.py`ni muhit o'zgaruvchilariga moslashtirish (`ALLOWED_HOSTS`, `DATABASES`, `SECRET_KEY`), `entrypoint.sh` skripti orqali migratsiya/`collectstatic`/server ishga tushirish ketma-ketligini avtomatlashtirish (`set -e` va `exec` bilan to'g'ri xato boshqaruvi va signal uzatish), va development (`compose.override.yaml`, bind mount, `runserver`) bilan production (`compose.prod.yaml`, `DEBUG=False`, Gunicorn) uchun alohida Compose konfiguratsiyalarini tashkil qilishni talab qiladi — bu yondashuv sizning oldingi Django darsligingizdagi (16-27-darslar) barcha g'oyalarni to'liq, professional Docker workflow'iga birlashtiradi.
