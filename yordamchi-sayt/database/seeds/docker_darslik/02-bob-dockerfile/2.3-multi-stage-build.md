# Multi-stage build

## Bu darsda nimalarni o'rganasiz

- Multi-stage build nima ekanini va u qanday muammoni hal qilishini tushunasiz
- Bir nechta `FROM` bosqichli Dockerfile yoza olasiz
- `COPY --from=` orqali bosqichlar orasida fayl ko'chira olasiz
- Image hajmini sezilarli kamaytirish uchun bu texnikani qo'llay olasiz

## Nazariy qism

### Muammo — "qurish vositalari" production image'da kerakmi

Ba'zi dasturlash tillari (masalan, Go, C++, yoki hatto ba'zi Python/Node.js loyihalari) kodni ishga tushirishdan oldin **kompilyatsiya qilish** yoki **build qilish** bosqichini talab qiladi. Bu bosqich uchun ko'pincha og'ir "qurish vositalari" (compiler, build tools) kerak bo'ladi — lekin bu vositalar **faqat qurish paytida** kerak, tayyor dastur ishga tushganda ular endi **keraksiz**.

Agar barcha qurish vositalarini production image'ga qoldirsangiz — image hajmi keraksiz katta bo'ladi (ba'zan 5-10 baravar), va bu ham disk joyini isrof qiladi, ham xavfsizlik nuqtai nazaridan yomon (ortiqcha vositalar — ortiqcha zaiflik nuqtalari).

### Multi-stage build — yechim

**Multi-stage build** — Dockerfile'da bir nechta `FROM` bosqichini ishlatish imkonini beradi: birinchi bosqich(lar)da og'ir qurish vositalari bilan kod tayyorlanadi, **oxirgi** bosqichda esa faqat **natija** (tayyor fayllar) yengil, minimal image'ga ko'chiriladi — qurish vositalarining o'zi yakuniy image'ga umuman kirmaydi.

### Oddiy misol — ikki bosqichli Dockerfile

```dockerfile
# ============ 1-BOSQICH: "builder" ============
FROM python:3.13 AS builder

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt


# ============ 2-BOSQICH: yakuniy, yengil image ============
FROM python:3.13-slim

WORKDIR /app

# Faqat BIRINCHI bosqichda o'rnatilgan kutubxonalarni ko'chirib olamiz
COPY --from=builder /root/.local /root/.local
COPY . .

ENV PATH=/root/.local/bin:$PATH

CMD ["python3", "main.py"]
```

`FROM python:3.13 AS builder` — bu bosqichga `builder` nomi berilmoqda (keyinchalik unga murojaat qilish uchun). `COPY --from=builder /root/.local /root/.local` — **faqat** `builder` bosqichida yaratilgan `/root/.local` papkasini (o'rnatilgan Python kutubxonalari) yakuniy image'ga ko'chiradi — `python:3.13` (to'liq, katta bazaviy image, qurish vositalari bilan) esa yakuniy image'ga **umuman kirmaydi**.

### Real hayotiy misol — Go dasturi bilan (kontrastni ko'rsatish uchun)

Multi-stage build'ning eng klassik va tushunarli namunasi — kompilyatsiya talab qiluvchi tillarda ko'rinadi:

```dockerfile
# 1-BOSQICH: kompilyatsiya (og'ir, ~800MB Go compiler bilan)
FROM golang:1.23 AS builder
WORKDIR /app
COPY . .
RUN go build -o mening-dastur

# 2-BOSQICH: faqat kompilyatsiya qilingan FAYLNI olamiz
FROM alpine:latest
WORKDIR /app
COPY --from=builder /app/mening-dastur .
CMD ["./mening-dastur"]
```

Bu holatda yakuniy image — bor-yo'g'i bir necha MB (faqat kompilyatsiya qilingan bitta fayl + minimal Alpine Linux), Go compiler'ning o'zi (~800MB) esa yakuniy image'ga **umuman kirmaydi**.

### Python loyihalarida multi-stage build — qachon foydali

Python — kompilyatsiya talab qilmaydigan til bo'lgani uchun, multi-stage build Go kabi tillarga qaraganda kamroq **dramatik** foyda beradi, lekin baribir foydali holatlar mavjud:

1. **Kompilyatsiya talab qiluvchi kutubxonalar** (masalan, ba'zi `C`-kengaytmali paketlar) — `gcc`, `build-essential` kabi og'ir kompilyatorlar faqat o'rnatish paytida kerak.
2. **Test va linting bosqichlarini** yakuniy image'dan ajratish — testlar uchun kerakli qo'shimcha kutubxonalar (`pytest`, `mypy`) production'da kerak emas.
3. **Frontend + Backend birlashgan loyihalarda** — masalan, React frontend'ni `node` bilan qurib, natijaviy statik fayllarni Django/Nginx image'ga ko'chirish.

```dockerfile
# 1-BOSQICH: kompilyatsiya talab qiluvchi kutubxonalarni o'rnatish
FROM python:3.13 AS builder

WORKDIR /app
RUN apt-get update && apt-get install -y gcc build-essential

COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt


# 2-BOSQICH: yakuniy, yengil, KOMPILYATOR YO'Q image
FROM python:3.13-slim

WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .

ENV PATH=/root/.local/bin:$PATH
CMD ["python3", "main.py"]
```

Bu yerda `gcc` va `build-essential` (jami yuzlab MB) — faqat `builder` bosqichida mavjud, yakuniy image ularni **umuman ko'rmaydi**.

### Bosqichlarni tanlab qurish — `--target`

```bash
docker build --target builder -t mening-loyiham-builder .
```

`--target <bosqich_nomi>` — Dockerfile'dagi **faqat** ko'rsatilgan bosqichgacha (uni ham qo'shib) quradi. Bu — masalan, faqat test bosqichini alohida ishga tushirish yoki debug qilish uchun foydali.

### Hajm farqini solishtirish

```bash
docker images | grep mening-loyiham
```

```
REPOSITORY              TAG            SIZE
mening-loyiham-single    latest         1.2GB    # bitta bosqichli, gcc bilan
mening-loyiham-multi      latest         180MB     # multi-stage, faqat kerakli qismlar
```

Bu — real loyihalarda **6-7 baravar** kichikroq image degani — kichikroq image tezroq yuklanadi, tezroq deploy qilinadi, va kamroq disk/tarmoq resursini sarflaydi.

## Amaliy misol

To'liq, amaliy multi-stage Dockerfile — Django loyihasi uchun (avvalgi Django darsligidagi 16-darsni eslatadi, endi chuqurroq optimallashtirilgan holda):

```dockerfile
# ============ 1-BOSQICH: bog'liqliklarni o'rnatish ============
FROM python:3.13-slim AS builder

WORKDIR /app

# Ba'zi Django loyihalarida psycopg2 kabi paketlar kompilyatsiya talab qiladi
RUN apt-get update && \
    apt-get install -y --no-install-recommends gcc libpq-dev && \
    rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt


# ============ 2-BOSQICH: yakuniy, production image ============
FROM python:3.13-slim

WORKDIR /app

# Faqat runtime uchun kerakli kutubxona (libpq5 — postgresql client, gcc EMAS)
RUN apt-get update && \
    apt-get install -y --no-install-recommends libpq5 && \
    rm -rf /var/lib/apt/lists/*

COPY --from=builder /root/.local /root/.local
COPY . .

ENV PATH=/root/.local/bin:$PATH
ENV PYTHONUNBUFFERED=1

EXPOSE 8000

CMD ["gunicorn", "--bind", "0.0.0.0:8000", "loyiha.wsgi:application"]
```

Diqqat qiling: birinchi bosqichda `gcc` va `libpq-dev` (kompilyatsiya uchun to'liq "dev" versiyasi) o'rnatiladi, ikkinchi (yakuniy) bosqichda esa faqat `libpq5` (ishga tushirish uchun yetarli, ancha kichikroq "runtime" versiyasi) — bu farq multi-stage build'ning amaliy qiymatini yana bir bor ko'rsatadi.

## Keng tarqalgan xatolar

**Xato 1:** `COPY --from=`da bosqich nomini noto'g'ri yozish yoki umuman `AS` bilan nom bermaslik.
❌ `COPY --from=builder ...` — agar birinchi bosqichda `AS builder` yozilmagan bo'lsa, Docker bu nomni tanimaydi va xato beradi.
✅ To'g'ri: har bir oraliq bosqichga `FROM <image> AS <nom>` orqali aniq nom bering, va `COPY --from=`da xuddi shu nomni ishlating.

**Xato 2:** yakuniy bosqichda ham kerak bo'lmagan qurish vositalarini qoldirish.
❌ Yakuniy bosqichda `FROM python:3.13` (to'liq versiya, `slim` emas) ishlatib, "multi-stage qildim" deb o'ylash — lekin agar yakuniy bosqichning bazaviy image'i o'zi allaqachon katta bo'lsa, multi-stage'ning foydasi kamayadi.
✅ To'g'ri: yakuniy bosqich uchun har doim eng **yengil** mos bazaviy image'ni (`slim`, `alpine`) tanlang — multi-stage build'ning maqsadi aynan shu, faqat kerakli narsalarni qoldirish.

**Xato 3:** `COPY --from=builder`da noto'g'ri yo'l ko'rsatish, natijada kerakli fayllar yakuniy image'ga tushmasligi.
❌ `pip install --user` orqali kutubxonalar `/root/.local`ga o'rnatiladi, lekin `COPY --from=builder /app/venv ...` kabi noto'g'ri yo'l yozilsa, fayllar topilmaydi va konteyner ishga tushganda `ModuleNotFoundError` beradi.
✅ To'g'ri: `pip install --user` qaysi papkaga o'rnatishini bilib oling (odatda `/root/.local`), va `COPY --from=`da **aynan shu** yo'lni ishlating; noaniqlik bo'lsa, `builder` bosqichida `RUN find / -name "site-packages"` kabi buyruq bilan tekshirib ko'rish mumkin.

## Mashq/topshiriq

**(Oson)** 2.1-darsdagi `salomlashuv-app` loyihasini ikki bosqichli (`builder` + yakuniy) Dockerfile'ga aylantiring, garchi bu loyihada kompilyatsiya kerak bo'lmasa ham — faqat sintaksisni mashq qilish uchun.

**(O'rtacha)** Bitta bosqichli (`FROM python:3.13`, `gcc` bilan) va ikki bosqichli (multi-stage, `gcc` faqat `builder`da) ikkita Dockerfile yozing (ikkalasida ham `numpy` kabi kompilyatsiya talab qiladigan kutubxonani `requirements.txt`ga qo'shing), ikkalasini quring va `docker images` orqali hajmlarini solishtiring.

**(Qiyin)** Uch bosqichli Dockerfile yozing: birinchi bosqich — test bog'liqliklarini o'rnatib testlarni ishga tushirish (`pytest`), ikkinchi bosqich — production bog'liqliklarini o'rnatish, uchinchi (yakuniy) bosqich — faqat production kutubxonalari va kodni birlashtiruvchi, eng yengil image. `--target` bayrog'i bilan faqat test bosqichini alohida ishga tushiring.

## Qisqacha xulosa

Multi-stage build — Dockerfile'da bir nechta `FROM` bosqichini ishlatib, og'ir qurish vositalarini (kompilyator, dev kutubxonalar) faqat **oraliq** bosqich(lar)da qoldirib, `COPY --from=<bosqich_nomi>` orqali faqat **natijani** yakuniy, yengil image'ga ko'chirish texnikasidir; bu — yakuniy production image hajmini sezilarli (ba'zan bir necha baravar) kamaytiradi, xavfsizlikni oshiradi (kamroq keraksiz vosita — kamroq zaiflik) va, `--target` bayrog'i orqali, testlash kabi qo'shimcha bosqichlarni ham bitta Dockerfile ichida tartibli tashkil qilish imkonini beradi — bu texnika real production loyihalarida (Django, Aiogram va boshqa xizmatlar uchun) standart amaliyot hisoblanadi.
