# Image qatlamlari (layers) va build cache

## Bu darsda nimalarni o'rganasiz

- Docker image'ning "qatlamlar" (layers) tuzilmasini tushuntira olasiz
- Build cache qanday ishlashini va undan qanday foydalanishni bilasiz
- Dockerfile buyruqlari tartibini build tezligini oshirish uchun to'g'ri tanlay olasiz
- `docker history` orqali image qatlamlarini tekshira olasiz

## Nazariy qism

### Image — qatlamlar to'plami

Docker image — bitta yaxlit fayl emas, balki **qatlamlar** (layers) to'plami. Har bir Dockerfile buyrug'i (`FROM`, `RUN`, `COPY` va h.k.) — odatda **yangi bitta qatlam** yaratadi:

```dockerfile
FROM python:3.13-slim        # 1-qatlam (bazaviy image)
WORKDIR /app                  # 2-qatlam
COPY requirements.txt .        # 3-qatlam
RUN pip install -r requirements.txt   # 4-qatlam
COPY . .                        # 5-qatlam
CMD ["python3", "main.py"]       # metama'lumot (odatda alohida qatlam yaratmaydi)
```

Har bir qatlam — o'zidan **oldingi** qatlam ustiga qo'yilgan "o'zgarishlar to'plami" (masalan, qaysi fayllar qo'shildi/o'zgardi). Bu tuzilma — Git'dagi commit'lar ketma-ketligiga o'xshaydi: har bir commit — oldingi holatga nisbatan farqni saqlaydi.

### Nega qatlamli tuzilma foydali — qayta ishlatish (reuse)

Qatlamlar **keshlanadi** (saqlab qo'yiladi) va bir nechta image orasida **ulashiladi**:

```
python:3.13-slim image'i:
┌─────────────────────┐
│ Qatlam 4: Debian paketlar │
│ Qatlam 3: Python o'rnatish │
│ Qatlam 2: Debian asosi     │
│ Qatlam 1: bo'sh fayl tizimi │
└─────────────────────┘

mening-loyiham:1.0 (yuqoridagi ustiga quriladi):
┌─────────────────────┐
│ Qatlam 8: CMD (metama'lumot) │
│ Qatlam 7: COPY . .           │
│ Qatlam 6: RUN pip install     │
│ Qatlam 5: COPY requirements.txt│
│ Qatlam 4: WORKDIR /app          │
├─────────────────────┤
│  python:3.13-slim'ning barcha qatlamlari (1-4) — QAYTA ISHLATILADI! │
└─────────────────────┘
```

Agar kompyuteringizda bir nechta image `python:3.13-slim` asosida qurilgan bo'lsa, ularning barchasi bazaviy qatlamlarni **ulashadi** — bu diskda joy tejaydi va yuklab olish/qurishni tezlashtiradi.

### Build cache — qurishni tezlashtirish mexanizmi

`docker build` har bir buyruqni bajarishdan oldin, **shu buyruq va undan oldingi barcha buyruqlar avval xuddi shunday bajarilganmi** (va tegishli fayllar o'zgarmaganmi) deb tekshiradi. Agar javob "ha" bo'lsa — Docker qaytadan bajarmasdan, **keshdan** (saqlangan natijadan) foydalanadi:

```bash
docker build -t mening-loyiham .
```

Birinchi marta qurish:

```
Step 1/6 : FROM python:3.13-slim
Step 2/6 : WORKDIR /app
Step 3/6 : COPY requirements.txt .
Step 4/6 : RUN pip install -r requirements.txt
 ---> Running in a1b2c3d4e5f6
 ... (bir necha soniya, kutubxonalar o'rnatilmoqda)
Step 5/6 : COPY . .
Step 6/6 : CMD ["python3", "main.py"]
```

Faqat `main.py`ni o'zgartirib, **qayta** qurish:

```
Step 1/6 : FROM python:3.13-slim
Step 2/6 : WORKDIR /app
Step 3/6 : COPY requirements.txt .
Step 4/6 : RUN pip install -r requirements.txt
 ---> Using cache          <-- KESHDAN OLINDI, qayta bajarilmadi!
Step 5/6 : COPY . .           <-- bu yerdan boshlab qayta bajariladi (chunki fayl o'zgargan)
Step 6/6 : CMD ["python3", "main.py"]
```

### Muhim qoida — buyruqlar tartibi va cache "buzilishi"

**Cache buzilishi qoidasi**: agar biror qatlam o'zgarsa (yoki uning kirish ma'lumoti o'zgarsa), Docker o'sha qatlamdan **boshlab, undan keyingi BARCHA qatlamlarni** qayta quradi — hatto ular o'zgarmagan bo'lsa ham. Shuning uchun Dockerfile'da buyruqlar tartibi **strategik** ahamiyatga ega:

```dockerfile
# ❌ NOTO'G'RI tartib — cache samarasiz ishlatiladi
FROM python:3.13-slim
WORKDIR /app
COPY . .                                    # HAR safar, istalgan fayl o'zgarsa, bu qatlam "buziladi"
RUN pip install -r requirements.txt           # ... va bu ham QAYTA bajariladi, hatto requirements.txt o'zgarmagan bo'lsa ham!
```

```dockerfile
# ✅ TO'G'RI tartib — cache samarali ishlatiladi
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .                      # faqat requirements.txt o'zgarganda "buziladi"
RUN pip install -r requirements.txt            # faqat requirements.txt o'zgarganda QAYTA bajariladi
COPY . .                                        # qolgan kod tez-tez o'zgaradi, lekin bu ENG OXIRIDA
```

**Amaliy qoida**: kamdan-kam o'zgaradigan narsalarni (bazaviy image, kutubxonalar o'rnatish) Dockerfile'ning **boshiga**, tez-tez o'zgaradigan narsalarni (o'z kodingiz) **oxiriga** joylashtiring.

### `docker history` — image qatlamlarini ko'rish

```bash
docker history mening-loyiham:1.0
```

Natija:

```
IMAGE          CREATED          CREATED BY                                     SIZE
a1b2c3d4e5f6   2 minutes ago    CMD ["python3" "main.py"]                        0B
b2c3d4e5f6a7   2 minutes ago    COPY . .                                          4.2kB
c3d4e5f6a7b8   3 minutes ago    RUN pip install -r requirements.txt               15.3MB
d4e5f6a7b8c9   3 minutes ago    COPY requirements.txt .                           45B
e5f6a7b8c9d0   3 minutes ago    WORKDIR /app                                       0B
...            2 weeks ago      /bin/sh -c #(nop) CMD ["python3"]                  0B
```

Bu buyruq — har bir qatlamning **hajmini** va uni yaratgan buyruqni ko'rsatadi, bu image hajmini optimallashtirish uchun juda foydali (masalan, qaysi `RUN` buyrug'i eng ko'p joy egallayotganini aniqlash).

### `RUN` buyruqlarini birlashtirish — qatlamlar sonini kamaytirish

```dockerfile
# ❌ Har biri ALOHIDA qatlam — 3 ta RUN
RUN apt update
RUN apt install -y curl
RUN apt install -y git
```

```dockerfile
# ✅ Bitta qatlamga birlashtirilgan — tezroq va kichikroq
RUN apt update && \
    apt install -y curl git && \
    rm -rf /var/lib/apt/lists/*
```

`&&` bilan bir nechta buyruqni **bitta** `RUN` qatoriga birlashtirish — natijada bitta qatlam yaratiladi (uch o'rniga), va `rm -rf /var/lib/apt/lists/*` — `apt`ning vaqtinchalik fayllarini o'sha **bitta** qatlam ichida tozalab, image hajmini kamaytiradi (agar tozalash alohida `RUN`da bo'lsa, eski qatlamdagi fayllar hali ham image tarixida "og'irlik" qilib qoladi, chunki qatlamlar faqat **qo'shiladi**, oldingi qatlamlar hajmi "kamaymaydi").

## Amaliy misol

Build vaqtini o'lchash orqali cache'ning amaliy foydasini ko'rish:

```bash
# 1-loyiha: to'g'ri tartib bilan
mkdir togri-tartib && cd togri-tartib
echo "requests==2.31.0" > requirements.txt
echo 'print("Versiya 1")' > main.py
cat > Dockerfile << 'EOF'
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python3", "main.py"]
EOF

# Birinchi qurish — vaqtni o'lchaymiz
time docker build -t togri-tartib .

# main.py'ni o'zgartiramiz (requirements.txt O'ZGARMAYDI)
echo 'print("Versiya 2")' > main.py

# Qayta qurish — bu safar SEZILARLI TEZROQ bo'lishi kerak (pip install keshdan olinadi)
time docker build -t togri-tartib .
```

Ikkinchi `docker build` chiqishida `RUN pip install ...` qatorida `CACHED` (yoki `Using cache`) belgisini ko'rasiz — bu build vaqtini sezilarli qisqartiradi, ayniqsa `requirements.txt`da ko'p va og'ir kutubxonalar (masalan, `pandas`, `torch`) bo'lganda bu farq **daqiqalar** bilan o'lchanishi mumkin.

## Keng tarqalgan xatolar

**Xato 1:** `COPY . .`ni kutubxonalar o'rnatishdan oldin yozish (2.1-darsda ham eslatilgan, bu yerda sababi chuqurroq tushuntiriladi).
❌ Bu — har qanday fayl o'zgarishida (hatto `README.md`ga bitta so'z qo'shilsa ham) butun `pip install` jarayonining qayta bajarilishiga olib keladi, chunki `COPY . .` qatlami "buziladi" va undan keyingi HAMMA qatlam qayta quriladi.
✅ To'g'ri: doim eng kam o'zgaradigan fayllarni (`requirements.txt`, `package.json`) birinchi, eng ko'p o'zgaradigan (o'z kodingiz) fayllarni oxiriga joylashtiring.

**Xato 2:** juda ko'p mayda `RUN` buyruqlarini alohida-alohida yozib, image hajmini keraksiz oshirish.
❌ Har bir `RUN apt install paket` — alohida qatlam yaratadi, va agar keyingi qatlamda `apt clean` qilinsa ham, oldingi qatlamlardagi vaqtinchalik fayllar image tarixida saqlanib qoladi (chunki qatlamlar faqat "qo'shiladi", "kamaymaydi").
✅ To'g'ri: bog'liq buyruqlarni `&&` bilan bitta `RUN`ga birlashtiring va tozalashni (`rm -rf /var/lib/apt/lists/*`) **o'sha bitta** qatorning ichida bajaring.

**Xato 3:** cache har doim foydali deb, uni hech qachon "sindirish" kerak emas deb o'ylash.
❌ Ba'zan (masalan, xavfsizlik yangilanishlari uchun) `apt update && apt install` buyrug'ini **majburan** qayta bajartirish kerak bo'ladi, lekin agar hech narsa o'zgarmagan bo'lsa, Docker uni keshdan oladi va eski, yangilanmagan paketlar bilan qoladi.
✅ To'g'ri: agar bazaviy paketlarni majburan yangilash kerak bo'lsa, `docker build --no-cache` bayrog'idan foydalaning (bu **butun** cache'ni e'tiborsiz qoldirib, hammasini noldan quradi) — buni muntazam emas, faqat kerak bo'lganda ishlatish tavsiya etiladi, chunki u buildni sezilarli sekinlashtiradi.

## Mashq/topshiriq

**(Oson)** 2.1-darsdagi `salomlashuv-app` loyihasini qayta quring, so'ng faqat `main.py` faylida bitta so'zni o'zgartirib, qayta quring va konsol chiqishida qaysi qatorlar `CACHED` deb belgilanganini toping.

**(O'rtacha)** `docker history salomlashuv-app:1.0` buyrug'ini ishga tushiring va natijadagi qatlamlar orasidan eng katta hajmga ega bo'lganini (odatda `pip install` qatlami) aniqlang.

**(Qiyin)** Ataylab **noto'g'ri** tartibli Dockerfile yozing (`COPY . .` `RUN pip install`dan oldin), uni qurib vaqtini o'lchang, so'ng `main.py`da kichik o'zgartirish qiling va qayta quring — bu safar **to'g'ri** tartibli versiyadan farqli o'laroq, `pip install` bosqichi ham qayta bajarilishini kuzating va ikkala usulning vaqt farqini yozib qoldiring.

## Qisqacha xulosa

Docker image — qatlamlar (layers) to'plami bo'lib, har bir Dockerfile buyrug'i odatda yangi qatlam yaratadi va bu qatlamlar **keshlanadi** hamda boshqa image'lar bilan **ulashiladi**; build cache — agar buyruq va uning kirish ma'lumotlari o'zgarmagan bo'lsa, uni qayta bajarmasdan saqlangan natijadan foydalanish orqali qurish vaqtini sezilarli qisqartiradi, lekin bitta qatlam "buzilsa", undan keyingi **barcha** qatlamlar qayta quriladi — shuning uchun kamdan-kam o'zgaradigan buyruqlarni (bazaviy image, kutubxona o'rnatish) Dockerfile boshiga, tez-tez o'zgaradigan kodni oxiriga joylashtirish — Docker bilan samarali ishlashning asosiy amaliy qoidasi hisoblanadi.
