# Production: Uvicorn worker'lari va Nginx

## Bu darsda nimalarni o'rganasiz

- Nima uchun production'da bitta Uvicorn jarayoni yetarli emasligini tushunasiz
- Ko'p worker jarayoni (multi-worker) sozlashni o'rganasiz
- Nginx'ni FastAPI oldida "teskari proksi" (reverse proxy) sifatida sozlashni bilasiz
- Statik fayllar, SSL va yuklama balansini (load balancing) tushunasiz

## Nazariy qism

### Nima uchun bitta jarayon (process) yetarli emas

0.1 va 6.3-darslarida ko'rilganidek, FastAPI'ning asinxron tabiati, **bitta jarayon ichida**, minglab so'rovlarni samarali boshqarishga imkon beradi. Lekin bu — **cheksiz** emas: bitta Python jarayoni, faqat **bitta protsessor yadrosidan** (CPU core) foydalana oladi (Python'ning Global Interpreter Lock — GIL cheklovi sababli).

Zamonaviy serverlar, odatda 4, 8 yoki undan ko'p protsessor yadrosiga ega. Agar faqat **bitta** Uvicorn jarayoni ishga tushirilsa, qolgan yadrolar **ishlatilmay** qoladi.

### Yechim — ko'p worker jarayoni

```bash
fastapi run app/main.py --workers 4
```

Bu buyruq — bitta emas, balki **4 ta mustaqil** Uvicorn jarayonini ishga tushiradi, har biri o'zining protsessor yadrosida ishlaydi. Kiruvchi so'rovlar, bu jarayonlar orasida **avtomatik taqsimlanadi**.

| Worker'lar soni | Tavsiya |
|---|---|
| `2 x CPU yadrolari soni + 1` | Umumiy qabul qilingan formula (masalan, 4 yadroli serverda — 9 ta worker) |
| Loyihaga qarab moslashtirish | Ma'lumotlar bazasiga bog'liq (I/O-intensiv) ilovalar uchun ko'proq, CPU-intensiv ilovalar uchun kamroq worker mos kelishi mumkin |

> ⚠️ **Muhim eslatma:** har bir worker — **mustaqil** Python jarayoni bo'lib, o'zining xotira maydoniga ega. Bu, worker'lar orasida **umumiy holat** (masalan, oddiy Python o'zgaruvchisida saqlangan ma'lumot) **avtomatik almashtirilmasligini** anglatadi — bunday umumiy holat kerak bo'lsa, tashqi xizmat (Redis kabi kesh, yoki ma'lumotlar bazasining o'zi) ishlatilishi kerak.

### Docker Compose'da worker'larni sozlash

```dockerfile
CMD ["fastapi", "run", "app/main.py", "--port", "8000", "--workers", "4"]
```

### Nginx — teskari proksi (Reverse Proxy) nima uchun kerak

Uvicorn/FastAPI, o'zi ham HTTP so'rovlarini to'g'ridan-to'g'ri qabul qila oladi, lekin production muhitida, odatda uning **oldida**, **Nginx** joylashtiriladi. Bu — Docker darsligining 5.3-darsida, Django+Gunicorn+Nginx production tuzilmasi misolida chuqur o'rganilgan naqshning, FastAPI uchun to'g'ridan-to'g'ri qo'llanilishi.

| Nginx'ning vazifasi | Tavsif |
|---|---|
| **SSL/TLS tugatish** | HTTPS shifrlashni Nginx boshqaradi, Uvicorn — oddiy HTTP bilan ishlaydi |
| **Statik fayllarni tarqatish** | Rasm, CSS, JS kabi fayllarni, Python ilovasidan chetlab, to'g'ridan-to'g'ri Nginx orqali tezroq uzatish |
| **Yuklama balansi** | Bir nechta backend serverga (yoki konteynerga) so'rovlarni taqsimlash |
| **Xavfsizlik qatlami** | So'rov hajmi cheklovlari, IP bloklash, rate limiting |
| **Siqish (compression)** | 3.3-darsda ko'rilgan `GZipMiddleware`ga o'xshash, lekin server darajasida, ko'proq samarali |

### Nginx konfiguratsiyasi — FastAPI uchun

```nginx
# nginx.conf
upstream fastapi_backend {
    server web:8000;
}

server {
    listen 80;
    server_name mening-apim.uz;

    location / {
        proxy_pass http://fastapi_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

| Direktiva | Vazifasi |
|---|---|
| `upstream fastapi_backend` | Backend server(lar)ni belgilaydi (Docker Compose'da, `web` — xizmat nomi) |
| `proxy_pass` | So'rovlarni, belgilangan backend'ga "uzatadi" |
| `proxy_set_header Host` | Asl so'rov header'larini saqlaydi (backend, haqiqiy domen nomini bilishi uchun) |
| `X-Forwarded-For` | Mijozning haqiqiy IP manzilini, backend'ga uzatadi (aks holda, backend faqat Nginx'ning IP'sini ko'radi) |

### WebSocket uchun maxsus sozlash

6.1-darsda ko'rilgan WebSocket'lar, Nginx orqali o'tkazilganda, qo'shimcha sozlamalarni talab qiladi:

```nginx
location /ws/ {
    proxy_pass http://fastapi_backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
```

`Upgrade`/`Connection` header'lari — Nginx'ga, bu so'rovni oddiy HTTP emas, balki WebSocket protokoliga "ko'tarishi" (upgrade) kerakligini bildiradi.

### Docker Compose'da to'liq Nginx + FastAPI tuzilmasi

```yaml
services:
  web:
    build: .
    environment:
      DATABASE_URL: postgresql://fastapi_user:parol123@db:5432/kutubxona_db
    expose:
      - "8000"    # faqat ichki tarmoqqa ochiq, tashqariga emas
    depends_on:
      db:
        condition: service_healthy

  nginx:
    image: nginx:1.27-alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - web

  db:
    image: postgres:17
    environment:
      POSTGRES_USER: fastapi_user
      POSTGRES_PASSWORD: parol123
      POSTGRES_DB: kutubxona_db
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fastapi_user"]
```

> 📌 **`expose` vs `ports` — muhim farq (Docker darsligining 3.2-darsida ko'rilgan):** `web` xizmati endi `ports` o'rniga `expose` ishlatadi — bu, uni faqat Docker'ning **ichki tarmog'ida** (Nginx'ga) ko'rinadigan qiladi, tashqi dunyoga **to'g'ridan-to'g'ri** ochiq qoldirmaydi. Faqat `nginx` xizmati, `ports` orqali, tashqi dunyoga (80-port) ochiq — bu, xavfsizlik nuqtai nazaridan to'g'ri arxitektura: barcha tashqi trafik, avval Nginx orqali "filtrlanadi".

### HTTPS/SSL — qisqacha

Production'da, HTTP o'rniga har doim **HTTPS** ishlatilishi kerak. Bepul SSL sertifikatlar uchun, **Let's Encrypt** va uning `certbot` vositasi keng qo'llaniladi:

```bash
sudo apt install certbot python3-certbot-nginx -y
sudo certbot --nginx -d mening-apim.uz
```

Bu — Nginx konfiguratsiyasini avtomatik yangilab, SSL sertifikatni sozlaydi va uni muntazam yangilab turadi (bu — ilg'or, to'liq deploy jarayonining bir qismi bo'lib, ushbu darslikning asosiy qamrovidan biroz tashqarida, lekin production uchun muhim ahamiyatga ega).

## Amaliy misol

To'liq, Nginx + FastAPI (4 worker) + PostgreSQL production tuzilmasi:

```
mening-fastapi-loyiham/
├── app/
├── Dockerfile
├── compose.yaml
├── nginx.conf
└── .env
```

```dockerfile
# Dockerfile - CMD qismi
CMD ["fastapi", "run", "app/main.py", "--port", "8000", "--workers", "4"]
```

```nginx
# nginx.conf
upstream fastapi_backend {
    server web:8000;
}

server {
    listen 80;
    server_name _;

    client_max_body_size 10M;   # fayl yuklash (2.2-dars) uchun chegara

    location /ws/ {
        proxy_pass http://fastapi_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }

    location / {
        proxy_pass http://fastapi_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

```yaml
# compose.yaml
services:
  web:
    build: .
    env_file: [.env]
    expose: ["8000"]
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  nginx:
    image: nginx:1.27-alpine
    ports: ["80:80"]
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on: [web]
    restart: unless-stopped

  db:
    image: postgres:17
    env_file: [.env]
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fastapi_user"]
      interval: 5s
      retries: 5

volumes:
  postgres_data:
```

```bash
docker compose up -d --build
curl http://localhost/salomatlik
```

Endi, tashqi dunyo, faqat 80-port (Nginx) orqali ilovaga kiradi, ichki 4 ta Uvicorn worker esa, so'rovlarni parallel, samarali qayta ishlaydi.

## Keng tarqalgan xatolar

**Xato 1:** production'da, ilovani, faqat bitta worker bilan (standart, `--workers` bayrog'isiz) ishga tushirish.
❌ Bu, ko'p yadroli serverning aksariyat resurslarini ishlatmay qoldiradi, va yuqori trafik ostida, ilova kutilganidan sezilarli sekinroq ishlaydi.
✅ To'g'ri: production'da, har doim `--workers` bayrog'ini, server protsessor yadrolari soniga mos ravishda (masalan, `2 x yadrolar + 1`) sozlang.

**Xato 2:** FastAPI konteynerining portini, Docker Compose'da `ports` orqali, to'g'ridan-to'g'ri tashqi dunyoga ochiq qoldirish, Nginx bilan birga ishlatilganda.
❌ Bu, tashqi foydalanuvchilarga, Nginx'ni (uning xavfsizlik va yuklama balansi afzalliklarini) **chetlab o'tib**, to'g'ridan-to'g'ri FastAPI'ga murojaat qilish imkonini beradi — bu, butun Nginx qatlamining maqsadini yo'qqa chiqaradi.
✅ To'g'ri: agar Nginx ishlatilsa, FastAPI xizmatida, `ports` o'rniga `expose` ishlatilishi kerak — faqat Nginx, tashqi dunyoga ochiq bo'lishi lozim.

**Xato 3:** WebSocket endpoint'larini (6.1-dars), maxsus `Upgrade`/`Connection` header sozlamalarisiz, oddiy `location /`orqali Nginx'ga uzatishga urinish.
❌ Bu, WebSocket ulanishlarining muvaffaqiyatsiz bo'lishiga (yoki kutilmagan uzilishlarga) olib kelishi mumkin, chunki Nginx, standart holda, so'rovni WebSocket protokoliga "ko'tarish" kerakligini bilmaydi.
✅ To'g'ri: WebSocket endpoint'lari uchun, har doim alohida `location` bloki, `proxy_http_version 1.1` va `Upgrade`/`Connection` header'lari bilan sozlanishi kerak.

## Mashq/topshiriq

**(Oson)** `fastapi run app/main.py --workers 2` buyrug'ini ishga tushiring va `ps aux | grep fastapi` (yoki `docker top <konteyner>`) orqali, haqiqatan 2 ta jarayon ishga tushganini tasdiqlang.

**(O'rtacha)** Oddiy Nginx konfiguratsiyasi (`nginx.conf`) yozing, u `http://localhost:8000`da ishlayotgan FastAPI ilovasiga, barcha so'rovlarni `proxy_pass` orqali uzatsin, va kerakli `proxy_set_header` direktivalarini qo'shing.

**(Qiyin)** To'liq `compose.yaml` yozing — FastAPI (4 worker, faqat `expose` bilan), Nginx (80-port bilan `ports` orqali ochiq) va PostgreSQL uchta xizmatni birlashtirsin. Nima uchun bu arxitekturada, `nginx` xizmati `depends_on: [web]`ga ega bo'lishi kerakligini, lekin `condition: service_healthy` talab qilinmasligi mumkinligini (FastAPI uchun alohida `healthcheck` qo'shilmagan taqdirda) muhokama qiling.

## Qisqacha xulosa

Production'da, FastAPI ilovasi — ko'p protsessor yadrosidan to'liq foydalanish uchun, bir nechta Uvicorn worker jarayoni bilan (`--workers` bayrog'i orqali) ishga tushiriladi; bu jarayonlar oldida, odatda **Nginx** teskari proksi sifatida joylashtirilib, SSL tugatish, statik fayllarni tarqatish va yuklama balansini boshqaradi — bu, Docker darsligining 5.3-darsida ko'rilgan naqshning, FastAPI uchun to'g'ridan-to'g'ri qo'llanilishi. Docker Compose'da, FastAPI xizmati `expose` (faqat ichki tarmoq uchun), Nginx esa `ports` (tashqi dunyo uchun) orqali sozlanadi, WebSocket endpoint'lari esa Nginx'da maxsus `Upgrade`/`Connection` header sozlamalarini talab qiladi. Keyingi, yakuniy darsda, bu to'liq tizimni GitHub Actions orqali avtomatik CI/CD zanjiriga bog'lab, butun darslikni to'liq, real loyiha misolida yakunlaymiz.
