# CI/CD bilan GitHub Actions va yakuniy real loyiha

## Bu darsda nimalarni o'rganasiz

- FastAPI loyihasi uchun to'liq CI/CD workflow'ini GitHub Actions bilan yaratasiz
- Testlarni, Docker build'ni va deploy jarayonini avtomatlashtirishni o'rganasiz
- Butun darslik davomida o'rgangan bilimlarni, bitta yakuniy, real loyiha misolida birlashtirasiz
- FastAPI bilan keyingi rivojlanish yo'nalishlari haqida tasavvurga ega bo'lasiz

## Nazariy qism

### CI/CD zanjiri — qisqa eslatma

Git va GitHub darsligining 6.1-darsida, GitHub Actions'ning Git voqealariga (`push`, `pull_request`, `tag`) qanday bog'lanishini chuqur o'rgangan edik. Ushbu darsda, aynan shu tamoyillarni, FastAPI loyihasiga to'liq qo'llaymiz.

### To'liq CI/CD workflow — bosqichlar

```
1. Dasturchi, feature branch'da ishlaydi (Git darsligi, 4.1-bob GitHub Flow)
2. Pull Request ochiladi
   → CI: testlar (6.2-dars) avtomatik ishga tushadi
3. Testlar muvaffaqiyatli o'tsa, review qilinadi va main'ga merge qilinadi
   → CI: testlar yana ishga tushadi
4. Tag qo'yiladi (masalan, v1.0.0)
   → CD: Docker image (7.1-dars) quriladi va registriga yuklanadi
   → CD: production serverga deploy qilinadi
```

### GitHub Actions workflow fayli — testlar bosqichi

```yaml
# .github/workflows/ci-cd.yml
name: FastAPI CI/CD

on:
  push:
    branches: [main]
    tags: ['v*']
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_USER: test_user
          POSTGRES_PASSWORD: test_parol
          POSTGRES_DB: test_db
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-retries 5

    steps:
      - uses: actions/checkout@v4

      - name: uv o'rnatish
        uses: astral-sh/setup-uv@v3

      - name: Python o'rnatish
        run: uv python install 3.13

      - name: Bog'liqliklarni o'rnatish
        run: uv sync --frozen

      - name: Testlarni ishga tushirish
        env:
          DATABASE_URL: postgresql://test_user:test_parol@localhost:5432/test_db
          MAXFIY_KALIT: test-uchun-vaqtinchalik-kalit
        run: uv run pytest -v
```

| Qism | Vazifasi |
|---|---|
| `services: postgres` | CI muhitida, vaqtinchalik PostgreSQL konteynerini ishga tushiradi (6.2-darsda ko'rilgan "testlar uchun alohida baza" tamoyilining, CI kontekstidagi ko'rinishi) |
| `astral-sh/setup-uv@v3` | `uv`ni, GitHub Actions muhitiga tezkor o'rnatuvchi rasmiy action |
| `uv sync --frozen` | 0.2-darsda ko'rilgan, `uv.lock`ga asoslangan **takrorlanuvchi** o'rnatish |

### Docker build va push bosqichi

```yaml
  build-and-push:
    needs: test
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Docker Hub'ga kirish
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Image qurish va yuklash
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ${{ secrets.DOCKERHUB_USERNAME }}/kutubxona-api:${{ github.ref_name }}
            ${{ secrets.DOCKERHUB_USERNAME }}/kutubxona-api:latest
```

Bu bosqich — Git va GitHub darsligining 6.1-darsida chuqur o'rganilgan `needs: test` va `if: startsWith(...)` naqshlarini, aynan o'sha mantiq bilan (testlar o'tgandan keyin, faqat tag push qilinganda) qo'llaydi.

### Deploy bosqichi — qisqacha

```yaml
  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - name: Serverga ulanish va yangilash
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SERVER_SSH_KEY }}
          script: |
            cd /home/deploy/kutubxona-api
            docker compose pull
            docker compose up -d

```

> 📌 **`SERVER_SSH_KEY` — Git darsligiga bog'liqlik:** bu, Git va GitHub darsligining 3.1-darsida chuqur o'rganilgan SSH kalit tushunchasining, CI/CD kontekstidagi qo'llanilishi — GitHub Actions, serverga ulanish uchun, xuddi shaxsiy kompyuterdagi kabi, SSH kalitdan foydalanadi, faqat bu safar kalit, GitHub'ning **Secrets** mexanizmida xavfsiz saqlanadi.

### Barcha maxfiy ma'lumotlarni GitHub Secrets orqali boshqarish

Git va GitHub darsligining 6.1-darsida ko'rilganidek, hech qanday parol yoki kalit, workflow faylida ochiq yozilmaydi:

| Secret nomi | Vazifasi |
|---|---|
| `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN` | Docker Hub'ga image yuklash uchun |
| `SERVER_HOST`, `SERVER_USER`, `SERVER_SSH_KEY` | Production serverga ulanish uchun |

Bular, GitHub repository sozlamalarida, **Settings → Secrets and variables → Actions** orqali qo'shiladi.

## Amaliy misol — yakuniy, to'liq loyiha xulosasi

Ushbu darslik davomida, bosqichma-bosqich quyidagi to'liq loyihani qurdik:

```
kutubxona-api/
├── app/
│   ├── main.py                    # FastAPI + lifespan (6.3-dars)
│   ├── config.py                  # Sozlamalar, .env orqali (4.1-dars)
│   ├── database.py                # Async engine, session (4.4-dars)
│   ├── security.py                # Parol xeshlash, JWT (5.1-dars)
│   ├── dependencies.py            # Rol tekshiruvi (5.2-dars)
│   ├── models.py                  # SQLModel modellari (4.1-4.2-darslar)
│   └── routers/
│       ├── auth.py                # Ro'yxatdan o'tish, kirish (5.1-dars)
│       ├── kitoblar.py            # CRUD, WebSocket (3.1, 4.2, 6.1-darslar)
│       └── admin.py               # Rol-asosidagi endpoint'lar (5.2-dars)
├── migrations/                     # Alembic (4.3-dars)
├── tests/
│   ├── conftest.py                # Test fixture'lari (6.2-dars)
│   └── test_kitoblar.py
├── .github/workflows/ci-cd.yml     # CI/CD (ushbu dars)
├── Dockerfile                      # Multi-stage build (7.1-dars)
├── compose.yaml                    # FastAPI + Nginx + PostgreSQL (7.1-7.2-darslar)

├── pyproject.toml
├── uv.lock
└── .env                            # (gitignore qilingan)
```

Bu tuzilma — darslik boshida (0.1-darsda) qo'yilgan savolga ("FastAPI qачон tanlash kerak") to'liq, amaliy javob beradi: bitta, ixcham, yaxshi hujjatlashtirilgan, xavfsiz autentifikatsiyaga ega, ma'lumotlar bazasi bilan to'liq integratsiyalashgan, avtomatik test qilinadigan va CI/CD orqali production'ga uzluksiz yetkaziladigan REST API.

### FastAPI bilan keyingi qadamlar — qisqacha yo'l xaritasi

Ushbu darslik, FastAPI'ning asosiy va ko'p ilg'or imkoniyatlarini qamrab oldi, lekin ekotizim yanada kengroq. Keyingi o'rganish uchun tavsiya etiladigan yo'nalishlar:

| Mavzu | Qisqacha tavsif |
|---|---|
| GraphQL FastAPI bilan (`strawberry-graphql`) | REST'ga muqobil so'rov tili |
| Celery / RQ | Uzoq muddatli fon vazifalari (6.1-darsda qisqacha eslatilgan) uchun to'liq navbat tizimi |
| Redis kesh | Tez-tez so'raladigan ma'lumotlarni keshlash orqali unumdorlikni oshirish |
| Pytest coverage | Test qamrovini (`pytest-cov`) o'lchash va oshirish |
| Sentry / OpenTelemetry | Production xatolarini kuzatish va monitoring |
| Kubernetes | Docker Compose'dan, katta miqyosli orkestratsiyaga o'tish |

## Keng tarqalgan xatolar

**Xato 1:** CI muhitida, haqiqiy (yoki hatto lokal rivojlantirish) ma'lumotlar bazasidan foydalanishga urinish.
❌ Bu, CI jarayonini, tashqi, ba'zan mavjud bo'lmagan yoki xavfsiz bo'lmagan resursga bog'liq qiladi, va parallel ishga tushirilgan bir nechta CI ishlari, bir-birining ma'lumotlarini buzishi mumkin.
✅ To'g'ri: har doim, `services:` bo'limi orqali, CI ish jarayoni **ichida**, vaqtinchalik, izolyatsiya qilingan PostgreSQL konteynerini ishga tushiring (yuqoridagi misoldagi kabi).

**Xato 2:** Docker image'ni, har bir oddiy `push`da (hatto kichik, sinov commit'larida ham) qurish va registriga yuklash.
❌ Bu, keraksiz CI vaqtini va Docker registry saqlash joyini sarflaydi, va aniq versiyalanmagan, "tartibsiz" image'lar to'planishiga olib keladi.
✅ To'g'ri: Docker build/push bosqichini, faqat **rasmiy tag** (`v1.0.0` kabi) push qilinganda ishga tushiring — bu, Git va GitHub darsligining 5.3-darsida ko'rilgan Semantik Versiyalash tamoyiliga ham mos keladi.

**Xato 3:** deploy bosqichini, testlar yoki Docker build muvaffaqiyatsiz bo'lgan taqdirda ham ishga tushirilishi mumkin qilib qoldirish.
❌ Bu, sinovdan o'tmagan yoki noto'g'ri qurilgan kodning, to'g'ridan-to'g'ri production'ga yetib borishiga olib kelishi mumkin.
✅ To'g'ri: har bir keyingi bosqich, `needs: <oldingi_bosqich_nomi>` orqali, oldingi bosqichning **muvaffaqiyatli** yakunlanishiga qat'iy bog'liq bo'lishi kerak — bu, butun zanjir davomida (test → build → deploy) izchil qo'llanilishi shart.

## Mashq/topshiriq

**(Oson)** `.github/workflows/ci-cd.yml` faylida, faqat `test` bosqichini (yuqoridagi misoldagi kabi, PostgreSQL `services` bilan) yozing va uni, GitHub'ga push qilib, "Actions" bo'limida muvaffaqiyatli ishga tushganini tekshiring.

**(O'rtacha)** Yuqoridagi workflow'ga, `build-and-push` bosqichini qo'shing (Docker Hub'ga ulanish uchun, o'zingizning test akkountingiz bilan), va uni faqat `v*` tag push qilinganda ishga tushishini sozlang.

**(Qiyin)** Ushbu darslik davomida qurilgan barcha komponentlarni (Pydantic modellari, SQLModel, JWT autentifikatsiya, rol tekshiruvi, testlar, Docker, Nginx, CI/CD) birlashtiruvchi, kichik, lekin **to'liq** yangi loyiha (masalan, "Vazifalar ro'yxati — Todo API", foydalanuvchilar, vazifalar va rollar bilan) rejasini tuzing — har bir komponent uchun, qaysi darsdagi qaysi naqshdan foydalanishni aniq belgilab, qisqa (bir necha jumlali) reja yozing.

## Qisqacha xulosa

GitHub Actions orqali, FastAPI loyihasi uchun to'liq CI/CD zanjiri — testlarni (vaqtinchalik PostgreSQL `services` bilan) avtomatik ishga tushirishdan, muvaffaqiyatli tag push qilinganda Docker image qurish va yuklashdan, va nihoyat, SSH orqali production serverga avtomatik deploy qilishdan iborat — bu, Git va GitHub darsligida o'rganilgan barcha tamoyillarning (branch strategiyasi, Secrets, Semantik Versiyalash), FastAPI'ga xos amaliy qo'llanilishi. Ushbu darslik, FastAPI'ning asoslaridan (routing, Pydantic validatsiyasi) tortib, ma'lumotlar bazasi integratsiyasi, xavfsiz autentifikatsiya, testlash va to'liq production deploy jarayonigacha bo'lgan yo'lni bosib o'tdi — endi, bu bilimlar asosida, real, to'liq qamrovli API loyihalarini mustaqil qurish va ularni xavfsiz, ishonchli tarzda production'ga yetkazish mumkin.
